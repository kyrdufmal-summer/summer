# TIL | RAG 청크 오버랩과 LLM 지식 단절 시점 이해

- 학습일: 2026-11-13
- 범위: 공개 가능한 일반 기술 개념에 대한 학습 대화
- 기록 기준: 당일 대화에서 실제로 질문한 개념만 학습 사실로 기록하고, 구현·실행·테스트는 별도로 구분
- 공개 보안 원칙: 개인·기업·팀·고객 정보, 비공개 아이디어, 내부 주소, 인증정보, 원본 화면 캡처 제외

## 1. 오늘의 핵심 결론

오늘은 생성형 AI 및 RAG의 기본 개념을 질문·답변 형태로 확인했다. 핵심 주제는 **Chunk Overlap(청크 오버랩)**과 **Knowledge Cutoff(지식 단절 시점)**이다.

청크 오버랩은 긴 문서를 여러 조각으로 나눌 때 인접한 조각 사이에 일부 텍스트를 겹치게 배치하는 설정이다. 지식 단절 시점은 모델의 학습 데이터가 포함하는 정보의 시기적 한계를 가리킨다. 두 개념은 서로 다른 문제를 다룬다.

- 청크 오버랩: **검색용 문서의 문맥이 조각 경계에서 끊기는 문제**
- 지식 단절 시점: **모델이 학습 이후의 새로운 사실을 기본 지식만으로 알 수 없는 문제**

이 두 한계를 구분하는 것은 검색 증강 생성(RAG)을 이해하는 출발점이다.

## 2. 왜 이 개념을 학습했는가?

긴 문서를 LLM에 활용할 때는 문서를 통째로 한 번에 처리하는 대신 적당한 길이로 나누어 저장·검색하는 경우가 많다. 이때 중요한 문장이 두 청크 사이에 걸쳐 있으면 검색 결과가 맥락을 충분히 담지 못할 수 있다.

또한 모델이 그럴듯하게 답하더라도 학습 이후의 최신 사실을 반드시 알고 있는 것은 아니다. 이 문제를 해결하려면 최신 정보의 출처를 별도로 조회하거나 연결해야 한다.

따라서 **문서 분할 품질**과 **정보 최신성**은 서로 구분해 설계하고 검증해야 한다.

## 3. 당일 실제 학습 기록

당일 대화에서 다음 두 가지 개념 문제가 제시되었다.

1. “텍스트 분할 시 앞뒤 청크 사이에 일부러 겹치는 구간을 두어 문맥 단절을 방지하는 설정값”의 이름을 질문했다.
   - 해당 개념: **Chunk Overlap(청크 오버랩)**
2. “모델이 사전 학습을 마친 기준 시점 이후에 발생한 사건이나 최신 정보를 알지 못하는 LLM의 한계”를 질문했다.
   - 해당 개념: **Knowledge Cutoff(지식 단절 시점)**

두 개념의 명칭과 의미를 확인하는 학습이 진행되었다.

**확인 범위:** 대화에서 제시된 개념 질문. 실제 청크 분할 코드, 벡터 DB 색인, 검색 로그, 모델 응답 품질 측정 결과는 확인되지 않았다.

## 4. 초보자 설명: Chunk와 Chunk Overlap

### Chunk란?

Chunk는 긴 문서를 나눈 **텍스트 조각**이다. 예를 들어 긴 사용 설명서를 여러 단락으로 나누어 검색하기 쉬운 단위로 만드는 것이다.

문서가 너무 길면 검색 결과에 불필요한 내용이 많이 포함되거나 모델 입력 제한에 걸릴 수 있다. 반대로 너무 짧게 자르면 문장 사이의 의미가 끊길 수 있다.

### Overlap이란?

Overlap은 **겹치는 구간**이다. 첫 번째 청크의 마지막 부분을 두 번째 청크의 앞부분에 다시 포함시키는 방식이다.

가상의 문장 예시:

- 원문: “회원 등록 요청은 서버에서 검증한다. 검증에 성공하면 데이터베이스에 저장한다. 저장에 실패하면 오류를 반환한다.”
- 청크 A: “회원 등록 요청은 서버에서 검증한다. 검증에 성공하면”
- 청크 B(겹침 적용): “검증에 성공하면 데이터베이스에 저장한다. 저장에 실패하면 오류를 반환한다.”

두 청크에 “검증에 성공하면”이 함께 포함되어 문맥을 이어 주는 역할을 한다.

이 예시는 설명을 위해 새로 작성한 가상 문장이다.

### 왜 필요한가?

청크 경계에서 조건문과 결론이 분리되면 검색된 청크 하나만으로 의미를 이해하기 어려워질 수 있다. 적절한 오버랩은 이러한 경계 문제를 완화한다.

단, 오버랩이 클수록 저장량, 임베딩 처리량, 중복 검색 결과가 늘어날 수 있다. **많이 겹치게 할수록 항상 좋은 것은 아니다.**

## 5. Chunk Size와 Chunk Overlap의 차이

| 항목 | Chunk Size | Chunk Overlap |
|---|---|---|
| 의미 | 한 청크의 길이 | 인접 청크가 공유하는 길이 |
| 목적 | 검색·입력 단위 조절 | 경계 문맥 보존 |
| 너무 작거나 적으면 | 정보가 지나치게 잘림 | 경계에서 의미 단절 |
| 너무 크거나 많으면 | 불필요한 내용·비용 증가 | 중복 저장·검색 증가 |

문자 수, 토큰 수 등 무엇을 길이 단위로 사용하는지는 구현 라이브러리의 설정에 따라 다르다. 따라서 수치를 비교할 때는 단위부터 확인해야 한다.

## 6. 초보자 설명: Knowledge Cutoff

Knowledge Cutoff는 모델이 학습 과정에서 접한 정보의 시기적 한계를 뜻한다.

예를 들어 특정 시점까지 학습한 모델에 그 이후에 새로 바뀐 정책이나 출시된 제품을 묻는다면, 모델 내부 지식만으로는 최신 사실을 확정할 수 없다.

이는 모델의 모든 지식이 정확히 한 날짜에 멈춘다는 단순한 의미라기보다, **학습된 지식만으로 최신성을 보장할 수 없다**는 운영상 한계로 이해하는 것이 적절하다.

### 해결 접근

- 공식 문서 또는 신뢰할 수 있는 최신 출처 조회
- 검색 결과의 작성일·수정일 확인
- 출처와 답변을 함께 제공
- 검색 결과가 오래되었거나 충돌하면 불확실성 표시

단, 외부 검색이나 RAG를 붙였다는 사실만으로 최신성·정확성이 자동 보장되지는 않는다. 검색 결과 자체가 오래되었거나 잘못될 수 있기 때문이다.

## 7. RAG 전체 흐름과 두 개념의 위치

RAG는 Retrieval-Augmented Generation, 즉 **검색 증강 생성**이다.

일반적인 문서 준비 단계:

문서 수집 → 텍스트 정리 → 청크 분할(Chunk Size·Overlap 설정) → 임베딩 생성 → 벡터 저장소 색인

일반적인 질문 응답 단계:

사용자 질문 → 질문 임베딩 또는 검색어 생성 → 관련 청크 검색 → 근거 선별 → LLM에 질문·근거 전달 → 답변 생성 → 출처 제시

여기서 청크 오버랩은 주로 **문서 준비와 검색 품질**에 영향을 준다. 지식 단절 문제는 **외부 최신 정보 검색 및 근거 검증**으로 완화할 수 있다.

이 흐름은 일반적인 RAG 구조의 개념 설명이며 오늘 실제 시스템을 구축했다는 의미는 아니다.

## 8. 적용 사례: 가상 운영 매뉴얼 검색

가상의 운영 매뉴얼에 다음 내용이 있다고 가정한다.

“사용자가 같은 요청을 다시 보내더라도 서버는 중복 처리를 방지해야 한다. 단, 실패한 요청은 상태를 확인한 뒤 안전하게 재시도할 수 있다.”

청크가 잘못 나뉘면 “중복 처리 방지”와 “재시도 허용 조건”이 서로 다른 검색 결과로 분리될 수 있다. 이때 적절한 오버랩이나 문단 단위 분할을 사용하면 관련 조건을 함께 검색할 가능성이 높아진다.

그러나 청크를 겹치게 했더라도 검색 순위가 낮거나 근거가 누락되면 정확한 답변이 보장되지 않는다.

## 9. 실무에서 예상할 수 있는 실패 시나리오

### 실패 A: 오버랩을 0으로 설정

- **가능한 문제:** 조건과 결과가 청크 경계에서 분리됨
- **대응:** 의미 단위 분할, 적절한 오버랩, 검색 평가
- **검증:** 경계에 걸친 질문의 정답 근거가 검색되는지 확인

### 실패 B: 오버랩을 지나치게 크게 설정

- **가능한 문제:** 중복 청크가 많아져 비용·저장량 증가, 검색 결과 다양성 감소
- **대응:** 중복 제거, 청크 길이와 오버랩의 조합 비교
- **검증:** 색인 크기·검색 지연·정답 근거 회수율 비교

### 실패 C: 최신 정보를 내부 지식으로만 답변

- **가능한 문제:** 정책·가격·일정 등의 최신 변경 누락
- **대응:** 공식 최신 자료 검색 및 날짜 확인
- **검증:** 답변의 핵심 사실이 최신 출처와 일치하는지 대조

### 실패 D: 검색 결과를 무조건 사실로 간주

- **가능한 문제:** 오래되거나 신뢰도가 낮은 자료를 근거로 잘못된 답변 생성
- **대응:** 출처 신뢰성·발행일·문서 버전 확인
- **검증:** 근거 문장과 최종 답변의 일치 여부 평가

이 실패 사례들은 일반적인 설계 위험을 설명하기 위한 가정이며 당일 발생한 실제 장애가 아니다.

## 10. 성능을 어떻게 검증할까?

실무에서는 오버랩 수치 자체보다 **질문에 필요한 근거를 정확하게 찾는지**를 측정하는 것이 중요하다.

추천 검증 항목:

1. **Recall@k:** 정답 근거가 상위 k개 검색 결과 안에 포함되는 비율
2. **검색 중복률:** 상위 검색 결과에 거의 같은 내용이 반복되는 정도
3. **응답 지연:** 검색과 생성에 걸린 시간
4. **처리 비용:** 임베딩 생성량, 저장량, 모델 입력 토큰량
5. **근거 충실도:** 생성된 답변이 검색된 자료로 뒷받침되는 정도
6. **최신성:** 답변에 사용한 문서의 발행일과 변경 시점

측정할 때는 동일한 평가 질문 집합과 동일한 검색 조건을 사용해야 설정별 비교가 공정해진다.

오늘 위 지표를 실제 측정한 기록은 없다.

## 11. 실험 설계 예시

실제 구현 시에는 문서 유형에 맞춰 다음과 같은 비교 실험을 계획할 수 있다.

| 실험군 | Chunk Size | Overlap | 목적 |
|---|---:|---:|---|
| A | 500토큰 | 0토큰 | 겹침 없는 기준선 |
| B | 500토큰 | 50토큰 | 적은 겹침 |
| C | 500토큰 | 100토큰 | 중간 겹침 |
| D | 800토큰 | 100토큰 | 큰 청크 비교 |

위 수치는 **가상의 실험 설계 예시**이며 최적값이나 실측 결과가 아니다. 문서 언어, 길이, 제목 구조, 검색기 종류에 따라 결과가 달라질 수 있다.

  - **상태:** 용어 확인

## 13. 근거 수준과 공개 검토

**당일 직접 확인한 근거:** 대화에서 두 용어를 묻는 질문이 제시되었다. 화면 이미지도 제공되었으나 원본 이미지는 공개 문서에 포함하지 않는다.

**일반 기술 설명:** 청크 분할·오버랩, 학습 시점의 한계, RAG 처리 단계와 평가 지표는 개념 설명이다.

**추정·미검증:** 실제 라이브러리 설정값, 문서 색인 결과, 검색 품질, 응답 정확도, 배포 결과, 외부 문서 검토 여부.

**증거 확인일:** 2026-11-13. 실제 명령 출력·테스트 리포트·PR·이슈·실험 로그가 확인되지 않았으므로 관련 링크나 수치를 만들지 않는다.

**공개 제외:** 개인·가족·기업·팀·고객 관련 대화, 비공개 프로젝트 설계, 내부 주소·파일·스크린샷, 인증정보. 예시는 새로 작성한 가상 데이터만 사용한다.

## 14. 다음 과제

1. 실제로 사용할 공개 문서 또는 권한이 확인된 테스트 문서를 선정한다.
2. 문서 구조를 분석하고 의미 단위 분할 기준을 정한다.
3. 청크 길이·오버랩 조합을 3~4개 설정한다.
4. 질문·정답 근거가 포함된 평가 세트를 만든다.
5. Recall@k, 중복률, 비용, 지연시간을 측정한다.
6. 최신 정보가 필요한 질문에는 출처와 날짜 확인 절차를 적용한다.
7. 검색 근거가 없을 때 답변을 보류하거나 불확실성을 표시하도록 설계한다.

청크 오버랩은 **문서 경계에서 의미가 끊기는 문제**를 완화하는 기술이고, 지식 단절 시점은 **모델 내부 지식의 최신성 한계**를 설명하는 개념이다.

두 문제를 해결하는 방법도 다르다. 전자는 문서 분할·검색 품질을 개선하고, 후자는 최신 근거의 검색과 검증을 강화해야 한다.

**핵심 원칙: RAG에서는 많이 저장하는 것보다 필요한 근거를 정확히 찾고, 그 근거가 언제의 정보인지 확인하는 것이 중요하다.**
