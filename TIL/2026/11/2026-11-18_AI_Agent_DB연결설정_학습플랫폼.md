# TIL — 2026-11-18 | AI Agent 실습: 데이터베이스 연결과 학습 플랫폼

> 공개용 독립 학습 기록. 개인·기업·팀 식별정보, 내부 문서, 원본 화면, 인증정보 및 비공개 코드는 포함하지 않는다.

## 1. 오늘의 학습 목표
AI Agent 실습 중 PostgreSQL 데이터베이스 생성과 연결 설정의 차이를 이해하고, 강의 내용을 자신에게 맞게 설명하는 학습 콘텐츠 플랫폼을 구상했다.

### 대화로 확인한 사실
- 데이터베이스를 반복해서 생성하는 이유를 질문했다.
- 데이터베이스 이름을 새로 만들지 않고 변경할 수 있는지 질문했다.
- 환경설정에 값을 추가해야 하는지 질문했다.
- 실습 중 false라는 결과가 나왔다고 보고했다.
- 학습 설명용 웹사이트를 만들기 위해 별도 AI 도구에 초기 요청을 전달했다고 보고했다.
- 상세 블로그 콘텐츠는 아직 전달하지 않았다고 밝혔다.

### 미검증
실제 DB 연결 성공, false의 원인, 데이터베이스 변경 완료, 웹사이트 구현·테스트·배포는 독립적으로 검증하지 못했다.

## 2. 문제 정의: 생성, 이름 변경, 연결 대상 변경은 다르다
PostgreSQL 서버를 건물이라고 보면 데이터베이스는 방이고 연결 설정은 어느 방에 들어갈지를 지정하는 안내문이다. 설정에서 이름을 바꾸는 것만으로 새 방이 생기거나 기존 방의 이름이 변경되지는 않는다.

- DB 생성: 서버 안에 새 데이터베이스를 추가한다.
- DB 이름 변경: 존재하는 데이터베이스 자체의 이름을 바꾼다.
- 연결 대상 변경: 애플리케이션이 접속하는 데이터베이스를 지정한다.

실무에서는 기존 데이터와 접속 중인 다른 프로그램이 있으므로, 변경 전에 실제 대상과 영향 범위를 확인한다.

## 3. 정상 데이터 흐름
사용자 → 웹 UI → API Router → Service → Repository → DB Connection/Session → PostgreSQL → 결과 → UI

| 계층 | 역할 | 오류 사례 |
|---|---|---|
| UI | 사용자 입력·표시 | 저장 전 성공 표시 |
| Router | HTTP 요청 수신 | 잘못된 경로 |
| Service | 업무 규칙·흐름 제어 | 실패 처리 누락 |
| Repository | DB 조회·저장 | 잘못된 테이블 접근 |
| Connection/Session | 접속·트랜잭션 관리 | 연결 실패·누수 |
| PostgreSQL | 데이터 영속 저장 | DB·테이블 불일치 |

이는 일반적인 설명 흐름이며 오늘 실제 구현 완료를 뜻하지 않는다.

## 4. 안전한 검증 절차
1. 기존 데이터베이스의 존재 여부를 먼저 확인한다.
2. 실행 중인 프로그램이 어느 데이터베이스에 접속하는지 확인한다.
3. 연결 대상만 바꿀지, DB 자체의 이름을 바꿀지 결정한다.
4. 설정을 최소한으로 변경하고 재연결한다.
5. 연결 성공과 실제 테이블 조회 성공을 각각 검증한다.
6. 기존 데이터가 유지되는지 확인한다.

일반적인 확인용 SQL 예시(실행했다는 뜻이 아님):

~~~sql
SELECT current_database();
SELECT current_schema();
SHOW search_path;
~~~

실제 호스트명·계정명·비밀번호·접속 문자열은 공개 로그에 남기지 않는다.

## 5. false 결과의 원인 분석
불리언 false는 항상 같은 의미가 아니다. 연결 검사 실패, 존재 여부 검사 결과, 조건식 불일치, 테스트 실패 등 여러 가능성이 있다. 오늘의 대화만으로는 어떤 명령에서 나온 값인지 확정할 수 없으므로 **원인 미확인**으로 기록한다.

실무 진단에서는 입력 → 실행 함수 → 반환 조건 → 로그 → 실제 시스템 상태 순으로 확인한다. false만 보고 DB를 다시 생성하거나 설정을 무작정 변경하면 문제를 키울 수 있다.

## 6. AI 학습 콘텐츠 플랫폼 설계
오늘은 강의 설명용 사이트와 유사한 학습 플랫폼을 만들고 싶다는 요구와 초기 AI 개발 도구 요청 사실을 확인했다. 실제 플랫폼의 완성 여부는 확인되지 않았다.

공개 가능한 독립 콘텐츠는 다음과 같이 구성할 수 있다.
- 용어와 쉬운 비유
- 왜 필요한지, 없으면 어떤 문제가 생기는지
- UI부터 DB까지 요청 흐름
- 정상·비정상·재시도·부분 실패 사례
- 검증 체크리스트와 복습 문제

원본 강의 자료를 그대로 게시하지 않고, 재배포 권한을 확인한 후 독자적으로 설명을 작성하는 방식이 안전하다.

## 7. RAG와의 연결
일반 SQL 조회는 구조화된 행을 조건으로 검색하고, 임베딩 기반 검색은 문장의 의미적 유사성을 이용한다. 가상의 RAG 흐름은 문서 → 청크 분할 → 임베딩 → 검색 → 근거 확인 → LLM 답변이다. 모든 학습 사이트에 벡터 DB가 필요한 것은 아니다.

## 8. 비정상 흐름과 위험
- 설정에 없는 DB를 지정하면 접속이 실패할 수 있다.
- DB 접속은 성공했지만 테이블이 없으면 실제 기능은 실패할 수 있다.
- 설정 파일이나 디버깅 로그에 비밀번호가 있으면 공개 시 정보 유출 위험이 생긴다.
- AI가 만든 학습 설명은 원본 근거와 검증 없이 사실로 단정해서는 안 된다.

위 사례는 학습용 가정이며 당일 실제 장애 발생을 의미하지 않는다.

## 9. 장단점 및 트레이드오프
| 선택 | 장점 | 주의점 |
|---|---|---|
| 기존 DB 재사용 | 데이터 연속성 | 다른 실습과 충돌 가능 |
| 새 DB 생성 | 실습 격리 | 중복·관리 부담 |
| 설정에서 연결 대상 변경 | 코드 수정 최소화 | 실제 DB 존재 확인 필요 |
| 학습 콘텐츠와 UI 분리 | 재사용·수정 용이 | 콘텐츠 버전 관리 필요 |

## 10. 재발 방지와 다음 과제
실습 전 현재 연결 DB와 변경 목적을 확인한다. false가 나오면 실행 함수의 반환 조건을 확인한다. 학습 사이트는 우선 공개 가능한 독립 설명과 검증 문제를 구성하고, 이후 UI 생성 결과를 테스트한다. 실습 완료 여부는 화면·로그·DB 조회로 구분해 기록한다.

## 11. 증거 수준과 최종 고찰
**확인:** 오늘의 질문과 진행 보고, 초기 제작 요청 전달 사실.
**추정:** false의 발생 원인과 시스템 구성.
**미검증:** DB 변경·연결 성공, 웹사이트 완성, 자동 테스트 통과.

결론: 데이터베이스를 생성하는 행위와 연결 대상을 지정하는 행위를 구분하고, 반환값 하나만으로 실패 원인을 확정하지 않는 것이 핵심이다. 학습 플랫폼도 구현 완료보다 콘텐츠 정확성과 검증 기준을 먼저 갖춰야 한다.
