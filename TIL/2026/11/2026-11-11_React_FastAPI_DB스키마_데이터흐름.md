# TIL | React·FastAPI·PostgreSQL 데이터 흐름과 스키마 변경 검증

- 학습일: 2026-11-11
- 학습 분야: React, Next.js, FastAPI, PostgreSQL, SQLAlchemy, API 설계, 데이터 무결성
- 공개 원칙: 당일 대화에서 확인된 학습·설계만 기록하고 개인·기업·팀 기밀 및 내부 시스템 정보는 제외한다.
- 증거 구분: 확인된 대화 / 기술적 설명 / 가설·미검증

## 1. 핵심 결론

회원관리 화면에 새로운 `gender` 필드를 추가할 때는 프론트엔드 입력창뿐 아니라 API 요청 모델, 업무 로직, ORM 모델, 실제 PostgreSQL 테이블을 함께 점검해야 한다. 특히 같은 이름의 테이블이 여러 스키마에 있을 수 있으므로 **어떤 DB 연결이 어떤 스키마를 사용하는지 확인하기 전에는 구조를 변경하지 않는 것**이 중요하다.

오늘은 데이터 흐름과 스키마 불일치 문제를 추적했지만, 성별 필드의 최종 저장 성공을 입증하는 테스트 결과는 확보하지 않았다.

## 2. 문제 정의와 학습 목적

기존 회원 데이터에 성별을 추가하려면 사용자가 입력한 값이 화면에서 끝나지 않고 서버 검증과 데이터베이스 저장까지 전달되어야 한다. 한 계층만 바꾸면 화면에는 입력값이 보여도 API가 값을 무시하거나 DB 저장에 실패할 수 있다.

**핵심 질문:** 지금 실행 중인 API는 실제로 어느 DB·스키마·테이블을 사용하며, 새 필드는 어느 계층까지 전달되는가?

## 3. 실제 확인된 대화와 문제 상황

당일 학습 대화에서 다음 내용을 확인했다.

- 프론트엔드와 기존 FastAPI 실습 서버를 연결하는 흐름을 다뤘다.
- DB 연결 설정 코드에 명시적인 `search_path`가 보이지 않는다는 점을 확인했다.
- `public.members`와 `practice.members`처럼 동일한 이름의 테이블을 서로 다른 스키마에서 구분해야 했다.
- Swagger의 회원 등록 요청 모델에 `name`, `email`, `age`가 나타나지만 `gender`는 표시되지 않는 상황을 다뤘다.
- 기존 데이터를 보존한 상태에서 성별 컬럼만 추가해야 한다는 요구를 확인했다.
- `ALTER TABLE`이 기존 행을 모두 삭제하는 명령인지에 관한 오해를 바로잡았다.

**미확인:** 실행 중인 SQLAlchemy 세션의 최종 유효 `search_path`, 성별 컬럼의 실제 추가 완료, POST/PATCH 및 DB 재조회 성공.

## 4. 전체 데이터 흐름

회원 등록의 기대 흐름:

사용자 → React 입력 폼 → `fetch()` POST → FastAPI Router → Pydantic Schema → Service → Repository → SQLAlchemy Session → PostgreSQL → 커밋 → API 응답 → React 화면

| 계층 | 책임 | 빠졌을 때 생길 수 있는 문제 |
|---|---|---|
| React Form | 사용자 입력과 상태 관리 | 성별 입력·전송 누락 |
| fetch | HTTP 요청 전송 | 요청 본문에 필드가 빠짐 |
| Router | URL·HTTP 메서드와 처리 함수 연결 | 요청이 올바른 기능에 도달하지 못함 |
| Pydantic Schema | 타입·형식·필수 여부 검증 | 필드가 거부·무시되거나 잘못된 값 통과 |
| Service | 업무 규칙과 트랜잭션 조율 | 규칙 누락·부분 처리 |
| Repository | DB 조회·저장 작업 | 컬럼 저장 누락 |
| ORM Model | Python 속성과 DB 컬럼 매핑 | 실제 DB 구조와 불일치 |
| PostgreSQL | 데이터의 영구 보관 | 컬럼이 없으면 저장 실패 가능 |

이 흐름은 학습용 정상 경로이며, 오늘 모든 단계의 성공을 확인한 실행 로그는 없다.

## 5. 초보자 개념: 데이터베이스·스키마·테이블

PostgreSQL의 데이터베이스는 저장 공간이고 스키마는 그 안에서 객체를 구분하는 이름 공간이다. `public.members`와 `practice.members`는 이름이 같아도 별개 테이블이다.

SQL에서 스키마를 생략하고 `members`만 쓰면 세션의 `search_path`에 따라 탐색한다. 연결 코드에 `search_path` 설정이 없다는 사실만으로 실제 적용 중인 값까지 확정할 수는 없다. ORM 모델에 스키마가 명시돼 있는지도 확인해야 한다.

**검증용 SQL 예시(오늘 실행했다고 주장하지 않음):**

```sql
SELECT current_database(), current_schema();
SHOW search_path;

SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_name = 'members';

SELECT table_schema, table_name, column_name, data_type
FROM information_schema.columns
WHERE table_name = 'members'
ORDER BY table_schema, ordinal_position;
```

## 6. ALTER TABLE과 데이터 보존

`ALTER TABLE`은 테이블의 구조를 바꾸는 SQL 명령이다. 기존 테이블에 컬럼을 추가하는 예시는 다음과 같다.

```sql
-- 실제 대상 테이블과 기존 컬럼 여부를 확인한 뒤에만 적용할 예시
ALTER TABLE public.members
ADD COLUMN gender VARCHAR(20);
```

일반적으로 컬럼 추가는 기존 행을 삭제하지 않는다. 기존 행의 새 컬럼 값은 별도 기본값·갱신이 없으면 NULL이 된다. 다만 잘못된 테이블을 변경하거나 제약 조건·기본값을 부주의하게 적용하면 장애가 날 수 있다.

**실무 절차:** 대상 DB 확인 → 스키마·컬럼 조회 → 기존 데이터 보존 정책 확인 → 마이그레이션 작성·검토 → 테스트 환경 적용 → API 검증 → DB 재조회.

위 SQL은 설명용이며 오늘 실제로 실행·성공한 것으로 기록하지 않는다.

## 7. gender 필드를 추가할 때 확인할 파일과 이유

### React 컴포넌트
입력 UI와 상태를 추가하고 POST/PATCH 요청 본문에 `gender`가 포함되는지 확인한다. 화면에 값이 보여도 전송 코드에 없으면 서버에 도달하지 않는다.

### Pydantic 요청·응답 Schema
허용 값, 필수 여부, null 허용 여부를 정의한다. 특히 PATCH에서 **필드 생략**과 **명시적 null**은 업무 정책상 다르게 해석될 수 있다.

### Router
실제 요청 경로와 연결된 Schema·Service가 맞는지 확인한다. 수정한 파일과 실행 중인 서버가 다르면 Swagger에 새 필드가 보이지 않을 수 있다.

### Service
업무 규칙과 변경 가능 여부를 판단한다. 단순 데이터 매핑과 별도로 검증해야 하는 규칙을 정의한다.

### Repository·ORM Model
실제 저장 대상 테이블과 컬럼을 매핑하고, 조회·수정 SQL이 변경 필드를 처리하는지 확인한다.

### PostgreSQL
기존 데이터가 있는 **실제 대상 테이블**에 컬럼이 존재하는지 확인한다.

## 8. HTTP 메서드와 검증

| 메서드 | 목적 | 검증 예시 |
|---|---|---|
| GET | 회원 목록·상세 조회 | 응답 필드와 DB 조회 일치 |
| POST | 회원 생성 | 응답 후 DB에서 새 행 확인 |
| PATCH | 일부 값 수정 | 생략/null 정책과 재조회 확인 |
| DELETE | 삭제 요청 | 응답 상태와 이후 조회 확인 |

Swagger에 요청 모델이 보인다는 사실은 문서와 서버 스키마를 점검할 근거지만, DB 저장 성공의 증거는 아니다. 브라우저 Network, 서버 응답, DB 조회를 함께 확인해야 한다.

## 9. 시행착오와 원인 분석

### 같은 테이블 이름을 여러 곳에서 발견
- **원인 가능성:** 여러 스키마에 `members`가 존재하거나 연결 대상이 예상과 다름.
- **대응:** DB 이름, 세션 `search_path`, ORM 모델 스키마, 실제 컬럼 목록을 순서대로 확인.
- **상태:** 확인 방향 정리, 최종 대상 확정 미검증.

### Swagger에 gender가 보이지 않음
- **원인 가능성:** 요청 Schema 미수정, 다른 Router·앱 실행, 서버 재시작 누락 등.
- **대응:** 실제 등록 엔드포인트가 참조하는 요청 모델을 추적하고 서버를 다시 확인.
- **상태:** 원인 후보 식별, 최종 해결 미확인.

### ALTER TABLE이 기존 데이터를 삭제하는지 혼동
- **개념 정리:** `ADD COLUMN`은 일반적으로 기존 행을 보존하면서 새 컬럼을 추가한다.
- **주의:** 데이터 손실을 유발할 수 있는 `DROP` 계열 명령과 구분한다.
- **상태:** 개념 설명 완료, 실제 마이그레이션 검증 미확인.

## 10. 실무 비정상 흐름과 위험

1. **화면만 성공:** React 상태만 바뀌고 서버 저장이 실패했는데 성공 메시지를 표시한다.
2. **API·DB 불일치:** API가 기대하지 않은 스키마를 조회해 다른 데이터를 보여준다.
3. **중복 등록:** 더블클릭이나 재시도로 중복 데이터가 생성된다. 서버 검증과 DB 유니크 제약이 필요하다.
4. **동시 수정:** 여러 요청이 같은 행을 덮어쓸 수 있다. 필요한 경우 버전 검사나 잠금 전략을 고려한다.
5. **삭제 실패 후 UI 불일치:** 서버 응답 전 화면에서만 항목을 지우면 사용자에게 잘못된 상태가 보일 수 있다.

이는 일반적인 운영 사고 시나리오이며 당일 실제 발생한 장애로 확인된 것은 아니다.

## 11. 인접 주제 학습: 발주 중심 SCM SaaS

당일 대화에서는 발주를 편리하게 만드는 업무 시스템의 설계 관점도 논의했다.

일반화된 흐름은 다음과 같다.

공급업체 등록 → 품목·SKU 관리 → 발주 → 입고 → 재고 반영 → 출고 → 변경 이력 관리

- **SKU:** 재고를 식별하고 관리하는 상품 단위.
- **멀티테넌트:** 여러 고객사가 하나의 SaaS를 사용하더라도 데이터와 권한을 분리하는 구조.
- **출고와 판매:** 유통 운영에서는 실제 재고 이동인 출고와 매출·판매 확정의 의미가 다를 수 있다.
- **이력 관리:** 변경 기록은 추적·감사에 유리하지만 법정 삭제 의무와 보존 기간을 함께 검토해야 한다.

**상태:** 설계 논의. 실제 SaaS 개발·배포·운영 완료를 입증하는 결과는 없음.

## 16. 최종 고찰

필드 하나를 추가하는 작업도 화면·API·ORM·DB가 일치해야 완성된다. 실제 연결 경로를 확인하지 않은 상태에서 데이터베이스를 수정하면 문제 해결보다 새로운 오류를 만들 수 있다.

**핵심 원칙: 연결 대상을 먼저 확인하고, 변경 후에는 화면·API·DB의 결과를 각각 검증한다.**
