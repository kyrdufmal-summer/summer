# TIL | FastAPI 회원 API 필드 확장과 계층별 데이터 흐름 검증

- 학습일: 2026-11-12
- 범위: Python, FastAPI, Pydantic, SQLAlchemy ORM, PostgreSQL, React
- 공개 범위: 일반 기술 학습만 기록. 특정 조직·고객·프로젝트·내부 시스템 정보는 포함하지 않음.
- 근거 수준: 당일 학습 대화에 나타난 진행 내용과 일반 기술 설명을 구분함.

## 1. 핵심 결론

회원 API에 필드를 추가할 때 데이터베이스 컬럼 하나만 바꿔서는 충분하지 않다. **DB 컬럼 → ORM 모델 → API 요청·응답 스키마 → Repository 저장 로직 → 프론트엔드 요청·상태**가 서로 일치해야 한다.

당일 학습에서는 회원 데이터가 들어 있는 기존 테이블을 확인하고, 새 필드를 DB·ORM·API 스키마로 연결하는 과정을 단계적으로 진행했다. 전체 프론트엔드 통합 테스트와 모든 CRUD 시나리오의 최종 통과는 별도로 검증해야 한다.

## 2. 왜 이 작업을 했는가?

사용자 입력 화면에 새 필드를 만들었더라도 서버가 그 필드를 받지 않거나 DB에 컬럼이 없다면 데이터는 저장되지 않는다. 반대로 DB 컬럼만 존재하고 API 응답 스키마에 빠져 있다면 화면에서 조회할 수 없다.

따라서 오늘의 학습 목표는 다음과 같다.

1. 현재 API가 실제로 사용하는 DB·스키마·테이블을 먼저 식별한다.
2. 기존 회원 데이터를 유지하면서 필드를 확장한다.
3. Python ORM과 Pydantic 스키마를 실제 DB 구조에 맞춘다.
4. 저장과 응답 흐름에서 값이 누락되지 않는지 확인할 준비를 한다.

## 3. 실제 진행 기록과 검증 범위

당일 학습 대화에서 확인된 진행 내용:

- 기존 회원 데이터가 보존되어 있는 대상 테이블을 식별했다.
- 새 필드를 위한 DB 컬럼 추가를 진행했다.
- SQLAlchemy ORM 모델의 필드 정의를 연결했다.
- Pydantic의 등록 입력 및 응답 스키마를 연결했다.
- Repository의 저장 로직까지 이어지는 작업을 검토했다.
- 도구가 코드를 일괄 생성하는 방식보다 직접 파일을 하나씩 확인하면서 이해하는 학습 방식을 택했다.

**확인 수준 주의:** 위 내용은 대화상 진행 기록이다. 이 TIL 작성 시점에 터미널의 원본 출력, 데이터베이스 쿼리 결과, 자동 테스트 리포트를 새로 실행·수집하지 않았다. 따라서 전체 기능이 최종 통과했다고 단정하지 않는다.

## 4. 초보자 개념 정리

### 데이터베이스 컬럼

테이블에서 각 행이 가지는 데이터 항목이다. 기존 데이터가 있는 테이블에 컬럼을 추가할 때는 기존 행의 값이 어떻게 처리되는지도 고려해야 한다.

### ORM 모델

SQLAlchemy ORM 모델은 Python 코드의 객체와 데이터베이스 테이블을 연결하는 정의다. ORM 모델에 속성이 있다고 실제 DB에 컬럼이 자동으로 생기는 것은 아니다. 반대도 마찬가지다.

### Pydantic 스키마

API가 어떤 입력을 허용하고 어떤 응답을 반환하는지 정의하는 데이터 계약이다. ORM 모델과 목적이 다르므로 필요한 필드가 각각 정의되어야 한다.

### Repository

데이터를 조회하고 저장하는 코드의 계층이다. 어떤 컬럼에 어떤 값을 기록할지 담당한다. 트랜잭션 경계를 Service가 소유하는 구조라면 Repository에서 임의로 commit하지 않는 것이 책임 분리에 유리하다.

### 트랜잭션

여러 데이터 변경을 하나의 작업 단위로 취급하는 개념이다. 성공하면 commit하고 실패하면 rollback해 중간 상태를 남기지 않도록 설계한다.

## 5. 전체 데이터 흐름

사용자 입력 → React State → HTTP JSON 요청 → FastAPI Router → Pydantic 요청 검증 → Service 업무 규칙 → Repository → SQLAlchemy ORM/Session → PostgreSQL → commit/rollback → API 응답 스키마 → React 화면

각 계층의 확인 포인트:

| 계층 | 확인 질문 | 잘못되면 발생할 수 있는 문제 |
|---|---|---|
| React | 입력값이 State에 있는가? | 화면에만 값이 존재 |
| HTTP 요청 | JSON에 필드가 들어 있는가? | 서버가 값을 받지 못함 |
| Router/Schema | 요청 모델이 필드를 허용하는가? | 검증 오류 또는 필드 누락 |
| Service | 업무 규칙과 트랜잭션이 올바른가? | 부분 성공·무결성 오류 |
| Repository | 필드를 저장 객체에 반영하는가? | DB 값 누락 |
| ORM | 실제 테이블과 매핑이 일치하는가? | 매핑·SQL 오류 |
| PostgreSQL | 실제 컬럼이 존재하는가? | INSERT/UPDATE 실패 |
| 응답 Schema | 반환 필드가 정의됐는가? | 저장돼도 화면에 보이지 않음 |

## 6. 안전한 필드 추가 절차

### Step 1. 대상 DB와 테이블 확인

스키마가 여러 개라면 같은 이름의 테이블이 존재할 수 있다. 다음은 일반적인 읽기 전용 점검 SQL이다.

```sql
SELECT current_database(), current_schema();
SHOW search_path;

SELECT table_schema, table_name, column_name, data_type
FROM information_schema.columns
WHERE table_name = 'members'
ORDER BY table_schema, ordinal_position;
```

이 SQL은 재현 가능한 예시이며 오늘 이 명령을 실행했다는 뜻이 아니다.

### Step 2. 기존 데이터 보존

테이블 구조 변경 전에 대상 테이블과 기존 데이터 상태를 확인한다. 운영 시스템에서는 마이그레이션 검토, 백업·복구 절차, 잠금과 배포 영향을 고려한다.

### Step 3. DB 컬럼 확장

```sql
-- 예시: 실제 적용 전 대상 스키마와 컬럼 존재 여부 확인
ALTER TABLE public.members
ADD COLUMN gender VARCHAR(20);
```

이 명령은 일반적으로 기존 행을 삭제하지 않고 컬럼을 추가한다. 기존 행의 새 컬럼은 기본값이 없다면 NULL이 된다. 실제 업무에서는 컬럼 타입·허용 값·NULL 정책을 API 계약과 일치시켜야 한다.

**주의:** 위 명령은 학습용 예시로, 실제 실행 결과를 주장하지 않는다.

### Step 4. ORM과 API 계약 변경

- ORM 모델: DB 컬럼과 대응되는 속성 정의
- 등록 요청 스키마: 새 필드의 타입·필수 여부 정의
- 응답 스키마: 저장된 값을 API 응답으로 전달
- Repository: 입력 필드를 저장 객체에 전달

### Step 5. 서버와 DB 재검증

Swagger의 요청·응답 모델, HTTP 상태 코드, 실제 DB 조회를 각각 확인한다. 화면에 값이 표시되는 것만으로 DB 저장 성공을 판정하지 않는다.

## 7. 정상 흐름과 비정상 흐름

### 정상 흐름

사용자가 입력 → 서버가 검증 → Repository가 저장 → Service가 트랜잭션을 완료 → 서버가 저장 결과 반환 → 프론트엔드가 성공 상태 표시.

### 비정상 흐름 A: API 스키마 누락

DB에는 컬럼이 있지만 Pydantic 요청 모델에 필드가 없다. 입력이 거부되거나 설정에 따라 무시될 수 있다. Swagger에 새 필드가 보이는지 먼저 확인한다.

### 비정상 흐름 B: ORM 불일치

API 스키마는 값을 받지만 ORM 모델 또는 Repository가 해당 값을 반영하지 않는다. DB 저장 결과를 직접 확인해야 한다.

### 비정상 흐름 C: 잘못된 스키마 선택

이름이 같은 테이블이 여러 스키마에 있으면 예상하지 않은 테이블을 변경할 수 있다. 연결 대상과 모델의 스키마 지정을 확인한다.

### 비정상 흐름 D: 재시도·중복 요청

사용자가 버튼을 두 번 누르거나 네트워크 타임아웃 후 재시도할 수 있다. 서버의 중복 검사와 DB 제약 조건, 필요한 경우 멱등성 전략을 고려한다.

### 비정상 흐름 E: 부분 실패

여러 변경 중 일부만 성공하면 데이터가 불일치할 수 있다. 트랜잭션 경계와 rollback 처리 여부를 점검한다.

이 사례들은 학습용 위험 시나리오이며 당일 실제 발생한 장애로 확인된 것은 아니다.

## 8. 시행착오에서 얻은 교훈

**문제:** 새 필드를 어디부터 수정해야 하는지 혼동하기 쉽다.

**원인:** 프론트엔드·요청 스키마·ORM·DB를 각각 독립된 파일로만 보면 데이터가 이동하는 전체 경로가 보이지 않기 때문이다.

**대응:** 실제 DB 대상을 확인한 뒤 계층별로 한 단계씩 수정하고, 각 단계의 책임을 설명하면서 검증한다.

**해결 수준:** DB·ORM·API 스키마 연결 작업의 진행 기록은 있으나, 최종 화면-API-DB 통합 성공을 입증하는 원본 로그는 미확인이다.

## 9. 설계 트레이드오프

| 접근 | 장점 | 위험 |
|---|---|---|
| 여러 파일을 한 번에 변경 | 빠름 | 실패 위치 파악 어려움 |
| 계층별로 단계적 변경 | 원인 추적·학습에 유리 | 초기 작업 시간 증가 |
| DB 직접 변경 | 소규모 실습에 간단 | 변경 이력·재현성 부족 |
| 마이그레이션 도구 사용 | 배포·버전 관리에 유리 | 도구·절차 학습 필요 |
| 프론트엔드만 검증 | UI 피드백이 빠름 | 실제 저장 실패를 놓칠 수 있음 |
| API·DB까지 검증 | 데이터 무결성 확인 가능 | 테스트 환경과 준비 필요 |

## 10. 재발 방지 체크리스트

- [ ] 현재 서버가 사용하는 DB와 스키마를 확인했다.
- [ ] 기존 행과 컬럼 구조를 확인했다.
- [ ] DB 변경 전에 데이터 보존·복구 방안을 검토했다.
- [ ] ORM과 요청·응답 스키마를 일치시켰다.
- [ ] Repository가 새 필드를 실제 저장에 반영한다.
- [ ] Swagger의 요청·응답 계약을 확인했다.
- [ ] POST/PATCH 이후 GET과 DB 재조회 결과를 확인했다.
- [ ] 누락/null·중복 요청·실패 응답을 테스트했다.

이 목록은 완료 증명이 아닌 향후 검증 기준이다.

## 13. 최종 고찰

실무에서 중요한 것은 코드를 많이 수정하는 속도가 아니라 **데이터가 실제로 어느 계층을 지나 저장되고, 실패하면 어디에서 멈추는지 설명할 수 있는 능력**이다.

회원 API의 필드 확장은 작은 기능처럼 보이지만 스키마 계약, 트랜잭션, DB 구조, 프론트엔드 상태를 함께 이해하는 좋은 연습이 된다. 확인된 결과와 미검증 사항을 분리하는 습관도 코드 자체만큼 중요하다.
