# TIL | LLM CLI 입력 검증과 Mock·Live 실행 경로

- 학습일: 2026-11-16 (KST)
- 주제: Python CLI, LLM API 호출, Mock/Live, 입력 검증, 비용 통제
- 공개 범위: 일반 기술 학습 내용과 독립적인 가상 예시만 포함
- 기록 원칙: 대화에서 확인된 문제와 설명을 구분하고 원본 실행 로그가 없는 결과는 별도 표기

## 1. 오늘의 핵심 결론

CLI 프로그램에서 사용자가 빈 질문을 입력했을 때 기본 질문으로 자동 대체하면, `--live` 모드에서 의도하지 않은 실제 LLM API 호출이 발생할 수 있다. **입력 검증은 Mock/Live 분기보다 앞에 배치**하고, 호출 비용이 발생하는 경로에 도달하기 전에 빈 문자열을 차단해야 한다.

오늘의 핵심 학습은 API 연결 자체보다 **입력 → 검증 → 실행 모드 결정 → 외부 호출 → 결과 출력**의 책임과 순서를 이해하는 것이었다.

## 2. 왜 이 문제를 다뤘는가?

학습용 AI 비서 CLI에서 Mock 모드는 가짜 응답을 반환하고 Live 모드는 실제 모델 API에 요청을 보낸다. 그런데 빈 입력이 코드의 기본 질문으로 대체되면 사용자는 아무 질문도 하지 않았는데 Live API가 호출될 수 있다.

문제는 단순한 빈 문자열 처리가 아니라 비용, 사용자 의도, 외부 호출 제어와 연결된다. API 요청 전에 유효성을 확인하지 않으면 불필요한 토큰 사용과 예상하지 못한 동작이 발생한다.

## 3. 확인된 학습 대화와 증거 수준

### 확인된 대화
- 학습용 Python CLI에서 `--mock`과 `--live` 실행 차이를 비교했다.
- 빈 입력이 기본 질문으로 대체되어 Live 호출로 이어지는 문제를 제기했다.
- `default` 인자를 없애는 경우와 `default=None`의 차이를 학습했다.
- API 호출 전에 빈 입력을 차단하는 방향으로 코드 수정과 검증을 논의했다.
- CLI → 입력 검증 → 실행 모드 선택 → API 또는 Mock 응답 → 출력의 흐름을 정리했다.

### 실행 결과에 대한 주의
당일 대화에는 Mock 실행, Live API 1회 성공, 빈 질문 차단 PASS, 자동 테스트 130개 통과라는 **진행 보고**가 있었다. 하지만 이 공개 TIL 작성 시점에는 해당 명령의 원본 출력, 테스트 파일 목록, CI 기록을 독립적으로 재검증하지 않았다. 따라서 아래 설명에서는 이를 재현 가능한 검증 절차와 구분하며, 최종 검증 완료의 증거로 사용하지 않는다.

## 4. 초보자 개념

### CLI
Command Line Interface. 터미널에서 인자를 입력해 프로그램을 실행하는 방식이다. 예를 들어 실행 옵션으로 실제 API를 사용할지 가짜 응답을 사용할지 선택할 수 있다.

### Mock
실제 외부 API를 호출하지 않고 미리 정한 결과를 반환하는 테스트용 대체 구현이다. 빠르고 비용이 들지 않는다는 장점이 있지만 실제 네트워크·권한·요금·모델 응답까지 검증하지는 못한다.

### Live
실제 모델 제공자의 API를 호출하는 실행 방식이다. 네트워크, 인증, 모델 사용 권한, 사용량 제한, 비용이 영향을 준다.

### default와 None
CLI 인자 파서의 `default`는 사용자가 인자를 주지 않았을 때 사용할 값을 정한다. `default=None`은 값이 주어지지 않았음을 명시적으로 표현할 수 있지만, 프로그램의 다른 코드에서 `None`을 기본 질문으로 다시 바꾸면 같은 문제가 재발할 수 있다. 따라서 **기본값 제거만으로 외부 호출 방지가 보장되는 것은 아니다.**

### 토큰
LLM이 입력과 출력을 처리할 때 사용하는 텍스트 단위다. 실제 과금은 제공자·모델·요금제에 따라 다르며, 불필요한 요청을 줄이면 비용과 지연을 줄일 수 있다.

## 5. 전체 데이터 흐름

### 문제가 되는 흐름
사용자 빈 입력 → 기본 질문 자동 삽입 → Live 모드 선택 → 실제 API 호출 → 토큰 사용 → 응답 출력

### 개선된 흐름
사용자 입력 → 공백 제거 → 빈 입력 검사 → 유효한 질문일 때만 Mock/Live 분기 → 응답 출력

이 순서에서 중요한 것은 **외부 API 호출 이전에** 검증이 완료되는 것이다.

## 6. 재현 가능한 독립 예시

아래 코드는 학습 내용을 설명하기 위해 새로 작성한 최소 예시이며, 당일 실제 프로젝트의 소스코드를 복사한 것이 아니다.

```python
def normalize_question(raw: str | None) -> str:
    # None은 입력이 전달되지 않았다는 뜻으로 처리한다.
    return (raw or "").strip()

def run(question: str | None, live: bool) -> str:
    # 실제 API 또는 Mock 실행을 선택하기 전에 검증한다.
    normalized = normalize_question(question)
    if not normalized:
        return "질문을 입력해 주세요. 외부 API는 호출하지 않았습니다."

    if live:
        # 실제 호출 코드는 별도 API 클라이언트에 구현한다.
        return "유효한 입력: Live 호출 대상"
    return f"[MOCK] {normalized}"
```

이 예시에는 실제 API 클라이언트와 인증정보가 없으므로 네트워크 호출이 발생하지 않는다. 빈 입력을 차단하는 제어 흐름을 설명하기 위한 코드다.

## 7. 검증 시나리오

| 입력 | 실행 모드 | 기대 결과 |
|---|---|---|
| `""` | Mock | 입력 안내, Mock 처리도 불필요 |
| `"   "` | Live | 입력 안내, 외부 호출 0회 |
| `None` | Live | 입력 안내, 외부 호출 0회 |
| `"안녕"` | Mock | Mock 응답 |
| `"안녕"` | Live | 유효한 질문만 실제 API 호출 |
| 유효한 질문 + 네트워크 오류 | Live | 오류 안내, 실패 상태 기록 |

핵심 테스트는 **빈 입력일 때 실제 API 호출 함수가 단 한 번도 실행되지 않았는지**를 확인하는 것이다. 화면에 안내 문구가 나왔다는 사실만으로 API 미호출이 입증되는 것은 아니다. Mock 객체의 호출 횟수나 네트워크 요청 기록을 검사해야 한다.

## 8. 시행착오와 원인

### 빈 문자열인데도 토큰을 사용한 이유
가능한 원인은 빈 질문이 `default` 또는 후속 폴백 로직을 거쳐 유효한 기본 질문으로 변환된 것이다. 구체적인 원인 라인은 실제 실행 코드와 로그를 대조해야 확정할 수 있다.

### `default` 제거와 `default=None`은 같은가?
둘 다 파서와 인자 정의에 따라 입력이 없음을 나타낼 수 있지만, 명시적 `None`은 의도를 드러낸다. 중요한 것은 인자를 받은 뒤 호출 직전까지의 데이터 변환이다.

### 빈 질문이면 무조건 Mock으로 보내야 하는가?
반드시 그럴 필요는 없다. 입력이 없으면 Mock으로 전환하는 정책도 가능하지만, 일반적인 질의응답 CLI에서는 **입력 안내 후 호출하지 않는 방식**이 사용자 의도를 더 명확히 반영한다. Mock 전환이 실제 실행 결과인 것처럼 표시되지 않도록 주의해야 한다.

## 9. 실무 적용 사례

- **LLM 챗봇:** 빈 메시지·공백만 있는 메시지 차단
- **자동 요약:** 원문이 비어 있으면 모델 호출을 생략하고 원인 안내
- **배치 처리:** 비어 있는 작업 단위를 건너뛰고 누락 건수를 기록
- **외부 API:** 유효성 검사, 재시도 제한, 타임아웃, 비용 예산을 호출 경계에 배치

이는 일반화된 적용 사례이며 오늘 운영 서비스에 적용했다고 주장하지 않는다.

## 10. 장단점과 트레이드오프

| 방식 | 장점 | 한계 |
|---|---|---|
| 모든 요청을 Live로 전송 | 실제 모델 응답 확인 | 비용·지연·실패 가능성 |
| Mock 중심 개발 | 빠르고 저렴한 테스트 | 실제 API 호환성 검증 부족 |
| 빈 입력 차단 | 비용 절감·의도 명확화 | 입력 UX 설계 필요 |
| 빈 입력을 기본 질문으로 대체 | 데모 흐름 간단 | 사용자가 요청하지 않은 호출 발생 가능 |

## 11. 비정상 흐름과 운영 위험

빈 입력 외에도 네트워크 타임아웃 후 중복 재시도, 응답 형식 오류, 인증 실패, 사용량 한도 초과, 실제 API 실패를 Mock 성공으로 오인하는 문제가 있다.

특히 **Mock PASS는 Live PASS가 아니다.** Mock 테스트와 실제 API 통합 테스트를 분리하고, Live 테스트에는 비용·호출 횟수 제한을 적용해야 한다.

## 12. RAG·Agent 학습과의 연결

오늘의 CLI 학습은 이후 문서 검색과 도구 사용을 결합하는 AI Agent의 기초다.

일반적인 확장 흐름:
사용자 질문 → 입력 검증 → 필요 시 문서 검색(RAG) → 도구 호출 여부 결정 → 외부 작업 → 응답·근거 반환

- **RAG:** 외부 문서를 검색해 답변 근거로 활용한다.
- **Embedding:** 텍스트의 의미를 벡터로 표현한다.
- **Vector DB:** 벡터를 저장하고 유사한 문서를 검색한다.
- **Tool Calling:** 모델 또는 실행기가 외부 도구를 호출하는 구조다.
- **MCP:** 도구·데이터 소스 연결을 표준화하는 프로토콜이다.
- **Memory:** 이전 상호작용의 유용한 정보를 유지·활용하는 기능이다.
- **Workflow:** 작업 순서와 조건·오류 처리를 명시적으로 정의한 실행 흐름이다.

위 개념은 학습 내용이며 오늘 모든 기능을 실제 구현·검증한 것은 아니다.

## 15. 최종 고찰

AI 기능을 구현할 때 중요한 것은 모델 호출을 성공시키는 것만이 아니다. **어떤 조건에서 호출하면 안 되는지**를 먼저 설계해야 한다. 입력 검증은 비용, 신뢰성, 사용자 의도, 오류 대응의 출발점이다.
