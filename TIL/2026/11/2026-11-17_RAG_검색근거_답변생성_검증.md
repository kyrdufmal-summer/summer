# TIL | RAG 검색 근거 검증과 답변 생성 단계 분리

- 학습일: 2026-11-17
- 분류: Python · RAG · 검색 품질 · LLM 응답 검증
- 공개 범위: 일반적인 기술 학습 원리와 독립적으로 구성한 가상 예시
- 작성·점검일: 2026-11-17 (Asia/Seoul)

## 1. 핵심 결론

RAG(Retrieval-Augmented Generation)에서는 **관련 문서를 찾아 출력하는 단계**와 **검색된 근거를 바탕으로 LLM이 최종 답변을 생성하는 단계**가 다르다. 검색 결과가 화면에 보인다는 이유만으로 AI 답변 생성까지 성공했다고 판단하면 안 된다.

오늘 확인 가능한 학습 기록에는 Python 파일의 문법 검사 명령과 문서 검색 CLI 실행 명령, 검색 근거가 출력된 사례가 있다. 다만 최종 생성형 AI 답변 및 실제 외부 API 호출 성공은 이 기록만으로 입증되지 않았다.

## 2. 왜 학습했는가?

문서 기반 질의응답을 만드는 과정에서, 프로그램이 검색한 근거를 출력했을 때 이를 완성된 AI 비서의 답변으로 오해하기 쉽다.

사용자가 알고 싶은 것은 단순히 '문서가 검색됐는가?'가 아니라 다음 질문이다.

1. 질문과 관련 있는 문서 조각을 찾았는가?
2. 찾은 조각이 실제 질문에 답할 수 있는 근거인가?
3. 근거가 없을 때 '모른다'고 답할 수 있는가?
4. 검색 단계 이후 LLM 답변 생성까지 실행됐는가?

이 질문들을 분리해야 디버깅과 검증이 가능하다.

## 3. 오늘 실제 확인된 작업

당일 대화에 제시된 터미널 기록에는 다음 종류의 명령이 있었다.

- `python -m py_compile <script>.py` 형식의 Python 문법 검사
- `python <script>.py "<질문>" --top-k 2` 형식의 문서 검색 CLI 실행
- 검색된 근거 조각을 문서 출처·섹션·점수와 함께 출력하는 결과
- 현재 실행이 **검색 근거만 보여주는 미리보기이며 실제 AI 답변 또는 API 호출이 아니라는 안내**

**증거 수준:** 대화에 제시된 명령·출력에 근거한 확인. 원본 파일·실행 환경·로그를 독립적으로 재실행한 것은 아니다. 개인정보나 내부 프로젝트를 식별할 수 있는 경로·파일명·문서 내용은 공개하지 않는다.

## 4. 정상적인 RAG 데이터 흐름

사용자 질문
→ 질문 전처리
→ 문서 검색(키워드 또는 벡터 검색)
→ 관련 청크 선택(top-k)
→ 출처·근거 확인
→ 프롬프트 구성
→ LLM 호출(선택적)
→ 근거 기반 답변 생성
→ 사용자에게 답변과 출처 표시

여기서 `top-k`는 검색 결과 중 상위 몇 개를 선택할지 정하는 값이다. `--top-k 2`는 상위 두 개의 결과를 요청한다는 의미다. **두 개가 검색됐다는 사실만으로 정확성이 보장되지는 않는다.**

## 5. 초보자를 위한 용어 설명

### 청크(Chunk)

긴 문서를 검색하기 쉽도록 나눈 작은 텍스트 조각이다. 교과서 전체를 매번 읽는 대신 관련 단락을 찾아보는 것과 비슷하다.

### 검색 점수(Score)

검색 결과의 관련성을 나타내는 값이다. 단, 점수의 계산 방법은 구현에 따라 다르므로, 점수 3이 점수 1보다 반드시 '세 배 정확하다'는 뜻은 아니다.

### 검색 미리보기(Preview)

LLM에 질문을 보내기 전 검색 근거만 표시하는 모드다. 문서 검색을 디버깅하고 불필요한 API 비용을 줄이는 데 유용하다.

### 근거 기반 답변(Grounded Answer)

검색된 문서에 있는 내용을 근거로 답하고, 근거가 없는 정보는 추측하지 않는 답변 방식이다.

## 6. 예시: 근거가 없는 질문을 처리하는 방법

아래는 오늘 확인된 문서의 원문이 아니라 새로 작성한 가상 사례다.

**가상 문서:** '실습 보고서는 금요일까지 제출한다. 질문은 게시판에 남긴다.'

- 질문 A: '보고서 제출일은?' → 문서에 답이 있으므로 '금요일'이라고 답할 수 있다.
- 질문 B: '보고서 만점은 몇 점?' → 문서에 점수 정보가 없으므로 '제공된 문서에서는 확인할 수 없다'고 답해야 한다.

LLM이 일반적인 학교 제도를 알고 있더라도 문서에 없는 점수를 지어내면 근거 기반 질의응답에 실패한 것이다.

## 7. 문제·원인·대응

| 문제 | 가능한 원인 | 권장 대응 | 검증 기준 |
|---|---|---|---|
| 검색 결과만 출력됨 | 검색 미리보기 단계만 구현·실행 | 생성 단계가 별도로 있는지 확인 | 실제 LLM 호출과 답변 출력 여부 |
| 관련 없는 청크 선택 | 검색 방식·청크 분할·질문 표현 문제 | 검색 쿼리와 청크 단위 조정 | 질문별 관련 청크 포함률 |
| 근거 없는 답변 생성 | 프롬프트·근거 검증 부족 | 근거 부재 시 답변 보류 | 문서에 없는 정보 추측률 |
| 같은 근거 반복 | 청크 중복 또는 높은 overlap | 중복 제거·검색 결과 다양화 | 중복 비율 |
| 검색 점수 과신 | 점수 의미를 잘못 해석 | 구현별 점수 정의 확인 | 사람이 평가한 정답 관련성 |

## 8. 검증 절차

아래는 다음 실습에서 사용할 **권장 절차**이며 오늘 모두 수행했다는 의미가 아니다.

1. Python 문법 검사에서 오류가 없는지 확인한다.
2. 정답이 명시된 문서 질문을 실행한다.
3. 검색된 청크가 실제 정답을 포함하는지 눈으로 확인한다.
4. 정답이 없는 질문을 추가해 근거 부재가 명확히 표시되는지 확인한다.
5. 검색 미리보기와 실제 LLM 생성 모드를 분리한다.
6. Live 실행 시 API 호출 여부와 비용을 확인한다.
7. 응답이 원문 근거와 일치하는지 점검한다.
8. 질문 유형별로 정답률, 근거 정확도, 무응답 적절성, 지연시간을 기록한다.

## 9. 실무에서 중요한 비정상 흐름

### 검색 결과는 있지만 답할 수 없는 경우

질문과 관련된 단어가 포함된 청크라도 답에 필요한 사실이 없을 수 있다. 이때는 검색 성공과 답변 가능을 구분해야 한다.

### 문서가 오래된 경우

검색된 근거가 오래된 정책이나 과거 공지라면 답변도 오래될 수 있다. 문서의 작성일과 유효기간을 관리해야 한다.

### API 호출이 실패한 경우

검색은 성공했지만 모델 호출이 타임아웃 또는 인증 오류로 실패할 수 있다. 사용자에게 검색 성공을 답변 생성 성공으로 표시해서는 안 된다.

### 문서에 민감정보가 있는 경우

검색 결과가 프롬프트나 로그로 전달될 수 있으므로 접근권한, 마스킹, 로그 보존정책을 먼저 검토해야 한다.

이 시나리오는 일반적인 설계 위험이며 오늘 발생한 사고라는 뜻이 아니다.

## 10. 장단점과 트레이드오프

| 선택 | 장점 | 단점 |
|---|---|---|
| 검색만 미리보기 | 빠른 디버깅·낮은 비용 | 최종 답변 품질은 검증 불가 |
| 작은 top-k | 프롬프트 짧음·비용 절감 | 필요한 근거 누락 가능 |
| 큰 top-k | 근거 확보 가능성 증가 | 잡음·비용·지연 증가 |
| 근거 없으면 답변 보류 | 환각 감소 | 일부 질문에 답하지 못함 |
| Live API 생성 | 실제 사용 흐름 검증 | 비용·오류·보안 위험 관리 필요 |

## 11. 확인 사실과 미검증 사항

**확인된 대화 기록:** Python 문법 검사 명령, 검색 CLI 명령, 두 개의 검색 근거 출력, 검색 미리보기 안내.

**추정하지 않은 사항:** 문법 검사 외 전체 테스트 통과, 검색 정확도 수치, 임베딩 모델 사용 여부, 벡터 DB 사용 여부, 외부 API 호출 성공, 최종 AI 답변 생성 완료.

**오늘의 결과:** 검색 근거를 확인하는 단계와 생성형 AI 응답 단계를 구분하는 학습 근거가 확보되었다. 독립적인 재실행과 성능 평가는 후속 과제다.

## 14. 최종 고찰

**'검색됐다'와 '답변했다'는 서로 다른 성공 조건이다.** 문서 검색, 근거 적합성, LLM 호출, 최종 답변을 단계별로 검증하면 장애 원인을 빠르게 좁힐 수 있다. 무엇보다 검색 결과에 없는 사실을 생성하지 않는 것이 문서 기반 AI의 신뢰성을 높이는 출발점이다.
