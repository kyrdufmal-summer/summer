# 2026-09-25 TIL — VOC 운영 관점과 서비스 장애 진단

## 오늘의 핵심

오늘은 VOC를 단순 고객문의가 아니라 제품·운영·개발 개선의 입력 데이터로 보는 관점을 학습했다.

고객의 증상을 수집한 뒤 분류하고, 원인을 분석하고, 담당자를 지정하고, 개발·정책 개선 후 실제 VOC가 감소했는지 검증하는 Closed Loop가 중요하다.

## VOC에서 놓치기 쉬운 것

고객이 직접 문의한 Explicit VOC뿐 아니라 문의 없이 이탈하거나 반복 재시도하는 Implicit VOC와 Silent Churn도 함께 봐야 한다.

단순 VOC 건수보다 전체 거래량 대비 VOC Rate가 중요하다. 또한 고객이 말한 증상과 실제 Root Cause를 별도 필드로 관리해야 한다.

금전 관련 VOC는 일반 불편과 분리하여 영향 고객 수, 영향 거래 수, 영향 금액, Severity를 함께 관리하는 것이 좋다.

상담사가 반복적으로 수동 처리하는 업무도 제품 개선 후보다. Manual Workaround가 많다는 것은 관리자 기능이나 사용자 기능의 자동화가 부족하다는 신호일 수 있다.

## VOC를 개발 요구사항으로 번역하기

예를 들어 고객이 "결제했는데 주문이 없어요"라고 말한다면, 개발 관점에서는 외부 결제 승인과 내부 주문 반영 사이의 불일치를 의심할 수 있다.

이때 필요한 것은 고객 문장을 그대로 Bug로 등록하는 것이 아니라 주문·결제 상태, 외부 거래 결과, 내부 처리 이력 등을 확인하여 Root Cause를 찾는 것이다.

이런 문제는 중간 상태 관리, 중복처리 방지, 재조회, 대사, 복구 기능, Audit Log 같은 개발 요구사항으로 이어질 수 있다.

## 결제 운영 관점

결제에서는 고객 화면의 상태, 내부 주문 상태, 결제 상태, 외부 결제사 상태, 정산 상태가 서로 다를 수 있다.

따라서 결제완료·취소·환불이라는 단순 상태만 보지 않고 승인, 취소, 부분취소, 환불 반영, 정산, 대사까지 거래 생명주기를 연결해서 보는 것이 중요하다.

특히 환불 처리가 완료되어도 고객의 금융기관 화면에 반영되는 시점에는 차이가 있을 수 있으므로 운영 안내 문구와 내부 상태를 구분해야 한다.

## 서버·네트워크 장애와 VOC

고객의 "사이트가 안 열려요"라는 한 문장도 여러 계층에서 원인이 발생할 수 있다.

~~~text
Browser
→ Network
→ IP / DHCP / 접근정책
→ DNS / Domain
→ HTTPS
→ Reverse Proxy
→ Application
→ PostgreSQL
→ OAuth / 외부 API
~~~

따라서 고객 증상만 보고 바로 Application 오류라고 단정하면 안 된다.

네트워크 연결과 주소 할당, Domain 이름해석, HTTPS 인증서, Reverse Proxy, Application Process, DB 연결, 외부 인증/API 순서로 범위를 좁히는 것이 좋다.

## Port와 운영 구조

Port는 한 서버에서 어떤 서비스와 통신할지 구분하는 논리적 접점이다.

대표적으로 HTTP 80, HTTPS 443, SSH/SFTP 22, PostgreSQL 5432 등이 있다.

운영환경에서는 사용자가 Application 내부 Port에 직접 접근하기보다 Reverse Proxy가 외부 HTTPS 요청을 받아 내부 Application으로 전달하는 구조를 많이 사용한다.

~~~text
Client
→ HTTPS
→ Reverse Proxy
→ Django / Application
→ PostgreSQL
~~~

## SSH / SFTP / FTP

SSH는 원격 서버 관리에 사용하며 로그 확인, 서비스 상태 확인, 배포와 운영 점검 등에 활용한다.

SFTP는 SSH 기반 파일전송이다. 전통적인 기본 FTP는 운영환경에서 보안 요구사항을 별도로 검토해야 한다.

파일 업로드 장애도 브라우저, HTTPS, Proxy 업로드 제한, Application 설정, File Storage, DB Metadata, 저장공간 상태처럼 여러 계층으로 나누어 진단할 수 있다.

## OAuth 운영 관점

소셜 로그인 실패는 단순 로그인 기능 오류가 아닐 수 있다.

Domain 변경, HTTPS 조건, Redirect 설정, Callback 처리, Session/Cookie, 사용자 권한 처리, 외부 Provider 상태 등을 함께 확인해야 한다.

따라서 Domain이나 HTTPS 구성을 변경할 때는 OAuth Redirect 설정도 배포 체크리스트에 포함하는 것이 좋다.

## Ubuntu 운영과 선제 모니터링

고객 문의가 들어온 뒤 장애를 발견하는 것보다 시스템 지표와 로그로 먼저 이상을 감지하는 것이 좋다.

Ubuntu 운영에서는 CPU, Memory, Disk, Network, Process, Web/Application 상태, PostgreSQL, File Storage, Error Log 등을 관찰한다.

특히 저장공간 부족은 로그 기록, DB, 파일업로드 등 여러 기능에 동시에 영향을 줄 수 있다.

## 신생회사가 놓치기 쉬운 VOC 누수

- 문의한 고객만 보고 Silent Churn을 놓친다.
- VOC를 건수로만 보고 거래량 대비 비율을 보지 않는다.
- 고객 증상과 Root Cause를 섞는다.
- 상담사의 반복 수동처리를 기록하지 않는다.
- 금전 VOC를 일반 문의와 같은 우선순위로 처리한다.
- 장애 Incident와 VOC가 분리된다.
- 배포 시점과 VOC 증가를 연결하지 않는다.
- 해결 후 VOC 감소 여부를 검증하지 않는다.
- 관리자 기능 부족으로 운영자가 위험한 수동 보정에 의존한다.
- 재시도 과정의 중복처리 위험을 놓친다.
- 정산 불일치를 늦게 발견한다.
- 기타 카테고리가 계속 쌓여도 Taxonomy를 개선하지 않는다.

## Closed Loop

~~~text
VOC
→ Issue
→ Root Cause
→ Owner
→ 개선 Action
→ 개발/정책 변경
→ Deploy
→ VOC 변화 측정
→ 재발방지
~~~

VOC 관리의 목적은 상담을 빨리 끝내는 것만이 아니라 반복되는 문의가 생기는 구조 자체를 개선하는 것이다.

## 개발 전에 던질 질문

새 기능을 만들 때 정상 Flow뿐 아니라 단계별 실패 Flow를 먼저 생각한다.

실패했을 때 고객에게 무엇이 보이는지, 운영자가 원인을 찾을 수 있는지, 안전하게 복구할 수 있는지, 금전·데이터 중복이 발생하지 않는지, 배포 후 개선 효과를 측정할 수 있는지를 함께 확인한다.

## 오늘의 결론

~~~text
고객 경험
→ VOC
→ 운영
→ 정책
→ 데이터
→ 개발
→ 인프라
→ 모니터링
→ 재발 방지
~~~

코드를 잘 작성하는 것만으로 운영 가능한 서비스가 완성되지는 않는다. 고객 문제를 데이터와 시스템 구조로 번역하고, 반복 문제를 제품과 운영 구조에서 제거하는 능력이 중요하다.

## 보안 기록 원칙

공개 저장소에는 인증정보, 비밀키, 비밀번호, 실제 환경설정 값, 실제 서버 접속정보를 기록하지 않는다. 필요한 경우 값은 `***`로 마스킹하고 구조와 원리만 기록한다.
