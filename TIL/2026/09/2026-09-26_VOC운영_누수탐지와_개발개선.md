# VOC 운영: 누수 탐지에서 개발 개선까지

## 오늘 한 일

오늘은 VOC를 단순 고객문의 기록이 아니라 **서비스 운영 문제를 발견하고 제품·정책·개발 개선으로 연결하는 시스템**으로 정리했다.

핵심은 다음과 같다.

> VOC는 고객의 불만을 모으는 일이 아니라, 회사가 스스로 보지 못하는 문제를 발견하고 재발을 막는 운영 센서다.

---

## 1. VOC Closed Loop

좋은 VOC 운영은 다음 흐름을 가진다.

~~~text
고객 경험
→ VOC / 행동 데이터 수집
→ 분류
→ Root Cause 분석
→ Owner 지정
→ 제품 / 정책 / 개발 개선
→ 배포
→ VOC 변화 측정
→ 재발방지
~~~

보고서 작성으로 끝내지 않고, 누가 무엇을 고치고 개선 후 효과가 있었는지까지 추적해야 한다.

---

## 2. Explicit VOC와 Implicit VOC

**Explicit VOC**는 전화, 채팅, 이메일, 설문, 리뷰처럼 고객이 직접 표현한 데이터다.

**Implicit VOC**는 고객이 말하지 않았지만 행동으로 드러나는 문제다.

- 결제 실패 후 이탈
- 반복 클릭과 재시도
- 특정 화면에서 이탈
- 오류 후 재방문 없음
- 환불 후 재구매 없음

특히 Silent Churn은 상담 데이터만으로 잡히지 않는다. 따라서 VOC는 상담 기록과 서비스 행동 데이터를 함께 봐야 한다.

---

## 3. 신생회사가 놓치기 쉬운 VOC 누수

### 문의한 고객만 보는 문제

실제 영향 고객이 많아도 문의 고객은 일부일 수 있다. VOC 건수와 함께 Affected Users, 실패율, 재시도율, 이탈률, 전환율 변화를 확인해야 한다.

### VOC Count보다 VOC Rate

서비스 규모가 변하면 단순 건수 비교가 왜곡된다.

~~~text
VOC Rate = VOC 건수 / 거래건수 또는 활성사용자수
~~~

결제 VOC/결제시도건수, 환불 VOC/환불건수처럼 분모를 함께 관리한다.

### 고객 증상과 Root Cause 혼동

"고객: 결제가 안 돼요"는 증상이다. 실제 원인은 인증 실패, 카드사 거절, 외부 결제사 응답 지연, 네트워크 오류, 내부 서버 장애, 중복 요청 차단 등일 수 있다.

VOC 데이터에는 customer_symptom, normalized_issue, root_cause, resolution을 분리하는 것이 좋다.

---

## 4. VOC를 개발 요구사항으로 번역하기

예:

~~~text
VOC
"결제는 된 것 같은데 주문이 보이지 않아요."

→ 결제 승인 성공 가능성
→ 주문 반영 실패 가능성
→ 외부 거래 재조회 필요
→ 내부 상태 불일치 확인
→ 중복 처리 방지
→ Reconciliation
→ 운영자 복구 기능
~~~

이렇게 VOC를 Root Cause와 시스템 요구사항으로 번역해야 한다.

---

## 5. 금전 VOC

금전 관련 VOC는 일반 불편과 동일한 한 건으로 취급하면 안 된다.

함께 볼 값:

- Financial Impact
- Affected Amount
- Affected Users
- Severity

결제·환불·정산 문제는 건수뿐 아니라 영향 금액도 중요하다.

---

## 6. Preventable VOC와 Manual Workaround

반복적으로 제거 가능한 VOC를 별도로 본다.

상담사가 관리자 화면에서 매번 같은 수동처리를 하고 있다면 고객 문제는 해결돼도 제품 문제는 숨어 있을 수 있다.

따라서 **Manual Workaround Count**도 중요한 운영 지표다. 운영자가 자주 수행하는 수동작업은 자동화 또는 제품 개선 후보가 된다.

---

## 7. 재문의와 해결 품질

빠르게 상담을 종료하는 것만으로 해결 품질을 판단하면 안 된다.

- First Contact Resolution
- Repeat Contact Rate

재문의 원인도 같은 문제 미해결, 처리 지연, 안내 부족, 정책 불만, 새로운 문제로 나누어 본다.

---

## 8. VOC Priority

단순 건수 순으로 개발 우선순위를 정하지 않는다.

~~~text
Priority
= Frequency
× Customer Impact
× Financial Impact
× Churn Risk
× Strategic Importance
~~~

낮은 빈도라도 금전·개인정보·대규모 장애와 관련되면 높은 우선순위가 될 수 있다.

---

## 9. VOC Spike, Incident, Release

평상시보다 특정 VOC가 급증하면 장애 신호일 수 있다.

~~~text
VOC Spike
→ Incident 후보
→ 서비스 Metric 확인
→ 로그 확인
→ Root Cause
~~~

배포 직후 특정 VOC가 증가했다면 Release Regression 가능성도 확인한다.

VOC와 incident_id, release_version, affected_users, financial_impact를 연결하면 원인 추적이 빨라진다.

---

## 10. 서버·네트워크 장애를 VOC에서 해석하기

고객에게는 모두 "사이트가 안 열려요"로 보일 수 있지만 기술적으로는 여러 Layer가 있다.

~~~text
Browser
→ Network
→ IP / DHCP
→ VLAN / ACL / Firewall
→ DNS / Domain
→ HTTPS / TLS
→ Reverse Proxy
→ Application Server
→ PostgreSQL
→ OAuth / 외부 API
~~~

따라서 고객 증상과 장애 Layer를 분리해 진단해야 한다.

### 네트워크 관점

연결 환경이 바뀐 뒤 접속이 되지 않는다면 DHCP, AP/VLAN, ACL, DNS Cache, Gateway, Firewall, 서버 주소 변경, 서비스 Port 등을 순서대로 확인한다.

### Domain / HTTPS 관점

~~~text
Domain
→ DNS Resolution
→ Server Address
→ HTTPS
→ TLS Certificate
→ Reverse Proxy
→ Application
~~~

웹페이지가 열리지 않는다고 곧바로 애플리케이션 오류로 판단하면 안 된다.

## 11. Port, SSH, SFTP, FTP

하나의 서버에서도 서비스마다 통신 목적과 Port가 다르다.

- HTTPS: 웹서비스 진입
- Application Port: 내부 웹 애플리케이션
- DB Port: PostgreSQL
- SSH: 서버 원격 관리
- SFTP: SSH 기반 파일 전송
- FTP: 별도 파일 전송 프로토콜

운영에서는 외부에 공개해야 하는 통신과 내부에서만 사용할 통신을 분리해야 한다.

SSH/SFTP 운영 시 최소 권한, 접근 범위 제한, 인증 정책, 로그인 로그, 파일 권한, 업로드 경로, Audit를 확인한다.

실제 Host, 계정, 비밀번호, Key, 접속주소는 공개 TIL에 기록하지 않고 모두 마스킹한다.

~~~text
SERVER_HOST=***
SERVER_USER=***
SECRET=***
~~~

## 12. Ubuntu 운영과 VOC

서비스 장애를 고객이 먼저 알려주기 전에 서버가 먼저 감지하는 구조가 필요하다.

확인 항목:

- Application Process
- Reverse Proxy
- CPU / Memory / Disk
- DB Connection
- Error Log
- Disk Usage
- TLS 인증서 만료
- Backup 상태
- 재부팅 후 자동기동
- Queue 적체
- Batch 실패

목표는 "고객 VOC → 장애 발견"이 아니라 "Monitoring Alert → 운영 대응 → 고객 영향 최소화"다.

---

## 13. OAuth VOC

소셜 로그인 실패도 하나의 FAILED 상태로만 보면 원인을 찾기 어렵다.

가능한 원인:

- Redirect URI 불일치
- Domain 변경
- HTTPS 요구조건
- Provider 정책
- Callback 처리 실패
- Session / Token 문제

failure_stage와 provider_error를 구분해 기록하면 운영 분석이 쉬워진다.

민감한 설정은 문서에서 다음처럼 마스킹한다.

~~~text
OAUTH_CLIENT_ID=***
OAUTH_CLIENT_SECRET=***
CALLBACK_URL=***
~~~

---

## 14. DB 운영과 VOC

DB 문제는 사용자에게 조회 실패, 저장 실패, 중복 저장, 상태 불일치, 느린 응답 등으로 보일 수 있다.

운영에서는 다음 추적성이 중요하다.

~~~text
VOC 발생시각
→ Request ID
→ Application Log
→ DB Query / Transaction
→ External API
→ 최종 상태
~~~

고객 문의 하나를 실제 Transaction까지 추적할 수 있어야 Root Cause 분석이 가능하다.

## 15. 역할별 VOC Dashboard

**경영:** Top VOC, VOC Rate, Revenue Impact, Churn Risk

**운영:** Open VOC, SLA, Severity, Escalation, Repeat Contact, Manual Workaround

**개발:** Root Cause, Error Code, Affected API, Incident, Release Version, Retry/Queue

**재무:** Financial Impact, Refund, Settlement, Mismatch

같은 데이터를 조직별 목적에 맞게 보여주는 것이 중요하다.
