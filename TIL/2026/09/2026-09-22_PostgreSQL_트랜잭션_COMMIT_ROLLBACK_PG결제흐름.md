# TIL - 2026-09-22

## 오늘 한 일

오늘은 PostgreSQL 트랜잭션을 단순한 SQL 문법이 아니라, 실제 서비스에서 자주 발생하는 **결제(PG) 실패 상황**과 연결해서 이해했다.

실습에서는 학생 102가 강의 302를 신청하는 상황을 가정하고, DB에서는 수강 신청 데이터를 먼저 변경한 뒤 외부 PG 결제 승인이 실패했다고 가정하여 `ROLLBACK`으로 변경을 취소하는 흐름을 확인했다.

핵심은 다음 한 문장으로 정리할 수 있다.

> **트랜잭션은 DB 내부 변경을 하나의 작업 단위로 묶고, 모든 조건이 성공했을 때만 COMMIT하여 확정하는 장치다.**

---

## 1. 트랜잭션을 왜 사용하는가

여러 SQL이 하나의 업무를 구성할 때 중간에 일부만 반영되면 데이터가 이상한 상태로 남을 수 있다.

예를 들어 수강 신청 업무를 생각하면 다음과 같은 작업이 연결될 수 있다.

```text
학생이 강의 신청
↓
수강 인원 증가
↓
신청 내역 생성
↓
결제 승인
↓
최종 확정
```

이 과정에서 결제가 실패했는데 DB에는 이미 수강 신청이 남아 있다면 실제 업무 상태와 데이터가 서로 달라진다.

그래서 관련 변경을 트랜잭션으로 묶는다.

```sql
BEGIN;

-- 수강 신청 데이터 변경
-- 수강 인원 변경
-- 기타 관련 작업

COMMIT;
```

모든 처리가 정상일 때만 `COMMIT`하여 확정하고, 문제가 생기면 `ROLLBACK`하여 트랜잭션 시작 전 상태로 되돌린다.

---

## 2. COMMIT 전과 후의 차이

오늘 가장 중요하게 구분한 부분이다.

### COMMIT 전

트랜잭션 안에서 실행한 변경은 **아직 최종 확정되지 않은 임시 상태**이다.

```text
BEGIN
↓
UPDATE / INSERT
↓
현재 세션에서는 변경된 값이 보임
↓
아직 확정되지 않음
```

따라서 이 시점에는 두 가지 선택이 가능하다.

```text
정상 → COMMIT
실패 → ROLLBACK
```

### COMMIT 후

`COMMIT`을 실행하면 변경 내용이 DB에 최종 반영된다.

```text
BEGIN
↓
변경
↓
COMMIT
↓
변경 확정
```

COMMIT 이후에는 같은 트랜잭션의 `ROLLBACK`으로 이전 상태로 되돌릴 수 없다.

### 내가 이해한 핵심

```text
COMMIT 전 = 아직 되돌릴 수 있는 상태
COMMIT 후 = DB에 최종 확정된 상태
```

즉 `COMMIT`은 단순히 SQL을 끝내는 명령이 아니라,

> **“이 변경을 실제 데이터로 확정하겠다”**

라는 의미이다.

---

## 3. ROLLBACK의 의미

`ROLLBACK`은 현재 트랜잭션에서 실행한 변경을 취소하고 `BEGIN` 이전 상태로 되돌리는 명령이다.

오늘 실습에서는 다음 상황을 가정했다.

```text
학생 102
↓
강의 302 신청
↓
DB에서는 신청 상태 임시 변경
↓
외부 PG 결제 승인 요청
↓
결제 실패
↓
ROLLBACK
↓
수강 신청 전 상태 복구
```

SQL의 개념으로 표현하면 다음과 같다.

```sql
BEGIN;

-- 학생 102가 강의 302를 신청한 상태를 임시 반영

-- 외부 결제 실패를 가정

ROLLBACK;
```

ROLLBACK 이후 다시 조회하면 트랜잭션 안에서 잠시 보였던 변경이 사라지고 원래 값으로 돌아간다.

### 배운 점

ROLLBACK은 단순히 “실수했으니 취소”하는 기능이 아니다.

실제 서비스에서는

- 결제 실패
- 재고 부족
- 다른 테이블 처리 실패
- 서버 내부 오류
- 업무 조건 불충족

등이 발생했을 때 **데이터 일관성을 지키기 위해 의도적으로 사용**된다.

---

## 4. PG사와 트랜잭션을 연결해서 이해하기

PG사는 온라인 결제 과정에서 가맹점과 카드사·은행 등의 결제수단 사이에서 결제 승인을 중계하는 역할을 한다.

서비스 입장에서 보면 결제 업무는 대략 다음 흐름으로 이해할 수 있다.

```text
사용자
↓
우리 웹서비스
↓
주문 / 신청 정보 생성
↓
PG사 결제 요청
↓
카드사·은행 승인
↓
결제 결과 반환
↓
우리 서비스의 DB 상태 확정
```

여기서 중요한 것은 **PostgreSQL 트랜잭션과 PG 결제가 같은 시스템이 아니라는 점**이다.

PostgreSQL의

```sql
BEGIN;
COMMIT;
ROLLBACK;
```

은 기본적으로 **우리 DB 내부 변경**을 제어한다.

반면 PG 승인/취소는 외부 결제 시스템에서 처리된다.

즉,

```text
DB Transaction
≠
PG Transaction
```

이다.

---

## 5. 왜 교수님이 DB 변경과 결제를 따로 설명했는지

처음에는

> “어차피 하나의 신청인데 왜 따로 하는 거지?”

라는 의문이 있었다.

하지만 실제 시스템에서는 다음 두 작업이 서로 다른 시스템에서 일어난다.

### 우리 DB에서 하는 일

```text
수강 신청
주문 상태
결제 상태
수강 인원
사용자 기록
```

### PG사에서 하는 일

```text
결제 승인
결제 실패
승인번호 생성
결제 취소 / 환불
```

따라서 DB의 SQL 트랜잭션 하나로 PG사까지 함께 ROLLBACK 할 수 없다.

예를 들어

```text
DB 변경 성공
↓
PG 결제 실패
```

라면 우리 DB는 `ROLLBACK`해서 신청 변경을 취소할 수 있다.

반대로

```text
PG 결제 승인 성공
↓
DB 저장 실패
```

라면 문제가 더 복잡해진다.

이미 외부 PG에서는 돈이 승인됐기 때문에 단순한 PostgreSQL `ROLLBACK`만으로 결제를 취소할 수 없다.

이 경우에는 별도로 **PG 결제 취소 API**를 호출해야 한다.

---

## 6. 실제 서비스에서 발생할 수 있는 문제

### 상황 1. DB 변경 후 PG 결제 실패

```text
BEGIN
↓
신청 정보 임시 변경
↓
PG 결제 요청
↓
결제 실패
↓
ROLLBACK
```

이 경우에는 DB 변경을 취소하면 된다.

---

### 상황 2. PG 결제 성공 후 DB 저장 실패

```text
PG 결제 성공
↓
DB 저장 시도
↓
DB 오류
```

이 경우는 단순 ROLLBACK만으로 해결되지 않는다.

PG에는 이미 결제가 승인되었기 때문에

```text
PG 결제 취소 API 호출
+
DB 상태 정리
```

가 필요하다.

### 배운 점

실제 서비스에서는 **DB 트랜잭션만 잘 사용한다고 전체 업무가 완벽하게 원자적으로 처리되는 것은 아니다.**

DB와 외부 서비스 사이의 실패 상황도 함께 설계해야 한다.

## 7. transaction_lab 테이블을 따로 만든 이유

오늘 실습 중 내가 사용하던 DB에는 교수님 화면에 있던 `transaction_lab` 테이블이 없어서 왜 없는지 확인했다.

이 테이블은 PostgreSQL에서 자동으로 생기는 시스템 테이블이 아니라, **트랜잭션 실습을 위해 별도로 만든 연습용 테이블**이다.

즉,

```text
PostgreSQL 설치
→ transaction_lab 자동 생성
```

이 아니라

```text
교수님 실습 환경
→ 실습용 transaction_lab 생성
→ COMMIT / ROLLBACK 비교
```

의 구조다.

### 배운 점

교수님 화면에 보이는 테이블이 내 DB에 없다고 해서 DB 설치가 잘못된 것은 아니다.

먼저 확인해야 할 것은

- 해당 테이블이 실습용인지
- CREATE TABLE 단계가 앞에 있었는지
- 현재 Schema가 같은지
- 현재 Database가 같은지

이다.

## 8. COMMIT과 ROLLBACK 비교 정리

| 구분 | COMMIT | ROLLBACK |
|---|---|---|
| 의미 | 변경 확정 | 변경 취소 |
| DB 상태 | 변경된 값 유지 | BEGIN 이전으로 복구 |
| 사용 시점 | 업무 정상 완료 | 오류·실패 발생 |
| 이후 취소 | 같은 트랜잭션에서 불가 | 변경 자체가 취소됨 |
| 실제 예 | 결제·신청 모두 성공 | 결제 실패로 신청 취소 |

핵심 흐름은 다음과 같다.

```text
BEGIN
  ↓
INSERT / UPDATE / DELETE
  ↓
업무 결과 확인
  ├─ 성공 → COMMIT
  └─ 실패 → ROLLBACK
```

## 9. 실제 서비스 관점에서 다시 연결

오늘 배운 내용을 수강 신청 서비스에 그대로 연결하면 다음과 같다.

```text
[사용자]
강의 신청 버튼 클릭
      ↓
[Django / Flask]
신청 요청 수신
      ↓
[PostgreSQL]
BEGIN
      ↓
신청 데이터 임시 처리
      ↓
[PG사]
결제 승인 요청
      ↓
┌───────────────┐
│ 승인 성공     │ 승인 실패
↓               ↓
DB 최종 처리    ROLLBACK
↓
COMMIT
```

하지만 운영환경에서는 PG 승인 성공 이후 DB 실패 가능성도 있으므로 별도의 실패 복구 설계가 필요하다.

따라서 실제 결제 시스템은 단순히

```text
BEGIN → 결제 → COMMIT
```

만으로 끝나는 것이 아니다.

## 10. 트랜잭션을 공부하며 바뀐 이해

처음에는 트랜잭션을

> “COMMIT 아니면 ROLLBACK 하는 SQL 기능”

정도로 생각했다.

오늘 PG 결제 상황과 연결해서 보니 트랜잭션의 목적은 문법 자체가 아니라 **업무 데이터의 일관성을 지키는 것**이라는 점이 더 중요했다.

```text
SQL 문법
        ↓
트랜잭션
        ↓
업무 단위 관리
        ↓
실패 시 복구
        ↓
데이터 일관성 유지
```

그리고 외부 API가 개입하면

```text
DB 일관성
+
외부 시스템 상태
```

를 함께 고려해야 한다.

---

## 11. 오늘의 핵심 정리

### COMMIT

> 지금까지의 DB 변경을 정상 처리된 결과로 확정한다.

### ROLLBACK

> 현재 트랜잭션에서 발생한 DB 변경을 취소하고 이전 상태로 되돌린다.

### PG 결제와의 관계

> PostgreSQL 트랜잭션은 우리 DB를 제어하고, PG 결제는 외부 시스템에서 처리되므로 둘의 실패 상태를 연결하는 별도의 애플리케이션 로직이 필요하다.

---

## 오늘의 한 줄 정리

> **트랜잭션은 단순한 COMMIT/ROLLBACK 문법이 아니라, 결제처럼 여러 단계로 이루어진 업무에서 실패가 발생해도 데이터가 어긋나지 않도록 지키는 안전장치다.**
