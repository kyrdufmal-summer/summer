# 2026-09-24 TIL — VOC 운영, 결제 도메인, 누수 탐지와 개발 개선

## 1. 오늘의 핵심

오늘은 기능을 구현하는 개발 관점에서 한 단계 더 나아가, **VOC를 회사의 운영·제품·개발 개선으로 연결하는 방법**을 정리했다.

핵심은 고객 문의를 단순히 상담 건수로 관리하는 것이 아니라 다음 흐름으로 연결하는 것이다.

```text
고객 불편
→ VOC
→ 증상 분류
→ Root Cause 분석
→ 고객 영향/금액 영향 파악
→ 제품·정책·시스템 개선
→ 배포
→ VOC 감소 여부 확인
→ 재발 방지
```

좋은 VOC 운영의 목적은 문의를 빨리 닫는 것이 아니라 **반복적으로 문의가 발생하는 구조 자체를 찾아 없애는 것**이다.

---

## 2. VOC는 고객 문의함이 아니라 회사의 센서다

VOC에는 고객이 직접 말한 내용뿐 아니라 행동으로 드러나는 문제도 포함해야 한다.

### Explicit VOC

- 전화
- 채팅
- 이메일
- 리뷰
- 설문
- 게시판

### Implicit VOC

- 결제 실패 후 이탈
- 같은 버튼 반복 클릭
- 여러 번 재시도
- 환불 후 탈퇴
- 오류 발생 후 재방문 없음
- 특정 단계에서 비정상적으로 높은 이탈률

특히 **Silent Churn**은 고객센터에 문의하지 않고 그냥 떠나는 고객이므로 상담 데이터만으로는 발견하기 어렵다.

따라서 VOC 건수만 보지 말고 서비스 행동 데이터와 함께 봐야 한다.

---

## 3. 신생회사가 놓치기 쉬운 VOC 누수

### 3.1 문의한 사람만 고객 문제라고 생각하는 오류

실제 장애 고객이 1,000명이어도 문의는 일부만 할 수 있다.

```text
실제 영향 고객 1,000명
├─ 고객센터 문의 20명
├─ 재시도 400명
├─ 그냥 포기 280명
└─ 서비스 이탈 300명
```

따라서 다음을 함께 봐야 한다.

- VOC Count
- Affected Users
- Failure Rate
- Retry Rate
- Drop-off Rate
- Churn
- Financial Impact

### 3.2 VOC 절대 건수만 보는 오류

서비스 규모가 커지면 VOC도 자연스럽게 늘 수 있다.

따라서 다음과 같은 비율 지표가 필요하다.

```text
VOC Rate = VOC 건수 / 거래건수 또는 활성사용자수
```

결제라면 다음처럼 세분화할 수 있다.

```text
결제 VOC / 결제 시도 건수
환불 VOC / 환불 처리 건수
배송 VOC / 배송 건수
```

### 3.3 상담사가 잘 처리해서 제품 문제가 가려지는 경우

상담사가 관리자 화면에서 매일 수동으로 주문 상태를 보정하거나 포인트를 복구하고 있다면 고객 문의는 해결되더라도 제품 문제는 남는다.

따라서 **Manual Workaround Count**도 제품 개선 지표로 봐야 한다.

운영자가 자주 누르는 관리자 버튼은 향후 자동화 또는 제품 요구사항 후보가 될 수 있다.

## 4. VOC Taxonomy는 처음부터 계층형으로 설계한다

`결제 / 배송 / 회원 / 기타` 정도의 분류만 사용하면 나중에 Root Cause를 찾기 어렵다.

예를 들어 결제 VOC는 다음처럼 계층화할 수 있다.

```text
Domain       : 결제
Journey      : 결제 시도
Issue Type   : 결제 실패
Failure Type : 카드 승인 실패
Root Cause   : 인증 실패 / 카드사 거절 / PG Timeout / 내부 서버 오류
```

또는 다음처럼 트리 형태로 관리할 수 있다.

```text
결제
└─ 승인
   ├─ 사용자 취소
   ├─ 카드사 거절
   ├─ 인증 실패
   ├─ Timeout
   └─ PG 장애
```

고객이 말한 **증상(Customer Symptom)**과 기술적으로 확인된 **Root Cause**는 반드시 구분한다.

## 5. 고객 언어를 개발 언어로 번역하기

고객 VOC:

> 돈은 빠져나갔는데 주문이 없어요.

운영 관점:

```text
결제 승인 여부 확인 필요
주문 생성 여부 확인 필요
```

개발 관점:

```text
PG 승인 성공
+
내부 주문 DB 저장 실패 가능성
```

필요한 시스템 기능:

- UNKNOWN 상태
- PG Transaction 조회
- Idempotency
- Reconciliation
- 주문 복구
- 운영자 재처리

즉 VOC 한 건이 새로운 개발 요구사항의 출발점이 될 수 있다.

## 6. 금전 VOC는 일반 VOC와 별도 관리한다

`버튼이 불편하다`와 `이중결제가 발생했다`는 같은 1건으로 취급하면 안 된다.

금전 VOC에는 최소 다음 항목을 별도로 관리하는 것이 좋다.

```text
Financial Impact
Affected Amount
Affected Customer Count
Payment Status
Refund Status
Settlement Status
```

예를 들어 VOC가 2건뿐이어도 영향을 받은 금액이 매우 크다면 최우선 장애가 될 수 있다.

따라서 우선순위를 단순 건수가 아니라 다음처럼 생각할 수 있다.

```text
Priority
= Frequency
× Customer Impact
× Financial Impact
× Churn Risk
× Strategic Importance
```

## 7. 결제 VOC를 볼 때 확인해야 할 전체 Lifecycle

결제 완료 하나만 보면 안 된다.

```text
주문
→ 결제 인증
→ 승인
→ 매입
→ 취소/부분취소
→ 환불
→ 정산
→ 대사
→ 분쟁/Chargeback
```

운영자가 보는 상태와 실제 금융 거래의 상태가 다를 수 있기 때문에 각 단계의 식별자와 시각을 추적할 수 있어야 한다.

대표적으로 다음을 구분한다.

- order_id
- 내부 payment_id
- PG 거래키
- 승인번호
- 원거래번호
- 취소 거래키
- 정산 reference

실제 값이나 접속정보는 공개 문서에 기록하지 않고 모두 `***` 처리한다.

---

## 8. 환불 VOC에서 특히 발생하는 시간차 문제

고객이 가장 이해하기 어려워하는 부분 중 하나가 다음이다.

```text
서비스 화면: 환불 완료
카드 앱: 아직 취소 반영 안 됨
```

이는 내부 취소 요청 성공과 금융기관 최종 반영 시점이 다를 수 있기 때문이다.

따라서 시스템은 가능하면 다음 상태를 구분해야 한다.

```text
REFUND_REQUESTED
REFUND_PROCESSING
REFUND_COMPLETED
REFUND_FAILED
```

그리고 고객 안내 문구 역시 시스템 내부 상태와 일치해야 한다.

`환불 완료`라고 너무 일찍 표시하면 불필요한 VOC가 발생할 수 있다.

## 9. Refund와 Chargeback을 구분한다

### Refund

가맹점이 고객 요청이나 정책에 따라 정상적으로 취소·환불하는 프로세스다.

### Chargeback / Dispute

고객이 카드사 등에 거래 이의를 제기하는 분쟁 프로세스다.

Chargeback 대응에는 다음 데이터가 필요할 수 있다.

- 주문 증빙
- 배송 증빙
- 서비스 사용 기록
- 고객 동의 기록
- 상담 이력
- 환불 정책 고지
- 결제 및 인증 로그

따라서 Chargeback은 개발팀만의 문제가 아니라 운영·CS·재무·법무·보안 데이터가 연결되는 영역이다.

---

## 10. FDS와 Fraud 관점

반복적인 결제 실패나 환불은 단순 VOC가 아니라 Fraud Signal일 수도 있다.

예를 들어 다음 패턴을 탐지할 수 있다.

- 동일 카드 반복 결제
- 여러 카드로 동일 계정 반복 시도
- 짧은 시간의 고액 결제 급증
- 동일 Device에서 다수 계정 결제
- 승인 실패 반복
- 비정상적인 환불률
- 평소와 다른 국가/지역의 거래

운영에서는 고객 불편과 보안 리스크를 동시에 봐야 한다.

## 11. VOC와 Incident를 연결한다

장애가 발생하면 기술 장애 기록과 고객 VOC가 분리되어서는 안 된다.

```text
Incident
├─ Root Cause
├─ 발생 시각
├─ 복구 시각
├─ Affected Users
├─ VOC Count
├─ Financial Impact
└─ Remediation
```

예를 들어 배포 직후 결제 실패 VOC가 급증했다면 다음 관계를 확인해야 한다.

```text
배포
→ Error Rate 상승
→ 결제 실패 상승
→ VOC Spike
```

따라서 release_version, deployment_id, incident_id와 VOC를 연결하면 원인 분석 속도가 크게 좋아진다.

---

## 12. VOC Spike를 장애 신호로 사용한다

평소 결제 실패 VOC가 시간당 3건인데 갑자기 30건으로 증가했다면 장애 가능성이 있다.

```text
VOC 발생량
> 평상시 Baseline × 임계치
→ Alert
```

VOC 자체가 Observability Signal이 되는 것이다.

다만 고객 문의는 실제 장애보다 늦게 들어올 수 있으므로 Application Metric, Error Log, Transaction Failure Rate와 함께 봐야 한다.

## 13. Closed Loop가 없는 VOC 운영은 불완전하다

다음 구조로 끝나면 안 된다.

```text
VOC 수집
→ 보고서
→ 회의
→ 종료
```

다음까지 연결되어야 한다.

```text
VOC
→ Issue 생성
→ Owner 지정
→ Severity
→ Due Date
→ Fix
→ Deploy
→ VOC 변화 측정
→ Close
```

특히 Owner가 없는 VOC 개선안은 회의 후 사라질 가능성이 높다.

---

## 14. Preventable VOC를 찾아야 한다

모든 VOC를 제거할 수 있는 것은 아니다.

따라서 다음을 구분한다.

```text
Preventable VOC
Unpreventable VOC
```

예를 들어 입력 UI가 불명확해서 반복 문의가 발생한다면 Preventable VOC다.

상담 처리 속도를 높이는 것보다 해당 문의가 다시 발생하지 않게 제품을 개선하는 것이 회사 전체 비용을 줄일 수 있다.

---

## 15. Cost of Failure 관점

VOC는 상담 비용만 발생시키지 않는다.

```text
고객 문의
→ 상담사 처리
→ 운영자 확인
→ PG 조회
→ 개발자 로그 확인
→ 재무 확인
→ 환불/보정
```

하나의 장애가 여러 조직의 시간을 사용한다.

따라서 반복 VOC는 **Product Debt이자 Operational Cost**로 볼 수 있다.

개발 개선 비용과 반복 처리 비용을 비교하면 자동화의 ROI를 판단할 수 있다.

## 16. 운영자가 필요한 관리자 화면

결제 관련 VOC를 제대로 처리하려면 관리자 화면에서 최소 다음을 한 번에 연결해서 조회할 수 있어야 한다.

```text
고객
→ 주문
→ 결제
→ 승인
→ 취소/환불
→ Webhook
→ Retry
→ 정산
→ Incident
→ VOC
```

필요 기능 예시:

- 주문번호 조회
- PG 거래 상태 재조회
- 승인/취소 이력
- 부분취소 누적금액
- Webhook 수신 이력
- Retry 이력
- 실패 코드
- 정산 상태
- Audit Log
- 수동 재처리 권한

수동 재처리 기능은 반드시 권한과 감사로그를 남겨야 한다.

## 17. 서버·네트워크 장애도 VOC Journey로 본다

웹서비스 접속 장애는 다음 계층으로 나누어 진단할 수 있다.

```text
사용자 Browser
↓
Wi-Fi / 내부 Network
↓
IP / DHCP / VLAN / ACL
↓
DNS / Domain
↓
HTTPS / TLS
↓
Reverse Proxy
↓
Application Server
↓
Database
↓
외부 API / OAuth / PG
```

고객에게는 모두 `사이트가 안 열려요`라는 하나의 VOC로 보일 수 있지만 Root Cause는 전혀 다르다.

따라서 운영자는 계층별로 장애를 분리해서 확인해야 한다.

## 18. Ubuntu 서버 운영에서 VOC와 연결되는 확인 항목

Ubuntu 기반 웹서비스를 운영할 때는 다음을 확인한다.

### Network

- IP 할당 상태
- DHCP 예약 여부
- Gateway
- DNS
- 방화벽
- 내부 접근 정책

실제 IP와 접속정보는 문서에 기록할 경우 `***`로 마스킹한다.

### Web Server / Reverse Proxy

```text
Browser
→ HTTPS 443
→ Reverse Proxy
→ Application
```

확인 항목:

- 서비스 프로세스 실행 여부
- Reverse Proxy 설정
- TLS 인증서
- 80 → 443 Redirect
- Application upstream 연결

### Database

```text
Application
→ PostgreSQL
```

확인 항목:

- DB 프로세스
- Connection
- Migration
- Connection Pool
- Backup / Restore
- DB 접근권한

DB 포트를 외부에 무조건 공개해서는 안 된다.

## 19. SSH / SFTP / FTP 운영 관점

### SSH

서버 원격 관리에 사용한다.

```text
관리자 PC
→ SSH
→ Ubuntu Server
```

### SFTP

SSH 기반 파일전송 방식이다.

```text
관리자 PC
→ SSH 인증
→ SFTP
→ Server File System
```

### FTP

별도 FTP 프로토콜이다.

운영 환경에서는 인증정보와 전송구간 보안을 고려해야 하며, 가능한 경우 암호화된 전송방식을 우선 검토한다.

접속 계정, 비밀번호, Private Key, 실제 Host/IP는 공개 TIL에 남기지 않는다.

```text
HOST=***
USER=***
PASSWORD=***
PRIVATE_KEY=***
```

## 20. HTTPS와 OAuth가 VOC에 미치는 영향

OAuth 로그인은 단순 로그인 버튼의 문제가 아니다.

다음 요소가 연결된다.

```text
Domain
+
HTTPS
+
Redirect URI
+
OAuth Provider 설정
+
Client ID / Secret
```

하나라도 불일치하면 고객은 단순히 `로그인이 안 돼요`라고 문의한다.

운영자는 다음을 구분해야 한다.

- Redirect URI mismatch
- HTTPS/TLS 문제
- Domain 문제
- OAuth Provider 설정
- Token 만료
- 사용자 권한/동의 문제
- Application Callback 처리 오류

OAuth Client Secret, Access Token, Refresh Token 등은 반드시 `***`로 마스킹한다.

## 21. .env와 Secret 관리

공개 문서나 Git 저장소에는 실제 Secret을 기록하지 않는다.

예시:

```text
DATABASE_URL=***
SECRET_KEY=***
OAUTH_CLIENT_ID=***
OAUTH_CLIENT_SECRET=***
PG_SECRET_KEY=***
WEBHOOK_URL=***
SMTP_PASSWORD=***
```

환경변수의 **이름과 역할은 문서화하되 실제 값은 분리**하는 것이 원칙이다.

## 22. 회사의 VOC 데이터 모델 제안

초기에는 최소 다음 구조를 고려할 수 있다.


## 24. 개발 시 기본 VOC 체크리스트

앞으로 기능을 설계할 때 다음을 함께 검토한다.

1. 정상 Flow는 무엇인가?
2. 예외 Flow는 무엇인가?
3. 고객은 실패를 어떤 문장으로 표현할까?
4. 고객이 말하지 않고 이탈하는 지점은 어디인가?
5. 운영자가 수동 처리해야 하는 부분은 어디인가?
6. 고객에게 노출되는 상태와 내부 상태가 일치하는가?
7. 금전 영향이 발생할 수 있는가?
8. Retry가 중복 처리를 만들 수 있는가?
9. 운영자가 조회할 식별자가 충분한가?
10. Alert를 만들 수 있는 지표가 있는가?
11. Incident와 연결할 수 있는가?
12. 배포 후 VOC가 감소했는지 측정할 수 있는가?

## 25. 오늘의 핵심 연결

오늘 가장 중요한 학습은 다음 연결이다.

```text
코드
↓
기능
↓
사용자 행동
↓
VOC
↓
운영 데이터
↓
Root Cause
↓
제품/정책/개발 개선
↓
배포
↓
모니터링
↓
재발 방지
```

코딩은 이 흐름의 일부다.

현업에서는 **고객에게 어떤 문제가 발생하고, 운영자가 어떻게 발견하고, 어떤 데이터를 근거로 원인을 찾고, 어떤 개발로 다시 발생하지 않게 할 것인지**까지 설계해야 한다.
