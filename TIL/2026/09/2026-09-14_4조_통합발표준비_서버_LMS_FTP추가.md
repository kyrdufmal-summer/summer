# TIL - 2026-09-14

## 오늘 한 일

오늘은 4조 통합 프로젝트 발표를 준비하면서, 현재까지의 서버·DB·LMS 통합 상태를 발표용 관점으로 다시 정리했다.

특히 4조의 역할을 단순 기능 개발이 아니라 **1·2·3조 기능을 하나의 운영환경으로 묶는 통합 기준 수립과 서버 운영 주관**으로 명확하게 정리했다.

추가로 서버 파일 반영 방식에서 FTP 계열의 직접 파일 전송 방식도 운영 검토 항목으로 포함해 정리했다.

## 1. 4조 발표 핵심 방향 정리

발표의 중심은 “기능을 얼마나 많이 만들었는가”가 아니라,

> **여러 조의 기능을 하나의 서버·DB·파일 저장소·공통 데이터 기준으로 어떻게 통합하고 있는가**

를 보여주는 것이다.

4조는 다음 기준을 주관한다.

- Ubuntu 통합 서버
- SSH 원격 접속
- 배포 반영 방식
- PostgreSQL 운영 기준
- File Storage Root / 권한 기준
- 공통 User / Team / Round 데이터 기준
- 조별 통합 후 Regression 기준

### 배운 점

통합 프로젝트에서는 기능 개발 자체보다 **운영 기준을 하나로 맞추는 역할**이 중요하다.

각 조의 기능이 개별적으로 정상 동작하더라도 서버 경로, DB 연결, 파일 저장 위치, 사용자 식별 기준이 다르면 최종 통합에서는 문제가 발생할 수 있다.

## 2. 현재 서버 구조 정리

현재 4조 Ubuntu PC가 통합 서버 역할을 한다.

발표에서는 서버 접속 구조를 다음과 같이 정리했다.

```text
사용자 / 운영자
    ↓
SSH / HTTP
    ↓
Ubuntu 통합 서버
    ↓
Nginx
    ↓
Gunicorn
    ↓
Django
    ↓
PostgreSQL
```

서버 접속 정보나 계정, 비밀번호처럼 민감한 값은 TIL에는 기록하지 않는다.

```text
SERVER_IP=***
SERVER_USER=***
SERVER_PASSWORD=***
DB_SUPERUSER=***
DB_PASSWORD=***
```

### 현재 확인된 항목

- Ubuntu 서버 구성
- SSH 접속 구조 확인
- Gunicorn 실행 확인
- PostgreSQL 운영
- Core DB / LMS DB 분리

### 아직 남은 운영화 항목

- 서버 재부팅 후 자동기동 확인
- HTTPS 적용
- 최신 develop 기준 전체 Regression
- 파일 저장소 실제 업로드·재다운로드 검증

## 3. DB 구조 정리

통합 서버 PostgreSQL에서는 Core 영역과 LMS 영역을 분리한다.

```text
PostgreSQL Server
├─ ax_evaluation     # Core DB
└─ assignment_lms    # LMS DB
```

### 배운 점

같은 PostgreSQL 서버를 사용하더라도 기능 특성이 다른 시스템은 Database 단위로 분리할 수 있다.

이렇게 하면

- 기존 Core 구조 보호
- LMS 독립성 유지
- 장애 범위 구분
- Migration 충돌 감소

등의 장점이 있다.

## 4. 2조 LMS 통합 상태 정리

현재 2조 LMS 기능은 통합 단계까지 진행된 상태로 정리했다.

주요 흐름은 다음과 같다.


다만 발표에서는 “전체 통합 완료”라고 표현하지 않고,

이라고 표현하는 것이 정확하다.

### 남은 확인 항목

- 최신 develop pull

- DB 연결 확인
- LMS 조회 Test
- 등록 / 수정 Test

- 파일 저장 경로 실제 반영 확인

## 5. LMS 테스트 순서 정리

LMS 테스트는 무조건 Migration부터 다시 실행하는 것이 아니라, 먼저 현재 코드와 환경 상태를 확인하는 순서가 중요하다.

```text
1. git status 확인
2. 최신 develop pull
3. .env 설정 확인
4. settings.py Multi-DB 설정 확인
5. Django check
6. assignment_lms 연결 확인
7. 조회 Test
8. 등록 / 수정 Test
9. 통합 화면 Test
10. 전체 Regression
```

`.env`의 실제 값은 문서에 남기지 않는다.

```env
LMS_DB_NAME=***
DB_HOST=***
DB_USER=***
DB_PASSWORD=***
```

### 배운 점

서버에 DB를 만들었다는 것만으로 통합이 완료되는 것은 아니다.

**코드 → 설정 → DB 연결 → ORM → 화면 → E2E** 순서까지 실제로 이어지는지 확인해야 한다.

## 6. File Storage Root 기준 정리

각 조의 파일이 한 폴더에 섞이지 않도록 저장소 Root 기준을 정리했다.

```text
files/
├─ core/
├─ game/
├─ lms/
├─ prd/
└─ face-recognition/
```

폴더를 생성했다고 운영 완료로 판단하지 않는다.

실제 운영 기준은 다음까지 확인해야 한다.

```text
업로드
→ 서버 저장
→ DB 경로 기록
→ 조회
→ 재다운로드
→ 재배포
→ 서버 재시작 후 파일 유지
```

추가로

- Host 경로
- 권한
- Volume
- 파일 크기
- 삭제 정책
- 보관 기간
- Backup

기준도 운영 측에서 정리해야 한다.

## 7. FTP 추가 검토 사항

오늘 추가로 **FTP 계열의 직접 파일 전송 방식**도 서버 파일 반영 방법 중 하나로 검토했다.

기존에 생각했던 서버 반영 방식은 다음과 같다.

```text
GitHub PR
→ Merge
→ 서버 git pull
```

여기에 운영 또는 파일 전달 상황에 따라 직접 파일 전송 방식도 고려할 수 있다.

```text
개발 PC
→ FTP / SFTP 계열 전송
→ Ubuntu 서버 지정 경로
→ 권한 확인
→ 서비스 반영
```

### 중요한 구분

FTP 방식은 **소스 형상관리 기준을 대체하는 방식**으로 사용하면 안 된다.

코드 변경은 기본적으로

```text
Branch
→ Commit
→ PR
→ Merge
→ 서버 반영
```

흐름을 유지하고,

FTP 계열은 다음과 같은 경우의 **보조 전송 방식**으로 보는 것이 적절하다.

- 대용량 파일 전달
- 운영 파일 반영
- 특정 서버 경로로 직접 업로드가 필요한 경우
- Git으로 관리하지 않는 파일 전달

### 운영 시 확인할 것

- FTP 계정 권한
- 업로드 가능 디렉터리 제한
- 실행파일 / 설정파일 직접 덮어쓰기 방지
- 파일 소유자 / 권한 확인
- 전송 로그 확인
- 기존 파일 Backup 여부

계정 정보와 비밀번호는 TIL에 기록하지 않는다.

```text
FTP_HOST=***
FTP_USER=***
FTP_PASSWORD=***
```

### 배운 점

서버로 파일을 옮길 수 있다는 것과 **안전하게 배포할 수 있다는 것**은 다른 문제다.

직접 파일 전송은 편하지만, 누가 어떤 파일을 언제 바꿨는지 추적하기 어려울 수 있기 때문에 소스코드는 Git을 기준으로 관리하는 것이 안전하다.

## 8. 발표에서 과장해서 말하면 안 되는 부분

현재 단계에서는 다음 표현을 사용하지 않는 것이 중요하다.

- 전체 시스템 완전 통합 완료
- 모든 CI 완전 PASS
- File Storage 운영 완료
- 서버 운영화 완료

대신 다음과 같이 표현한다.

```text
최신 develop 기준 전체 Regression 최종 확인 중
```

또는

```text
주요 통합 기능 반영 완료, 운영환경 기준 검증 진행 중
```

### 배운 점

발표에서는 진행률을 크게 보이게 만드는 것보다 **확인된 사실과 남은 검증 항목을 명확하게 구분하는 것**이 중요하다.
