```text
Django Application
↓

VOC
↓
```

# 1. Ubuntu LMS 접속 장애를 운영 관점에서 보기

오늘 가장 중요한 서버 운영 이슈는 **LMS가 정상 접속되다가 Wi-Fi를 껐다 켠 뒤 일부 사용자에게 다시 접속되지 않는 현상**이었다.

서버 애플리케이션만 보면 정상일 수 있다.

```text
Django 실행 정상
PostgreSQL 정상
Ubuntu 정상
```

그런데 사용자는 접속하지 못할 수 있다.

이 경우 문제 범위를 다음처럼 분리해야 한다.

```text
Application
Network
DNS
Firewall / ACL
HTTPS
Client Network
```

즉, **웹서비스 장애 = 애플리케이션 장애**라고 바로 판단하면 안 된다.

# 2. 네트워크팀의 DHCP 예약 의미

서버 PC는 특정 내부 Wi-Fi에 연결되어 있고, 네트워크팀에서 DHCP 주소가 변경되지 않도록 예약한 상태였다.

실제 내부 IP 등 접속정보는 문서에 남기지 않고 다음처럼 관리한다.

```text
Server Internal IP = ***
Public IP = ***
Subnet = ***
Gateway = ***
DNS = ***
SSH Account = ***
SSH Password = ***
```

DHCP Reservation은 일반적으로 서버의 네트워크 인터페이스 식별정보를 기준으로 **DHCP 서버가 같은 주소를 반복 할당하도록 예약**하는 방식이다.

### 중요한 구분

```text
DHCP 예약
≠
모든 네트워크에서 항상 같은 IP
```

서버가 같은 네트워크에 정상 연결되고 DHCP 과정이 정상이어야 예약 주소를 받을 수 있다.

따라서 Wi-Fi 재연결 후에는 다음을 확인해야 한다.

```bash
ip addr
ip route
```

확인 항목:

- 서버가 예상 인터페이스에 연결되었는가
- 예약된 주소를 실제로 받았는가
- Default Gateway가 존재하는가
- DNS가 정상인가
- 웹서버가 해당 인터페이스에서 Listen 중인가

# 3. Wi-Fi OFF/ON 후 접속이 달라질 수 있는 이유

Wi-Fi 재연결은 단순히 무선 신호를 다시 잡는 작업이 아니다.

다음 과정이 다시 발생할 수 있다.

```text
Wi-Fi Association
↓
DHCP
↓
IP 할당
↓
Gateway 설정
↓
DNS 설정
↓
Routing
↓
Network ACL 적용
```

따라서 재연결 후 문제가 생긴다면 다음 후보를 본다.

### 네트워크 측 후보

- DHCP Reservation이 기대한 장비에 적용되지 않음
- 다른 VLAN / SSID 정책 적용
- 수강생망과 임직원망 ACL 차이
- 특정 Source Network만 허용
- HTTPS/SSH 정책 일부 미적용
- ARP/세션/정책 갱신 문제

### 서버 측 후보

- 서버 IP 변경
- Default Route 변경
- 방화벽 규칙
- Django/Nginx Bind 주소
- 서비스 재시작 실패

### 클라이언트 측 후보

- DNS Cache
- 잘못된 hosts 파일
- 다른 Wi-Fi 접속
- 브라우저 Cache
- Proxy/VPN

운영에서 중요한 것은 **“안 된다”를 바로 서버 문제라고 하지 않고 계층별로 범위를 줄이는 것**이다.

# 4. 접속 장애 Troubleshooting 순서

현업에서는 아래 순서로 확인하면 효율적이다.

```text
1. 서버 자체 상태
↓
2. 서버 IP / Route
↓
3. 서버 내부 Local 접속
↓
4. 같은 Network에서 접속
↓
5. 다른 Network에서 접속
↓

↓
```

반대로 서버 내부에서도 실패한다면 Django/Nginx/Application Process를 먼저 본다.

# 5. Port는 서버의 방 번호처럼 이해할 수 있지만 더 정확한 의미가 있다

IP가 서버를 찾는 주소라면 Port는 **그 서버 안에서 어떤 네트워크 서비스를 찾을지 구분하는 번호**다.

```text
Server IP
├─ Web Service
├─ HTTPS
├─ SSH / SFTP
└─ PostgreSQL
```

대표적으로:

```text
HTTP        80
HTTPS       443
SSH/SFTP    22
PostgreSQL  5432
```

하지만 운영환경에서는 실제 Port와 공개 여부가 다를 수 있으므로 문서에는 실제 접속정보를 직접 남기지 않는다.

### 중요한 점

사용자가 웹페이지를 열 때 PostgreSQL Port로 직접 접속하는 것이 아니다.

```text
Browser
↓ HTTPS
Web Server / Django
↓ DB Driver
PostgreSQL
```

즉 Browser는 웹서비스에 요청하고, Backend가 DB에 접근한다.

# 6. 8000 같은 개발 Port를 운영에서 숨기는 이유

Django 개발 서버는 학습·개발 단계에서 별도 Port로 실행할 수 있다.

운영에서는 보통 다음 구조를 사용한다.

```text
User
↓
https://service.example.com
↓ 443
Nginx / Reverse Proxy
↓
Application Server
↓
Django
```

사용자는 내부 Application Port를 알 필요가 없다.

### 장점

- HTTPS 종료 가능
- 내부 Port 은닉
- 여러 서비스 Route 분리
- Static/Media 처리
- 접근 로그
- Rate Limit
- 보안 정책 적용

# 7. Domain, DNS, hosts의 관계

도메인은 사람이 기억하기 쉬운 이름이고 IP는 네트워크에서 서버를 찾는 주소다.

```text
service.example.com
↓ DNS
***
```

학습 환경에서 hosts 파일을 쓰면 DNS 서버를 거치지 않고 로컬 PC에서 이름을 직접 매핑할 수 있다.

```text
***    service.test
```

하지만 hosts는 **그 PC 한 대에만 적용**된다.

따라서 팀 전체나 외부 사용자가 접근하는 운영서비스라면 정식 DNS가 필요하다.

# 8. HTTPS가 필요한 이유

HTTPS는 단순히 URL 앞에 `https://`를 붙이는 기능이 아니다.

필요 요소:

```text
Domain
↓
DNS
↓
Public/Reachable Network
↓
443 정책
↓
TLS Certificate
↓
Reverse Proxy
↓
Application
```

HTTPS를 적용하면 통신 구간이 암호화되고 브라우저가 서버 인증서를 검증할 수 있다.

### 운영 전 체크

- Domain 소유권
- DNS Record
- 인증서 발급/갱신
- 443 접근 정책
- HTTP → HTTPS Redirect
- Reverse Proxy Header
- Django `ALLOWED_HOSTS`
- CSRF Trusted Origin
- Secure Cookie

# 9. OAuth와 HTTPS/도메인의 관계

Google 등 외부 OAuth Provider는 Redirect URI를 엄격하게 검증한다.

개발환경에서는 localhost 예외가 존재할 수 있지만, 운영에서 임의의 사설 IP와 HTTP 조합은 제약을 받을 수 있다.

따라서 운영 OAuth를 준비할 때는 다음이 필요하다.

```text
정식 Domain
+
HTTPS
+
등록된 Redirect URI
+
OAuth Client 설정
```

민감정보:

```env
OAUTH_CLIENT_ID=***
OAUTH_CLIENT_SECRET=***
OAUTH_REDIRECT_URI=***
```

OAuth가 동작하지 않을 때 Application 코드만 수정하기 전에 **Provider Console에 등록된 Redirect URI와 실제 URL이 정확히 일치하는지** 확인해야 한다.

# 10. SSH와 SFTP

SSH는 원격 서버 Shell에 접속하는 프로토콜이고, SFTP는 SSH 연결을 이용해 파일을 전송한다.

```text
관리자 PC
↓ SSH
Ubuntu Server

관리자 PC
↓ SFTP over SSH
Ubuntu File System
```

따라서 일반적인 SFTP는 별도 FTP Server를 의미하지 않는다.

### FTP와 SFTP 차이

| 구분 | FTP | SFTP |
|---|---|---|
| 기반 | FTP Protocol | SSH |
| 암호화 | 기본 FTP는 평문 위험 | 암호화 |
| 인증 | FTP 계정 | SSH 계정/Key |
| 운영 권장 | 제한적 | 일반적으로 더 안전 |

운영에서는 가능하면 Password보다 SSH Key 기반 인증을 고려한다.

민감정보는 절대 TIL에 기록하지 않는다.

```text
Host = ***
User = ***
Password = ***
Private Key = ***
```

# 11. DB Port를 외부에 열 필요가 있는가

웹서비스 사용자는 PostgreSQL에 직접 접근할 필요가 없다.

권장 구조:

```text
Internet/User
    ↓
443
    ↓
Web/Application Server
    ↓ Internal Network
PostgreSQL
```

DB Port를 불필요하게 외부에 노출하면 공격면이 커진다.

필요한 관리자 접근이 있다면 VPN, Bastion, SSH Tunnel, 내부망 등의 통제된 방식을 검토한다.

# 13. PostgreSQL Transaction 기본

오늘 DB 실습에서는 `COMMIT`과 `ROLLBACK`을 비교했다.

```sql
BEGIN;

-- INSERT / UPDATE / DELETE

COMMIT;
```

정상 처리라면 COMMIT한다.

```sql
BEGIN;

-- 임시 변경

ROLLBACK;
```

실패라면 BEGIN 이후 변경을 취소한다.

### 핵심

```text
COMMIT 전
→ 현재 Transaction의 미확정 변경

COMMIT
→ 변경 확정

ROLLBACK
→ 현재 Transaction 변경 취소
```

# 14. 실습용 transaction_lab 테이블을 따로 만드는 이유

실습 화면에 있는 테이블이 내 DB에 없다고 해서 PostgreSQL 설치가 잘못된 것은 아니다.

`transaction_lab` 같은 이름은 PostgreSQL이 자동 생성하는 시스템 테이블이 아니라 **트랜잭션 학습을 위해 별도로 만든 실습 테이블**일 수 있다.

확인 순서:

```text
Database 확인
↓
Schema 확인
↓
CREATE TABLE 단계 확인
↓
현재 Connection 확인
```

---

# 15. DB Transaction과 PG Transaction은 다르다

이 부분이 오늘의 핵심 연결이다.

```text
PostgreSQL Transaction
≠
PG Transaction
```

PostgreSQL ROLLBACK은 **우리 DB 안의 변경**을 되돌린다.

이미 외부 PG에서 카드 승인이 완료됐다면 DB ROLLBACK만으로 카드 승인을 취소할 수 없다.

예:

```text
PG 승인 성공
↓
우리 DB 저장 실패
↓
PostgreSQL ROLLBACK
↓
PG에는 승인 거래가 남음
```

따라서 별도 보상 처리가 필요하다.

```text
PG 취소 API
+
DB 상태 복구
+
운영 기록
```

# 16. 현업 PG 결제 Lifecycle

```text
PG 계약 / 가맹점 심사
↓
MID / 운영 Key 발급
↓
결제수단 활성화
↓
주문 생성
↓
결제 인증
↓
승인 Authorization
↓
매입 Capture
↓
정산 Settlement
```

결제 API가 성공했다고 회사 통장에 바로 돈이 들어오는 것이 아니다.

### 주요 참여자

- Merchant: 상품/서비스 판매자
- PG: Merchant가 여러 결제수단을 연동할 수 있게 하는 결제 중계 계층
- VAN/결제망: 거래 메시지 중계 영역
- Issuer: 카드 발급사
- Acquirer: 가맹점 거래 매입 영역
- Card Network: 카드 결제 네트워크

국내 실제 계약/처리 구조는 결제수단과 사업자에 따라 달라질 수 있으므로 특정 구조를 모든 거래에 동일하게 적용하면 안 된다.

# 17. Authorization / Capture / Settlement

### Authorization

카드 사용 가능 여부와 거래 승인을 확인한다.

### Capture / 매입

승인 거래를 매출 처리 흐름으로 확정한다.

### Settlement

취소·수수료·조정 등을 반영하여 가맹점 지급으로 이어진다.

이 구분이 필요한 이유는 **취소 시점의 의미가 달라지기 때문**이다.

```text
승인 후 매입 전 취소
→ 승인 해제 성격

매입 후 취소
→ 매출 흐름에 들어간 거래 취소

정산 후 취소
→ 이후 정산에서 상계/조정 가능
```

# 18. 결제 전에 반드시 확정할 업무 정책

코드보다 먼저 다음을 결정해야 한다.

| 정책 | 결정 사항 |
|---|---|
| 결제수단 | 카드/계좌/가상계좌/간편결제 |
| 승인시점 | 주문/예약/배송 전 |
| 부분취소 | 지원 여부 |
| 환불 | 자동/운영자 승인 |
| 쿠폰 | 환불 시 복원 여부 |
| 포인트 | 사용/복구 순서 |
| 재고 | 결제실패/취소 시 복구 |
| 가상계좌 | 입금기한/환불계좌 |
| 정기결제 | Billing Key 정책 |
| 정산 | 주기/수수료/보류 |
| 운영권한 | 강제취소/상태보정 권한 |

정책이 정해지지 않으면 DB Schema도 안정적으로 설계할 수 없다.

# 19. Order와 Payment 상태를 분리한다

```text
Order
ORDER_CREATED
PAID
PREPARING
SHIPPED
COMPLETED
CANCELED
```

```text
Payment
READY
IN_PROGRESS
DONE
FAILED
UNKNOWN
PARTIAL_CANCELED
CANCELED
```

예를 들어 상품 품절 때문에 주문은 CANCELED지만 결제 취소 처리가 아직 진행 중일 수 있다.

따라서:

> **Order Status와 Payment Status는 같은 상태 머신이 아니다.**

---

# 20. UNKNOWN 상태가 중요한 이유

```text
우리 서버
↓ 승인 요청
PG
↓ 승인 성공
응답 전송
↓
Network Timeout
↓
우리 서버는 결과를 모름
```

이때 바로 FAILED 처리하면 실제 카드에서는 승인됐는데 우리 DB에는 실패로 남을 수 있다.

따라서:

```text
UNKNOWN / CONFIRMING
↓
PG 거래 조회
↓
실제 상태 확인
↓
DONE 또는 FAILED 보정
```

이 필요하다.

---

# 21. Idempotency와 중복 결제

사용자가 결제 버튼을 두 번 누르거나 서버가 Timeout 때문에 Retry할 수 있다.

```text
첫 승인 요청
↓
PG 승인 성공
↓
응답 Timeout
↓
Retry
↓
중복 승인 위험
```

방어 수단:

- 고유 orderId
- Idempotency Key
- Unique Constraint
- 기존 거래 조회
- 처리 Event ID 기록

결제 Retry는 단순 HTTP Retry처럼 다루면 위험하다.

---

# 22. 환불 시점은 하나가 아니다

운영에서 반드시 구분해야 한다.

```text
1. 고객 환불 요청 시각
2. PG 취소 승인 시각
3. 카드사/은행 반영 시각
```

고객이 가장 많이 혼동하는 부분 중 하나다.

따라서 상태도 필요에 따라 분리한다.

```text
REFUND_REQUESTED
REFUND_PROCESSING
PG_CANCELED
REFUND_COMPLETED
REFUND_FAILED
```

---

# 23. 부분취소

```text
원결제 100,000
↓
부분취소 20,000
↓
부분취소 10,000

원결제금액 100,000
누적취소금액 30,000
잔여금액 70,000
```

`payment.status = CANCELED` 하나로는 표현할 수 없다.

각 취소 거래를 별도로 보존해야 한다.

---

# 24. Refund와 Chargeback

### Refund

Merchant가 정책에 따라 정상 취소/환불하는 흐름이다.

### Chargeback / Dispute

고객이 카드사 등에 거래 이의를 제기하는 분쟁 절차다.

운영에서는 다음 증빙이 중요해질 수 있다.

- 주문 정보
- 배송/서비스 이용 증빙
- 고객 동의
- 상담 이력
- 결제/취소 시각
- 정책 고지

즉 Chargeback은 개발만의 문제가 아니라 CS·운영·재무·법무 데이터가 함께 연결되는 문제다.

---

# 25. Fraud / FDS

이상거래 예:

- 짧은 시간 반복 결제
- 여러 카드 반복 시도
- 고액 결제 급증
- 동일 Device의 다계정 결제
- 승인 실패 반복
- 비정상 환불 패턴

Risk Score를 통해 정상/추가인증/차단 같은 정책으로 연결할 수 있다.

---

# 26. 3DS와 인증 단계

결제 실패는 하나의 FAILED로 끝내면 원인 분석이 어렵다.

```text
카드사 거절
한도 초과
사용자 취소
3DS 인증 실패
PG 장애
Network Timeout
```

따라서 다음 메타데이터가 필요하다.

```text
failure_code
failure_message
failure_stage
```

---

# 27. 정기결제와 Billing Key

정기결제는 카드번호 자체를 반복 저장하는 방식보다 PG의 Billing Key/Token을 사용하는 구조를 고려한다.

```text
최초 인증
↓
Billing Key 발급
↓
Token 저장
↓
정기 결제일
↓
Token 기반 승인
```

운영에서는 카드 만료, 재발급, Billing Key 폐기, Retry, Grace Period, 미수금까지 고려한다.

---

# 28. Webhook

사용자가 브라우저를 닫아도 결제 상태가 나중에 변경될 수 있다.

대표 예: 가상계좌 입금.

```text
가상계좌 발급
↓
사용자 이탈
↓
나중에 입금
↓
PG 입금 확인
↓
Webhook
↓
우리 DB 상태 변경
```

Webhook 처리 원칙:

```text
Raw Event 저장
↓
Signature 검증
↓
Event ID 중복 확인
↓
현재 상태 확인
↓
필요 시 PG 재조회
↓
DB 반영
↓
processed_at 기록
```

Webhook도 중복 수신될 수 있다는 전제로 설계한다.

---

# 29. Payment Ledger

`payments.status`만 덮어쓰면 돈의 이동 이력이 사라진다.

따라서 승인·취소·환불·조정 거래를 별도 Ledger/Transaction으로 기록하는 것이 좋다.

```text
원승인
├─ 부분취소 #1
├─ 부분취소 #2
└─ 조정
```

돈의 변경은 단순 UPDATE보다 **근거가 남는 Event**로 생각하는 것이 안전하다.

---

# 30. Source of Truth

하나의 DB가 모든 업무의 진실이 되는 것은 아니다.

```text
주문 상태 → Order DB
금전 이벤트 → Payment Ledger
외부 승인 → PG Transaction
실제 지급 → Settlement Data
회계 확정 → Accounting Ledger
```

그래서 서로 비교하는 **Reconciliation**이 필요하다.

---

# 31. Settlement와 T+N

승인과 정산은 다르다.

```text
거래일 T
↓
매입/취소/수수료/조정
↓
T+N
↓
가맹점 지급
```

정확한 N은 계약/결제수단에 따라 다를 수 있으므로 코드에 고정하지 않는다.

정산 데이터 예:

```text
Gross Sales
Cancellation
Fee
Tax
Adjustment
Reserve / Hold
Net Settlement
```

---

# 32. Reconciliation

```text
우리 Payment Ledger
vs
PG 거래내역
vs
PG Settlement
```

Mismatch가 발생하면:

```text
차이 탐지
↓
원인 분석
↓
PG 재조회
↓
DB 보정 / 취소 / 재처리
↓
Audit Log
```

> **결제 시스템의 완성은 승인 API 성공이 아니라 대사가 가능한 상태다.**

---

# 33. Saga와 Compensation

분산 시스템에서는 모든 외부 시스템을 하나의 PostgreSQL ROLLBACK으로 되돌릴 수 없다.

```text
주문 생성
↓
결제 승인
↓
재고 차감
↓
쿠폰 사용
↓
배송 생성 실패
```

보상 흐름:

```text
쿠폰 복구
↓
재고 복구
↓
PG 취소
↓
주문 취소
```

이것이 Compensation의 핵심이다.

---

# 34. Outbox / Queue / DLQ

DB 저장은 성공했는데 Message 발행이 실패할 수 있다.

Transactional Outbox는 비즈니스 데이터와 발행할 Event를 같은 DB Transaction에 저장한다.

```text
BEGIN
orders INSERT
outbox_events INSERT
COMMIT
```

Worker가 Outbox를 읽어 Queue로 발행한다.

메시지는 중복 전달될 수 있으므로 Idempotent Consumer가 필요하다.

계속 실패하는 Event는 DLQ로 격리한다.

운영에서는 다음을 본다.

- Retry 횟수
- DLQ 건수
- 가장 오래된 Event Age
- 영향 고객 수
- 영향 금액
- 재처리 성공률

---

# 35. VOC를 시스템 설계에 포함해야 하는 이유

오늘 추가로 정리한 가장 중요한 운영 관점이다.

VOC는 단순한 고객 문의 목록이 아니다.

```text
고객 불편
↓
VOC
↓
Pattern
↓
Root Cause
↓
Product / Policy / System Issue
↓
Owner
↓
Fix
↓
VOC 감소 확인
```

즉 VOC는 **회사가 스스로 발견하지 못한 문제를 알려주는 Sensor**로 볼 수 있다.

---

# 36. Explicit VOC와 Implicit VOC

### Explicit VOC

- 전화
- 채팅
- 이메일
- 설문
- 리뷰
- 게시판

### Implicit VOC

고객이 말하지 않고 행동으로 남기는 문제다.

- 결제 실패 후 이탈
- 반복 클릭
- 같은 화면 반복 진입
- 환불 후 탈퇴
- 오류 후 재방문 없음
- 인증 중도 포기

신생회사는 **문의한 고객만 보면 Silent Churn을 놓치기 쉽다.**

---

# 37. VOC 건수만 보면 안 된다

서비스가 성장하면 절대 건수는 자연스럽게 증가한다.

따라서:

```text
VOC Rate = VOC 건수 / 거래건수 또는 활성사용자수
```

결제 예:

```text
결제 VOC / 결제시도건수
환불 VOC / 환불건수
중복결제 VOC / 승인건수
```

를 같이 본다.

---

# 38. VOC는 증상이고 Root Cause는 별개다

고객:

> 결제가 안 돼요.

가능한 Root Cause:

```text
카드사 거절
3DS 인증실패
PG Timeout
우리 Backend 오류
금액 mismatch
중복 Lock
Network 장애
```

따라서 VOC Data Model에서 최소한 다음을 분리하는 것이 좋다.

```text
customer_symptom
category
root_cause
resolution
```

---

# 39. VOC Taxonomy

`결제 / 배송 / 회원 / 기타` 수준만으로는 개발 개선까지 연결하기 어렵다.

예:

```text
Domain: 결제
Journey: 결제시도
Issue Type: 결제실패
Failure Type: 카드승인실패
Root Cause: 한도초과
```

계층형 분류를 만들면 어떤 문제를 개발해야 하는지 훨씬 명확해진다.

---

# 40. VOC 누수 Case 1 - 문의하지 않고 떠나는 고객

```text
실제 장애 고객 1,000명
├─ 문의 20명
├─ 재시도 400명
├─ 그냥 이탈 300명
└─ 포기 280명
```

VOC 20건만 보면 영향도를 심각하게 과소평가할 수 있다.

그래서 다음을 함께 본다.

```text
VOC
Affected Users
Retry Rate
Drop-off
Conversion
Churn
```

---

# 41. VOC 누수 Case 2 - 상담사가 너무 잘 처리해서 제품 문제가 숨겨짐

예:

```text
고객: 배송지 변경이 안 돼요.
↓
상담사가 관리자 화면에서 매번 수정
↓
고객 문제 해결
↓
Product Team에는 Bug가 안 보임
```

이때 **Manual Workaround Count** 자체가 중요한 VOC 지표다.

운영자가 반복해서 누르는 관리자 기능은 제품 자동화 후보가 될 수 있다.

---

# 42. VOC 누수 Case 3 - 재문의

상담을 빨리 종료했다고 해결된 것이 아니다.

다음날 같은 고객이 같은 문제로 다시 연락하면 실제 해결률은 낮다.

중요 지표:

```text
First Contact Resolution
Repeat Contact Rate
Reopen Rate
```

재문의 이유도 구분한다.

- 미해결
- 안내 부족
- 처리 지연
- 정책 불만
- 새로운 문제

---

# 43. VOC 누수 Case 4 - 배포 직후 문제

```text
14:00 Deploy
↓
14:07 결제 실패 VOC 급증
```

이 연결이 가능하면 장애 탐지가 빨라진다.

추천 연결정보:

```text
release_version
deployment_id
error_code
api_endpoint
voc_created_at
incident_id
```

---

# 44. VOC Spike Detection

평상시 시간당 결제실패 문의가 3건인데 갑자기 30건이 되면 장애 신호일 수 있다.

```text
VOC Baseline
↓
실시간 Count
↓
Threshold / Anomaly
↓
Alert
```

사람이 문의를 하나씩 읽고 장애를 발견하는 구조는 늦다.

---

# 45. 금전 VOC는 별도 Severity가 필요하다

```text
검색 버튼 불편 1건
≠
이중결제 1건
```

같은 1건으로 계산하면 안 된다.

추가 지표:

```text
Affected Customer Count
Financial Impact
Amount at Risk
Refund Pending Amount
```

금전 이슈는 건수보다 금액이 Severity를 결정할 수 있다.

---

# 46. VOC Priority

단순 Frequency만으로 우선순위를 정하지 않는다.

개념적으로:

```text
Priority
=
Frequency
× Customer Impact
× Financial Impact
× Churn Risk
× Strategic Importance
```

예:

```text
UI 불편 5,000건 / 금전영향 없음
이중결제 5건 / 금전영향 매우 큼
```

후자가 더 높은 우선순위가 될 수 있다.

---

# 47. Preventable VOC

VOC를 다음처럼 나눌 수 있다.

```text
Preventable VOC
Unpreventable VOC
```

회사는 특히 **예방 가능한 반복 VOC**를 줄여야 한다.

예:

```text
안내 문구 부족
UX 오류
상태 표시 부족
자동화 부족
정책 모호
재시도 설계 부족
```

이런 문제는 Product/Engineering 개선으로 문의 자체를 없앨 수 있다.

---

# 48. Closed Loop VOC

VOC를 수집해서 보고서만 만들면 반쪽짜리다.

```text
VOC
↓
Issue
↓
Owner
↓
Severity
↓
Due Date
↓
Fix
↓
Deploy
↓
VOC 변화 측정
↓
Close
```

반드시 Action과 결과 측정까지 이어져야 한다.

---

# 49. VOC를 개발 요구사항으로 번역하는 방법

VOC:

> 돈은 빠져나갔는데 주문이 없어요.

운영 해석:

```text
Payment succeeded
but Order state missing
```

기술 후보:

```text
PG 승인 성공
+
DB 저장 실패
```

필요 개발:

```text
UNKNOWN 상태
PG Transaction Lookup
Idempotency
Reconciliation
Order Recovery
Alert
```

이렇게 **고객 언어 → 운영 언어 → 시스템 언어 → 개발 요구사항**으로 번역한다.

---

# 50. 서버 장애 VOC도 같은 방식으로 본다

VOC:

> LMS가 아까는 됐는데 Wi-Fi를 다시 연결하니까 안 돼요.

단순 답변:

```text
다시 접속해 보세요.
```

로 끝내면 안 된다.

운영 분석:

```text
Client Network 변경
↓
DHCP / VLAN / ACL / DNS 후보
↓
서버 Application 정상 여부 확인
↓
Network Path 비교
↓
영향 사용자 범위 확인
```

개발/운영 개선:

- Health Check
- 접근 로그
- Network Monitoring
- 사용자 오류화면 개선
- 장애 공지
- Incident ID
- 접속 실패 VOC 자동 Tagging

---

# 51. 신생회사가 놓치기 쉬운 VOC 운영 포인트

1. 문의한 고객만 보고 Silent Churn을 놓친다.
2. VOC 건수만 보고 거래량 대비 Rate를 보지 않는다.
3. 고객 증상과 Root Cause를 같은 값으로 저장한다.
4. Taxonomy가 너무 얕아 개발 요구사항으로 연결되지 않는다.
5. Owner가 없어 Issue가 사라진다.
6. 상담사의 수동처리가 Product Debt를 숨긴다.
7. 재문의율을 보지 않는다.
8. 금전 이슈를 일반 문의와 같은 Priority로 계산한다.
9. Deploy/Incident와 VOC를 연결하지 않는다.
10. 해결 후 VOC가 실제 감소했는지 확인하지 않는다.
11. 고객 Journey 전체가 아니라 메뉴별 문의만 본다.
12. 오류코드와 VOC를 연결하지 않는다.
13. 운영자 Admin 행동 로그를 분석하지 않는다.
14. 고객에게 보이는 상태와 내부 상태의 차이를 관리하지 않는다.

# 55. 오늘의 End-to-End 이해

```text
[사용자]
LMS / 서비스 접속
↓
[Network]
Wi-Fi / DHCP / VLAN / ACL
↓
[Name Resolution]
Domain / DNS
↓
[Security]
HTTPS / TLS
↓
[Reverse Proxy]
Nginx
↓
[Application]
Django
↓
[Database]
PostgreSQL Transaction
↓
[External System]
PG / OAuth
↓
[Distributed Consistency]
Webhook / Retry / Outbox / Compensation
↓
[Operations]
Monitoring / Reconciliation / Audit
↓
[Customer]
VOC / Silent Churn
↓
[Improvement]
Root Cause → Product/Engineering Fix
```

이 구조를 이해하면 서버, DB, 네트워크, 결제, 운영이 각각 따로 존재하는 것이 아니라 **한 사용자의 경험을 완성하는 하나의 시스템**이라는 것이 보인다.
