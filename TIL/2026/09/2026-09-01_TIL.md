## 1. 공통 DB VIEW 검증

통합 프로젝트에서 사용하는 공통 VIEW가 실제 DB에 존재하고 정상적으로 조회되는지 직접 확인했다.

### 확인한 내용
- 공통 VIEW 실제 DB 존재 여부 확인
- VIEW 직접 조회
- 조회 결과 데이터 이상 여부 확인
- VIEW의 목적과 사용 대상 정리

### 배운 점

VIEW는 단순히 조회 편의를 위해 만드는 것이 아니라,  
통합 프로젝트에서 여러 기능이 **동일한 사용자·팀 데이터를 같은 기준으로 조회하도록 만드는 공통 조회 기준**으로 사용할 수 있다.

특히 통합 단계에서는 각 프로젝트가 User / Student / Team 데이터를 제각각 조회하거나 중복 생성하지 않도록 기준을 잡는 것이 중요하다.

## 3. GitHub Issue와 실제 개발 내용 연결

팀원이 Issue에서 완료했다고 표시한 내용이 실제 코드나 문서에 존재하는지 확인하는 기준을 정리했다.

### 확인 기준

1. Issue에 적힌 작업과 실제 변경 내용이 일치하는가
2. 완료 체크한 항목에 실제 근거가 있는가
3. Deliverable이 실제 개발 내용을 정확하게 설명하는가
4. PR의 base branch가 `develop`인지 확인
5. 테스트 또는 검증 결과가 기록되어 있는가
6. 누락되거나 과장된 완료 체크가 없는가
7. 팀장 입장에서 Merge를 승인할 수 있는 상태인가

### 상태 판단 기준

- **PASS** : 근거와 검증이 충분하여 승인 가능
- **보완 필요** : 기능은 있으나 문서·검증 등이 부족
- **BLOCKER** : 통합에 영향을 줄 수 있는 문제 존재

### 배운 점

GitHub Issue의 체크박스가 체크되어 있다고 해서 실제 작업이 완료된 것은 아니다.

**Issue → 코드/문서 → 테스트 → Deliverable → PR**

까지 근거가 연결되어야 실제 완료라고 판단할 수 있다.

## 4. Branch / PR / Merge 개념 정리

오늘 GitHub의 Pull Request가 무엇을 의미하는지도 다시 정리했다.

### 작업 흐름

```text
개인 Branch
    ↓
개발 또는 문서 수정
    ↓
Commit / Push
    ↓
Pull Request
    ↓
Reviewer 확인
    ↓
Merge
    ↓
develop 기준 재검증
```

Pull Request가 생성됐다는 것은

> 새로운 변경사항을 기준 브랜치에 합쳐달라는 요청이 등록되었다

는 의미이다.

따라서 **PR 생성 = 통합 완료**가 아니다.

실제로 `Merged` 상태가 되어야 `develop` 또는 `main`에 변경사항이 반영된다.

## 5. 아직 소스 통합 전이라는 점 구분

현재 각 조에서 기능을 개별적으로 개발하고 있기 때문에 아직 전체 소스가 완전히 통합된 상태는 아니다.

따라서 현재 단계에서 확인할 수 있는 것과 없는 것을 구분해야 한다.

### 지금 확인 가능한 것

- 개별 기능 구현 여부
- Branch 존재 여부
- Commit 여부
- PR 여부
- 문서 작성 여부
- 개별 DB 검증
- 테스트 결과
- Deliverable 작성 여부

### 아직 최종 판단하기 어려운 것

- 전체 기능 간 충돌
- 전체 Regression
- 전체 E2E Flow
- 모든 프로젝트 통합 후 DB 충돌
- 최종 통합 시스템 정상 동작 여부

### 배운 점

통합하기 전인데도 “전체 통합 검증 완료”라고 기록하면 과장된 완료 처리가 된다.

개발 단계에서는 반드시

**개별 기능 검증**

과

**통합 후 검증**

을 구분해서 기록해야 한다.

## 6. Daily Deliverable의 역할 이해

개발하거나 검증한 결과는 GitHub Issue 댓글에만 남기는 것이 아니라  
`docs/deliverables` 아래에 공식 산출물로 남겨야 한다.

Deliverable에는 최소한 다음 내용이 있어야 한다.

- 작업 목적
- 수행 내용
- 실제 검증 방법
- 검증 결과
- 문제점
- 현재 상태
- 다음 작업

### 배운 점

Deliverable은 단순한 작업일지가 아니라

> 다른 사람이 이 문서만 보고도 무엇을 했고, 어떻게 검증했고, 왜 완료라고 판단했는지 알 수 있는 근거 문서

여야 한다.

## 7. 오늘 가장 중요하게 배운 점

오늘 가장 크게 이해한 것은  
**“개발 완료”와 “검증 완료”는 다르다**는 것이다.

기능을 만들었다고 바로 완료가 아니라,

```text
개발
 ↓
직접 실행
 ↓
DB 확인
 ↓
테스트
 ↓
문서화
 ↓
Cross Check
 ↓
PR
 ↓
Merge
 ↓
통합 후 재검증
```

과정을 거쳐야 최종적으로 완료라고 할 수 있다.

특히 팀 통합 프로젝트에서는  
개인의 개발 속도보다 **근거가 남아 있는 개발 프로세스와 검증 가능성**이 중요하다.
