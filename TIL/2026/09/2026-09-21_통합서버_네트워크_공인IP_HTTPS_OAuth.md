## 1. 네트워크팀 회신 구조 정리

네트워크팀에 답변할 때는 단순히 현재 IP만 전달하는 것이 아니라, 서버 운영에 필요한 전체 네트워크 항목을 구조적으로 정리해야 한다.

답변을 받은 뒤 내부 정리용 기준은 다음과 같이 잡았다.

```text
내부 IP:
공인 IP:
Subnet:
Gateway:
DNS:
Domain:
HTTPS:
80/443 정책:
22 SSH/SFTP 정책:
5432 DB 정책:
관리 담당자:
```

이 형식은 네트워크팀에 그대로 보내는 질문지라기보다, **네트워크팀 답변을 받은 뒤 운영 정보를 한 곳에 정리하는 체크리스트**로 보는 것이 자연스럽다.

## 2. 현재 통합 서버 네트워크 방향

현재 4조 통합 서버는 Ubuntu 환경에서 운영 중이며, 내부망 기준 Django 서비스가 동작하고 있다.

현재 내부 IP:

```text
10.2.16.254
```

현재 서비스 접근 형태:

```text
http://10.2.16.254:8000/
```

운영 방향은 다음과 같이 정리했다.

- 수강생 네트워크에서 접근 가능
- 임직원 네트워크에서도 접근 가능
- 고정 IP는 임의 설정하지 않음
- 네트워크팀에서 사용 가능한 고정 IP를 배정
- Subnet / Gateway / DNS 정보를 함께 받아 Ubuntu에 적용
- 향후 Domain + HTTPS 적용

### 배운 점

고정 IP는 “현재 IP를 그냥 고정해서 쓰는 것”이 아니라 **네트워크팀이 충돌 없는 IP와 네트워크 정보를 배정하고, 서버에서 그 값을 설정하는 방식**이 안전하다.

## 3. 내부 IP와 공인 IP 구분

내부 IP는 같은 조직 또는 같은 네트워크 안에서 통신할 때 사용하는 주소이다.

예:

```text
10.2.16.254
```

이 주소는 일반적으로 인터넷 외부에서 직접 접근할 수 없다.

반면 공인 IP는 인터넷에서 해당 네트워크를 식별할 수 있는 주소이다.

전체 개념은 다음과 같이 이해할 수 있다.

```text
외부 사용자
↓
공인 IP
↓
Firewall / Router
↓
내부 IP
↓
Ubuntu Server
↓
Django
```

외부 접속 가능 환경을 만든다는 것은 단순히 Ubuntu에 IP 하나를 넣는 문제가 아니라,

```text
공인 IP
+ Firewall
+ Port
+ Domain
+ HTTPS
```

까지 함께 설계해야 하는 문제이다.

## 4. Domain과 HTTPS가 필요한 이유

현재는 IP와 Port를 직접 입력해서 접속한다.

```text
http://10.2.16.254:8000/
```

운영 서비스에서는 보통 다음 형태로 바뀐다.

```text
https://service.example.com
```

이 구조에서는

- 사용자는 IP를 직접 기억할 필요가 없음
- 8000 같은 내부 Application Port를 직접 노출하지 않아도 됨
- HTTPS 인증서를 적용할 수 있음
- OAuth 같은 외부 인증서비스 연동이 쉬워짐

일반적인 구조는 다음과 같다.

```text
사용자
↓
https://domain
↓
443
↓
Nginx
↓
Django / Gunicorn : 8000
```

### 핵심 이해

8000 Port가 없어진다는 의미는 Django가 8000을 전혀 사용하지 않는다는 뜻이 아니다.

외부 사용자는 443으로 접속하고, Nginx 내부에서 443 → 8000으로 전달할 수 있다.

즉, 8000은 **내부 Application Port**로 남을 수 있다.

## 5. Google OAuth와 현재 서버 환경

현재 Google OAuth는 사설 IP + HTTP 환경에서 정책상 제약이 있기 때문에 소셜 로그인 기능을 임시 제한한 상태이다.

현재 흐름:

```text
내부 IP
+
HTTP
↓
OAuth 제한
↓
Google / Kakao 로그인 임시 비활성화
```

향후 목표:

```text
외부 접근 환경
+
Domain
+
HTTPS
↓
OAuth Redirect URI 등록
↓
소셜 로그인 재활성화
```

### 배운 점

OAuth 문제는 단순 Django 코드 오류가 아니라 **외부 인증서비스의 보안 정책 + 현재 서버 네트워크 구조**와 연결된 문제이다.

따라서 해결 순서도 코드 수정이 먼저가 아니라,

```text
네트워크 환경 준비
→ Domain
→ HTTPS
→ OAuth 설정
→ 기능 재활성화
```

순서가 된다.

## 6. Port 정책을 따로 정리해야 하는 이유

서버에서는 Port마다 역할과 공개 범위가 다르다.

### 80 / 443
웹서비스용

```text
80  = HTTP
443 = HTTPS
```

최종 서비스에서는 일반적으로 443을 중심으로 사용한다.

### 22
SSH / SFTP 관리용

```text
22
```

개발자 또는 서버 관리자만 접근해야 한다.

### 5432
PostgreSQL 기본 Port

```text
5432
```

일반 사용자에게 공개할 이유가 없다.

서비스 구조는 보통 다음과 같다.

```text
사용자
→ 443
→ Django
→ PostgreSQL : 5432
```

### 배운 점

“서버가 외부에 열려 있다”와 “모든 Port를 외부에 공개한다”는 전혀 다른 의미이다.

최소한의 Port만 공개하는 것이 기본 원칙이다.
