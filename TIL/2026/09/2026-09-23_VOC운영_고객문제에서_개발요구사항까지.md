# 2026-09-23 TIL — VOC 운영: 고객의 문제를 개발 요구사항과 운영 개선으로 바꾸기

## 1. 오늘의 핵심

오늘은 기능을 단순히 구현하는 개발 관점에서 더 나아가, **VOC(Voice of Customer)를 회사의 운영·제품·개발 개선으로 연결하는 방법**을 정리했다.

핵심은 다음과 같다.

> VOC는 고객 문의를 모으는 데이터가 아니라, 회사가 아직 발견하지 못한 제품·정책·운영·시스템 문제를 탐지하는 센서다.

따라서 좋은 VOC 운영은 `문의 접수 → 답변 → 종료`가 아니라 다음의 Closed Loop를 가져야 한다.

```text
고객 문제
↓
VOC 수집
↓
증상 분류
↓
Root Cause 분석
↓
영향 범위·금액 산정
↓
Owner 지정
↓
제품/정책/개발 개선
↓
배포
↓
VOC 감소 여부 확인
↓
재발 방지
```

---

## 2. VOC와 Root Cause를 분리해야 하는 이유

고객이 말하는 것은 대부분 **증상(Symptom)** 이다.

예를 들어 고객이 말하는 내용이 다음과 같다고 하자.

```text
"결제가 안 돼요."
```

하지만 실제 원인은 다음처럼 매우 다양할 수 있다.

- 카드사 승인 거절
- 본인인증 실패
- PG Timeout
- 우리 서버 오류
- 주문금액과 승인금액 불일치
- 중복결제 방지 Lock
- 네트워크 단절
- 외부 결제서비스 장애

따라서 VOC 데이터에는 최소한 다음 개념을 구분해야 한다.

```text
customer_symptom
issue_category
root_cause
resolution
```

이 구분이 없으면 고객의 표현을 그대로 집계할 뿐, 개발팀이 고칠 수 있는 데이터로 변환되지 않는다.

## 3. VOC Taxonomy는 처음부터 계층형으로 설계한다

초기 회사에서 흔히 다음 정도로만 분류하기 쉽다.

```text
결제
환불
배송
회원
기타
```

하지만 이런 대분류만으로는 반복 원인을 찾기 어렵다.

예를 들어 결제 VOC는 다음처럼 계층화할 수 있다.

```text
Domain: 결제
└─ Journey: 결제시도
   └─ Issue Type: 결제실패
      └─ Failure Type: 승인실패
         └─ Root Cause: 카드사 거절
```

또는 시스템 관점에서 다음처럼 볼 수 있다.

```text
결제
├─ 승인
│  ├─ 사용자취소
│  ├─ 카드사거절
│  ├─ 인증실패
│  ├─ Timeout
│  └─ PG장애
├─ 취소
├─ 부분취소
├─ 환불
└─ 정산
```

### 왜 필요한가?

`결제 VOC 1,000건`만 알아서는 무엇을 고쳐야 할지 모른다.

반면 다음처럼 알 수 있다면 행동이 가능하다.

```text
결제실패 1,000건
└─ 인증실패 620건
   └─ 특정 인증 단계 이탈 480건
```

이제 개발팀은 해당 인증 Flow를 분석할 수 있다.

## 4. VOC 건수보다 VOC Rate를 본다

서비스 규모가 커지면 문의 건수 자체는 증가할 수 있다.

따라서 절대 건수만 보면 서비스가 나빠졌다고 잘못 판단할 수 있다.

예:

```text
서비스 A
고객 1,000명 / VOC 100건
→ 10%

서비스 B
고객 100,000명 / VOC 500건
→ 0.5%
```

VOC는 B가 더 많지만 실제 문의 발생률은 A가 훨씬 높다.

따라서 업무별 분모를 같이 관리한다.

```text
VOC Rate = VOC 건수 / 대상 거래 또는 사용자 수
```

결제 도메인이라면 다음 지표가 가능하다.

- 결제 VOC / 결제시도건수
- 환불 VOC / 환불요청건수
- 배송 VOC / 배송건수
- 로그인 VOC / 로그인시도건수

## 5. 가장 위험한 VOC 누수: 문의하지 않은 고객

VOC 시스템이 고객센터 문의만 수집하면 실제 문제 규모를 과소평가할 수 있다.

예를 들어 1,000명이 결제 오류를 경험해도 실제 문의는 일부만 할 수 있다.

```text
오류 경험 고객 1,000명
├─ 고객센터 문의
├─ 여러 번 재시도
├─ 결제 포기
└─ 서비스 이탈
```

따라서 Explicit VOC와 Implicit VOC를 같이 봐야 한다.

### Explicit VOC

- 전화
- 채팅
- 이메일
- 설문
- 리뷰
- SNS

### Implicit VOC

- 페이지 이탈
- 결제 실패
- 반복 클릭
- 재시도
- 환불
- 구독 해지
- 오류 이후 재방문 없음

특히 아무 말 없이 떠나는 **Silent Churn**은 상담 데이터만으로는 잡히지 않는다.

## 6. 반복 VOC는 상담 문제가 아니라 Product Debt일 수 있다

같은 질문이 매일 반복된다고 하자.

```text
"비밀번호는 어디서 변경하나요?"
```

상담사가 빠르게 답변하면 상담 생산성 지표는 좋아질 수 있다.

하지만 회사 전체 관점에서는 다음 문제일 수 있다.

```text
정보구조 문제
UX 문제
안내문구 문제
정책 노출 문제
Self-service 부재
```

따라서 좋은 VOC 조직의 목표는 단순히 **상담을 빨리 끝내는 것**이 아니라 **예방 가능한 문의 자체를 줄이는 것**이어야 한다.

이를 다음처럼 분리할 수 있다.

```text
Preventable VOC
Unpreventable VOC
```

예방 가능한 반복 문의는 Product Backlog로 보내야 한다.

## 7. 상담사의 수동처리는 중요한 제품 데이터다

신생회사에서 특히 놓치기 쉬운 지점이다.

운영자가 관리자 화면에서 다음 작업을 반복할 수 있다.

- 주문 강제취소
- 결제 상태 보정
- 알림 재발송
- 포인트 복구
- 회원정보 수정
- Webhook 재처리

이것을 단순히 운영 업무라고 생각하면 안 된다.

운영자가 같은 수동조치를 반복한다면 다음을 질문해야 한다.

> 이 기능은 제품이나 시스템이 자동으로 처리해야 하는 것은 아닌가?

따라서 `Manual Workaround Count` 자체가 중요한 VOC/제품 지표가 될 수 있다.

## 8. 결제 VOC를 개발 요구사항으로 번역하는 예

### 고객 VOC

```text
"돈은 빠져나갔는데 주문이 없어요."
```

### 운영 관점

```text
결제는 승인된 것으로 보이나 주문이 생성되지 않음
```

### 기술적 가설

```text
PG 승인 성공
↓
우리 서버 응답 지연 또는 DB 오류
↓
Order 저장 실패
```

### 확인할 데이터

- 내부 주문 ID
- 내부 Payment ID
- PG 거래 식별자
- 승인 시각
- 승인 금액
- DB Transaction 결과
- Webhook 수신 여부
- Retry 이력

민감한 실제 식별자나 접근정보는 문서에 기록하지 않고 `***`로 마스킹한다.

### 필요한 개발 기능

```text
UNKNOWN 결제 상태
PG 거래 재조회
Idempotency
Payment Ledger
Reconciliation Batch
주문 복구 절차
```

즉 VOC 하나가 **운영 정책 → 데이터 요구사항 → 시스템 설계 → 개발 Backlog**로 연결된다.

## 9. 금전 VOC는 일반 VOC와 분리한다

다음 두 건은 동일한 1건으로 취급하면 안 된다.

```text
버튼 위치가 불편함
```

```text
고액 이중결제 발생
```

결제·환불·정산 관련 VOC에는 다음 정보를 추가로 관리하는 것이 좋다.

```text
financial_impact
amount_at_risk
affected_customer_count
transaction_count
```

우선순위도 단순 건수가 아니라 다음 요소를 함께 본다.

```text
Priority
= Frequency
× Customer Impact
× Financial Impact
× Churn Risk
× Strategic Importance
```

소수 건이어도 금액 피해가 크면 최고 우선순위가 될 수 있다.

## 10. Severity는 고객 영향 기준을 포함해야 한다

기술 장애 시간만으로 Severity를 정하면 고객 피해를 놓칠 수 있다.

예시 기준:

| 등급 | 예시 |
|---|---|
| S0 | 금전·개인정보·대규모 고객 피해 |
| S1 | 핵심 기능 사용 불가 |
| S2 | 일부 사용자 영향, 우회 가능 |
| S3 | UX 불편 |
| S4 | 개선 제안 |

중요한 것은 기술 장애의 크기와 고객 영향의 크기를 함께 보는 것이다.

## 11. VOC Spike는 장애 탐지 센서가 될 수 있다

평소 결제실패 VOC가 시간당 몇 건 수준인데 갑자기 몇 배로 증가하면 서비스 장애의 초기 신호일 수 있다.

```text
최근 30분 결제실패 VOC
> 평상시 Baseline × 임계치
→ Alert
```

운영자가 문의를 하나씩 읽다가 장애를 발견하면 늦을 수 있다.

따라서 다음 데이터를 함께 모니터링하는 것이 좋다.

- VOC Rate
- Error Rate
- Payment Failure Rate
- HTTP 5xx
- Timeout
- Queue 적체
- Webhook 실패
- DB Error

## 12. 배포와 VOC를 연결한다

배포 이후 VOC가 갑자기 증가하면 Release Regression일 가능성이 있다.

```text
배포
↓
특정 기능 오류 증가
↓
VOC Spike
```

따라서 분석 데이터에 다음 연결정보가 있으면 좋다.

```text
release_version
deployment_id
incident_id
voc_id
```

그러면 다음과 같은 분석이 가능하다.

```text
특정 Release 이후
결제 실패 VOC 증가
→ 해당 Release 변경사항 분석
```

## 13. Incident와 VOC를 연결한다

장애관리와 VOC 관리가 분리되어 있으면 고객 영향 규모를 제대로 계산하기 어렵다.

Incident 종료 후에는 최소한 다음을 남기는 것이 좋다.

```text
Incident
Root Cause
Affected Users
Related VOC Count
Financial Impact
Recovery
Remediation
Owner
Due Date
```

이렇게 해야 장애 복구에서 끝나지 않고 재발 방지까지 이어진다.

VOC가 회의자료에서 끝나지 않으려면 반드시 Owner가 있어야 한다.

```text

```

전체 흐름은 다음과 같다.

```text

↓
```

## 17. 서버·네트워크·DB 장애도 VOC 관점으로 본다

오늘의 핵심 관점은 결제뿐 아니라 서버 운영에도 그대로 적용된다.

예를 들어 고객의 증상은 단순히 다음과 같을 수 있다.

```text
"사이트가 안 열려요."
```

하지만 Root Cause 후보는 여러 계층에 있다.

```text
Client
↓
Wi-Fi / Network
↓
DNS / Domain Resolution
↓
HTTPS / TLS
↓
Reverse Proxy
↓
Application Server
↓
DB
↓
외부 API / OAuth
```

따라서 운영자는 고객 문구만 보고 원인을 단정하지 않고 계층별로 확인해야 한다.

### 네트워크 계층

- DHCP 상태
- IP 변경 여부
- VLAN / ACL
- Gateway
- DNS
- 방화벽

### Web 계층

- Domain Resolution
- 80/443 접근
- TLS 인증서
- Reverse Proxy
- Application Health

### Application 계층

- Django/FastAPI 등 애플리케이션 상태
- Process/Worker 상태
- 환경변수 로딩
- OAuth Callback 설정

### DB 계층

- PostgreSQL Process
- Connection
- Migration
- Connection Pool
- Lock / Transaction

### 운영 계층

- SSH/SFTP 접근
- 배포 상태
- 로그
- 재부팅 후 자동기동
- Backup/Restore

실제 서버 IP, SSH 계정, DB 계정, 비밀번호, OAuth Secret, API Key, Webhook URL, `.env` 값은 TIL에 직접 기록하지 않고 모두 `***` 처리한다.

## 18. SSH/SFTP와 FTP를 운영 관점에서 구분

파일 전송이 필요하다고 해서 무조건 FTP를 별도 구축할 필요는 없다.

일반적인 Linux 서버 운영에서는 SSH가 준비되어 있다면 **SFTP**를 우선 검토할 수 있다.

```text
SSH
├─ 원격 Shell
└─ SFTP 파일 전송
```

SFTP는 SSH 기반이므로 별도의 평문 FTP 계정을 운영하는 것보다 접근통제와 운영 단순성 측면에서 유리한 경우가 많다.

VOC 관점에서도 다음 문제를 미리 정의해야 한다.

- 접속은 되지만 업로드가 안 됨
- Permission denied
- 경로를 찾지 못함
- 업로드 성공했지만 서비스에서 파일이 안 보임
- 파일 소유권이 달라 Application이 읽지 못함
- 용량 제한 초과

즉 파일전송 기능도 `접속 성공`만 테스트할 것이 아니라 **업로드 → 저장 → 권한 → Application 조회 → 백업**까지 End-to-End로 확인해야 한다.

## 19. HTTPS·Domain·OAuth는 하나의 흐름으로 본다

OAuth 로그인에서는 다음 요소가 서로 연결된다.

```text
Domain
↓
DNS
↓
HTTPS
↓
Redirect URI
↓
OAuth Provider
↓
Callback
↓
Application Session / Token 처리
```

따라서 OAuth 오류를 단순 로그인 기능 오류라고 보면 안 된다.

가능한 원인:

- Redirect URI 불일치
- HTTP/HTTPS 차이
- Domain 변경
- Callback Path 오류
- Client 설정 오류
- Session/Cookie 설정
- Reverse Proxy Header 문제

실제 OAuth Client ID, Client Secret, Callback 운영주소 등은 공개 TIL에서 `***`로 마스킹한다.

## 20. 신생회사가 놓치기 쉬운 VOC 운영 포인트

오늘 정리한 내용 중 특히 초기 회사에서 누수되기 쉬운 항목은 다음과 같다.

1. 고객센터에 연락한 사람만 VOC로 본다.
2. VOC 절대 건수만 보고 분모를 보지 않는다.
3. 고객 증상과 Root Cause를 같은 것으로 저장한다.
4. `기타` 카테고리가 너무 커진다.
5. 반복 수동처리를 정상 운영으로 받아들인다.
6. 상담 Macro가 Product 문제를 숨긴다.
7. 문의 감소를 무조건 개선으로 해석한다.
8. Silent Churn을 보지 않는다.
9. VOC와 Release/Incident를 연결하지 않는다.
10. 금전 피해 VOC와 일반 UX 문의를 같은 우선순위 체계로 본다.
11. Owner와 Due Date가 없다.
12. 수정 후 VOC가 실제로 감소했는지 확인하지 않는다.
13. CS·개발·재무가 서로 다른 ID로 같은 사건을 관리한다.
14. 운영자가 어떤 관리자 기능을 반복 사용하는지 측정하지 않는다.
15. 재문의율을 보지 않고 처리시간만 본다.

## 21. 앞으로 기능을 볼 때 적용할 VOC 체크리스트

새 기능이나 시스템을 설계할 때 다음 순서로 검토한다.

```text
1. 정상 Flow는 무엇인가?
2. 예외 Flow는 무엇인가?
3. 고객은 실패를 어떻게 표현할까?
4. 고객이 말하지 않고 이탈할 지점은 어디인가?
5. VOC가 수집되지 않는 지점은 어디인가?
6. 운영자가 수동으로 처리할 작업은 무엇인가?
7. Root Cause 확인에 필요한 데이터가 저장되는가?
8. 개발팀이 재현할 수 있는가?
9. 모니터링과 Alert가 있는가?
10. 금전·이탈·고객영향을 측정할 수 있는가?
11. Incident/Release와 연결할 수 있는가?
12. 수정 후 효과를 검증할 수 있는가?
```

## 22. 오늘의 결론

오늘 가장 중요한 학습은 **코딩을 잘하는 것만으로 좋은 서비스를 만들 수 없다는 것**이다.

개발자는 코드의 성공 여부를 볼 수 있지만 고객은 서비스 경험 전체를 본다.

따라서 다음 연결을 할 수 있어야 한다.

```text
고객 불편
↓
VOC
↓
데이터
↓
Root Cause
↓
업무 정책
↓
개발 요구사항
↓
운영도구
↓
모니터링
↓
재발방지
```

> **좋은 VOC 운영은 문의를 잘 처리하는 것이 아니라, 반복되는 고객 문제를 회사의 시스템과 제품에서 제거하는 과정이다.**

앞으로 서버·DB·결제·인증·파일업로드·배포 같은 기술을 공부할 때도 `기능이 동작하는가?`에서 끝내지 않고 **어떤 VOC가 발생할 수 있는가, 어떤 데이터가 있어야 원인을 찾을 수 있는가, 운영자가 무엇을 해야 하는가, 어떤 부분을 자동화해야 하는가**까지 함께 설계해야 한다.
