## 4조 시스템 모듈 재정의

오늘 요구사항을 기능이 아니라 책임 기준으로 나누면 다음 7개 모듈로 정리할 수 있다.

| 모듈 | 주요 책임 | 구분 |
|---|---|---|
| 공통정보 | 회원, 학생, 팀, 팀원 | 기존 확장 |
| 평가 | 상호평가, 객관평가, 팀평가, 종합평가 | 기존 확장 |
| 과제/시험 | 과제 생성, 개인/팀 과제, 시험정보, 점수 | 신규 |
| 팀편성 | 자동 팀배정, NEW-FACE | 기존 확장 |
| 근태 | 출석/출근 체크, 당일 출석 기록 | 신규 |
| 얼굴인식 | 얼굴 등록, 인식, 출석사진 저장 | 신규 |
| Integration | 타조 API, Slack 초대/알림 | 신규 |

이렇게 모듈을 나누면 각 조원이 기능 하나만 보는 것이 아니라 **자신이 맡은 모듈이 어떤 데이터와 API에 영향을 주는지** 확인할 수 있다.

## 1. 공통정보 모듈

1조와 회원정보, 학생정보, 팀정보를 공유해야 한다.

가장 먼저 협의해야 할 것은 데이터의 주인이 누구인지이다.

예를 들어 1조와 4조가 학생 정보를 각각 독립적으로 관리하면 다음과 같은 문제가 생길 수 있다.

```text
1조 Student
student_id = 10
team_id = 2

4조 Student
student_id = 31
team_id = 3
```

같은 학생이 시스템마다 다른 ID와 팀을 가지면 평가 결과를 합칠 수 없다.

따라서 공통 식별자를 먼저 맞춰야 한다.

```text
user_id
student_id
team_id
course_id
assessment_id
```

그리고 각 데이터마다 Master Data Owner를 정해야 한다.

예:

```text
회원정보 → 1조가 원본 관리 / 4조는 참조
팀정보   → 협의 후 원본 결정
평가결과 → 4조 관리
```

## 2. 평가 모듈

기존 4조의 중심 기능은 상호평가였다.

```text
상호평가
├─ 팀 평가
└─ 개인 평가
```

오늘 요구사항에서는 시험·과제 등의 객관적 평가가 추가되었다.

```text
평가
├─ 상호평가
│  ├─ 팀 평가
│  └─ 개인 평가
│
├─ 객관평가
│  ├─ 시험
│  └─ 과제
│
└─ 종합평가
   └─ 상호평가 + 객관평가
```

따라서 기존 `TeamEvaluation`, `PeerEvaluation`만 생각할 것이 아니라 평가 전체를 감싸는 상위 구조가 필요한지 검토해야 한다.

핵심 질문은 다음이다.

> 시험 점수, 과제 점수, 상호평가 점수를 어떤 기준으로 합산해서 최종 팀평가 결과를 만들 것인가?

이 계산 기준이 확정되어야 DB 구조와 집계 함수도 설계할 수 있다.

## 3. 과제 / 시험 모듈

신규 요구사항에는 개인 과제와 팀 과제 관리가 포함된다.

```text
과제 생성
    ↓
대상 지정
├─ 개인
└─ 팀
    ↓
제출 / 점수
    ↓
평가 결과 반영
```

시험정보도 향후 다른 조에서 전달받을 수 있으므로, 과제와 시험을 기존 상호평가 테이블에 억지로 넣기보다 별도 도메인으로 관리하는 것이 필요하다.

신규 Entity 후보:

```text
Assignment
AssignmentSubmission
Exam
ExamResult
AssessmentResult
```

아직 확정 테이블은 아니며 ERD 검토 후 결정해야 한다.

## 4. 팀편성 모듈 - NEW-FACE

기존 자동 팀배정 기능에 `NEW-FACE` 모드 요구사항이 추가되었다.

NEW-FACE의 목적은:

> 이전에 같은 팀을 했던 사람보다 한 번도 같은 팀을 하지 않았던 사람을 우선해서 새로운 팀을 만드는 것.

이 기능은 현재 팀 정보만으로는 구현할 수 없다.

과거 팀편성 기록이 필요하다.

```text
학생 목록
   ↓
과거 팀편성 이력 조회
   ↓
학생 A-B가 과거 같은 팀이었는지 확인
   ↓
같은 팀 경험이 없는 조합 우선
   ↓
팀 생성
```

조건을 만족하는 팀을 만들 수 없다면 예외 처리도 필요하다.

```text
NEW-FACE 조건으로 팀을 구성할 수 없습니다.
```

따라서 기존 `Team`, `TeamMember` 외에 팀편성 이력을 별도 관리할지 검토해야 한다.

신규 후보:

```text
TeamFormationHistory
```

```text

   ↓

   ↓

```

근태 데이터와 얼굴인식 기능은 서로 연결되지만 같은 책임은 아니다.

따라서 `Attendance`와 얼굴인식 기능은 분리하는 것이 좋다.

신규 Entity 후보:

```text
Attendance
AttendanceImage
```

## 6. 얼굴인식 모듈

교수님 요구사항의 목표 흐름은 다음과 같다.

```text
학생 얼굴 등록
   ↓
카메라에서 얼굴 감지
   ↓
누구인지 식별
   ↓
"OOO님 안녕하세요"
   ↓
출석 처리
   ↓
당일 사진 저장
```

딥러닝 테스트를 위해 출석한 학생들의 사진 데이터도 남겨야 한다.

얼굴인식은 난도가 높기 때문에 한 번에 구현하기보다 단계적으로 나누는 것이 안전하다.

```text
1단계: 사진 촬영 + 출석 기록
2단계: 얼굴 Detection
3단계: 얼굴 Identification
4단계: 자동 출석 처리
```

신규 Entity 후보:

```text
FaceProfile
AttendanceImage
```

주의할 점은 얼굴 이미지나 임베딩을 Student 테이블에 직접 섞기보다 별도 테이블로 분리하는 것이다.

## 7. Integration 모듈

### 1·2·3조 데이터 연동

교수님은 1·2·3조에서 발생한 평가 결과를 4조 데이터로 취합할 수 있을지 검토하도록 했다.

개념적으로는 다음 구조가 된다.

```text
1조 ─┐
2조 ─┼─→ Integration Layer ─→ 4조 평가 데이터
3조 ─┘
```

다른 조의 DB 테이블을 직접 참조하기보다 API를 통해 데이터를 전달받는 구조가 변경에 더 안전하다.

이번 주말 각 조 ERD 초안이 나오면 다음 항목을 맞춰야 한다.

```text
공통 ID
Entity 관계
데이터 소유권
API Request / Response
평가결과 전달 규칙
```

### Slack API

팀배정이나 대상자 목록을 기준으로 Slack 초대 또는 알림을 보낼 수 있는 공통 함수를 모듈화해야 한다.

개념 예시:

```python
invite_users(target_users)
```

호출하는 기능에서는 대상자 리스트만 전달하고, 실제 Slack API 호출 로직은 Integration 모듈 내부에서 처리하는 방식이다.

```text
팀배정 완료
   ↓
대상 학생 리스트
   ↓
Slack Integration
   ↓
초대 / 알림
```

이렇게 하면 팀편성, 평가, 과제 등 여러 기능에서 같은 Slack 로직을 재사용할 수 있다.

요구사항이 들어왔다고 바로 ERD나 코드를 수정하면 안 된다.

먼저 다음 순서로 확인해야 한다.

```text
교수님 요구사항
    ↓
Business Requirement
    ↓
Impact Analysis
    ↓
Domain / Module
    ↓
Entity
    ↓
API Interface
    ↓
ERD
    ↓
Issue
    ↓
개발
```

특히 여러 서비스가 연결되는 프로젝트에서는 **어떤 데이터를 누가 소유하는지와 어떤 인터페이스로 전달하는지**가 먼저 정해져야 한다.
