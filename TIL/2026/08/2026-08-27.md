# TIL | 기존 시스템을 이해하기 위한 ERD 분석과 통합 방법

## 오늘의 학습 주제

오늘은 새로운 기능을 만드는 것보다 먼저 해야 하는 일인 **기존 시스템의 구조를 이해하는 방법**에 대해 많이 고민했다.

특히 여러 팀에서 만든 기능을 하나의 시스템에 통합해야 하는 상황에서, ERD를 단순히 테이블 그림으로 보는 것이 아니라 **기능과 데이터의 관계를 파악하는 설계도**로 읽는 방법을 학습했다.

---

## 1. ERD를 볼 때 가장 먼저 해야 하는 것

처음 ERD를 보면 테이블과 선이 너무 많아서 어디부터 읽어야 할지 막막했다.

처음에는 테이블 하나하나의 컬럼을 전부 이해하려고 했는데, 오히려 전체 구조가 더 보이지 않았다.

그래서 ERD를 볼 때는 다음 순서로 접근하는 것이 훨씬 효과적이라는 것을 알게 되었다.

### 1단계. 핵심 엔티티 찾기

먼저 시스템에서 중심이 되는 테이블을 찾는다.

예를 들면 다음과 같은 데이터들이다.

- 사용자
- 팀
- 프로젝트
- 과제
- 평가
- 출석
- 문서

핵심 테이블을 먼저 찾으면 시스템이 무엇을 관리하는 프로그램인지 대략적인 구조가 보이기 시작한다.

---

## 2. 관계선은 양쪽을 모두 읽어야 한다

ERD에서 가장 헷갈렸던 부분은 관계선(Cardinality)이었다.

예를 들어 다음과 같은 관계가 있다고 가정한다.

```text
USER  |────○<  PARTICIPANT
```

이 관계를 한쪽 방향으로만 읽으면 이해하기 어렵다.

양쪽에서 읽어보면 훨씬 쉽다.

### USER → PARTICIPANT

한 명의 USER는 0개 이상의 PARTICIPANT 정보를 가질 수 있다.

### PARTICIPANT → USER

하나의 PARTICIPANT는 반드시 한 명의 USER와 연결된다.

즉 ERD 관계는

> "A가 B를 몇 개 가질 수 있는가?"

그리고 반대로

> "B 하나는 A 몇 개와 연결되는가?"

두 방향으로 읽는 것이 중요하다.

---

## 3. 테이블 이름보다 먼저 '왜 존재하는 테이블인지' 생각하기

ERD를 분석하면서 가장 크게 느낀 점은 **컬럼을 먼저 보는 것보다 테이블의 존재 이유를 먼저 정의해야 한다는 것**이었다.

예를 들어 출석 관련 테이블이 있다고 하더라도 모든 출석이 같은 의미는 아니다.

```text
학습 출석
게임 참여
일일 퀘스트 참여
교육 과정 출석
과제 제출 여부
```

겉으로 보면 모두 사용자의 활동 기록처럼 보이지만 업무적으로는 목적이 다를 수 있다.

따라서 이름이 비슷하다고 무조건 하나의 테이블로 합치면 안 된다.

반대로 이름은 다르더라도 실제 역할과 데이터가 거의 같다면 통합 후보가 될 수 있다.

---

## 4. 여러 ERD를 통합할 때 사용한 기준

여러 시스템의 ERD를 하나로 합칠 때는 테이블을 크게 세 가지로 분류할 수 있다.

| 구분 | 판단 기준 | 처리 방법 |
|---|---|---|
| 유지 | 기존 시스템의 핵심 기능 | 기존 구조 우선 |
| 통합 | 기능과 데이터 의미가 거의 동일 | 하나의 구조로 통합 |
| 분리 | 이름은 비슷하지만 업무 목적이 다름 | 별도 테이블 유지 |

여기서 중요한 원칙은 **기존 운영 시스템을 기준점으로 잡는 것**이다.

새로운 기능 때문에 기존 데이터 구조를 전부 변경하면 영향 범위가 너무 커질 수 있다.

따라서 다음 순서가 더 안전하다.

```text
기존 ERD
    ↓
기존 기능 파악
    ↓
새로운 ERD 비교
    ↓
중복 기능 확인
    ↓
통합 가능 여부 판단
    ↓
필요한 테이블만 추가
```

---

## 5. ERD 통합은 결국 '업무 기능 비교'다

처음에는 ERD 통합을 단순히 테이블을 합치는 작업이라고 생각했다.

하지만 오늘 분석하면서 생각이 바뀌었다.

ERD 통합의 핵심은 사실 **각 시스템이 어떤 업무를 처리하고 있는지 비교하는 작업**에 더 가깝다.

예를 들어 두 시스템에 다음 테이블이 있다고 하자.

```text
SYSTEM A
- attendance
- mission
- participant

SYSTEM B
- attendance
- assignment
- user
```

단순히 이름만 보면 `attendance`가 같기 때문에 합치고 싶어진다.

하지만 실제 업무를 확인해보면

```text
SYSTEM A attendance
→ 게임 미션 참여 기록

SYSTEM B attendance
→ 교육 과정 출석 기록
```

일 수도 있다.

이 경우 데이터의 의미가 다르기 때문에 분리해서 관리하는 것이 더 적절하다.

---

## 6. 테이블 비교 시 체크해야 할 항목

앞으로 여러 ERD를 비교할 때는 다음 기준으로 정리하면 좋을 것 같다.

1. 이 테이블이 어떤 기능을 지원하는가?
2. 누구의 데이터를 저장하는가?
3. 어떤 행동을 했을 때 데이터가 생성되는가?
4. 어떤 테이블과 연결되는가?
5. 기존 시스템에서 이미 같은 역할을 하는 테이블이 있는가?
6. 통합 시 기존 API나 화면에 어떤 영향이 있는가?

---

## 7. ERD만 보고 결정하면 안 되는 이유

ERD는 데이터 구조를 보여주지만 **기능의 전체 흐름까지 설명해주지는 않는다.**

따라서 ERD를 분석할 때는 가능하면 다음 자료를 함께 봐야 한다.

```text
요구사항
   ↓
기능
   ↓
화면/API
   ↓
ERD
   ↓
실제 데이터
```

예를 들어 테이블 이름만 보고 기능을 추측했는데 실제 요구사항을 확인하면 전혀 다른 목적으로 사용되고 있을 수도 있다.

그래서 ERD 분석은 다른 산출물과 함께 진행해야 한다.

---

## 8. 기존 시스템을 인수받았을 때의 분석 순서

오늘 내용을 기준으로 기존 시스템을 인수받았을 때의 분석 순서를 정리해봤다.

### STEP 1. 시스템의 주요 기능을 나눈다.

회원, 팀, 프로젝트, 평가, 출석, 과제, 문서, 알림처럼 기능 단위로 먼저 분리한다.

### STEP 2. 기능별 관련 테이블을 찾는다.

`기능 → 테이블` 형태로 연결한다.

### STEP 3. 테이블 관계를 확인한다.

PK와 FK를 기준으로 데이터가 어떤 방향으로 연결되는지 확인한다.

### STEP 4. 새로운 시스템의 ERD와 비교한다.

- 기존에 있는 기능인가?
- 새로 추가되는 기능인가?
- 비슷하지만 목적이 다른 기능인가?

를 구분한다.

### STEP 5. 유지 / 통합 / 분리 / 신규로 분류한다.

이 단계부터 실제 통합 ERD의 방향이 결정된다.

---

## 9. 오늘 가장 크게 배운 점

오늘 가장 크게 배운 것은 ERD를 잘 읽는 것이 단순히 PK, FK와 관계선을 읽을 줄 아는 것만을 의미하지 않는다는 점이다.

ERD를 제대로 분석하려면

```text
업무 요구사항
+
기능
+
데이터
+
테이블 관계
+
기존 시스템 영향도
```

를 함께 봐야 한다.

특히 기존 시스템을 이어받는 프로젝트에서는 새로운 구조를 만드는 것보다 **기존 구조를 최대한 유지하면서 필요한 기능을 확장하는 판단**이 중요하다는 것을 알게 되었다.

---

## 오늘의 한 줄 정리

> **ERD 통합은 테이블을 합치는 작업이 아니라, 기존 시스템의 업무와 데이터 의미를 이해한 뒤 무엇을 유지하고 무엇을 분리할지 결정하는 과정이다.**

## 다음 학습 목표

다음에는 ERD 분석에서 한 단계 더 나아가

```text
요구사항
→ 기능
→ 화면/API
→ 테이블
→ 테스트
```

가 어떻게 연결되는지 정리해보고 싶다.

이 연결 관계를 이해하면 ERD를 단순한 데이터베이스 그림이 아니라 **전체 시스템을 추적할 수 있는 설계 문서**로 활용할 수 있을 것 같다.
