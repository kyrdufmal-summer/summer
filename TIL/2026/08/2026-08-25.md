# 2026-08-25 TIL

## 오늘 배운 것

오늘은 Django 프로젝트를 이어받아 **프로덕션과 유사한 데이터를 로컬 DB에 구성하는 흐름**을 정리했다.

처음에는 "SQL 파일을 DBeaver에서 열면 DB가 생기는 것인가?", "Django는 지금 SQLite를 보는가 PostgreSQL을 보는가?", "왜 CMD에서 이 명령을 치는가?"가 각각 따로 느껴졌지만, 작업을 진행하면서 결국 하나의 연결 구조라는 것을 이해했다.

핵심은 다음과 같다.

> **Django 코드 → DB 접속 설정 → 로컬 PostgreSQL → 전달받은 SQL 데이터 → DBeaver로 확인**

단순히 명령어를 따라 치는 것이 아니라, **현재 애플리케이션이 어느 DB를 바라보고 있는지 확인하고, 그 DB 안에 필요한 구조와 데이터를 복원하는 과정**이라는 점이 가장 중요했다.

---

## 1. 먼저 정의: "DB를 로컬로 띄운다"는 무슨 뜻인가?

처음에는 "DB를 띄운다"를 프로그램 하나를 실행하는 것으로 생각하기 쉬웠다.

하지만 실제 의미는 다음 세 가지가 모두 준비되어야 한다는 것이다.

1. **DBMS(PostgreSQL)가 내 PC에서 실행되고 있어야 한다.**
2. **프로젝트가 그 PostgreSQL에 접속하도록 설정되어 있어야 한다.**
3. **필요한 테이블과 데이터가 로컬 DB 안에 들어 있어야 한다.**

즉 DBeaver는 DB 자체가 아니다.

- **PostgreSQL**: 실제 데이터를 저장하고 SQL을 처리하는 DBMS
- **DBeaver**: PostgreSQL 내부를 눈으로 보고 SQL을 실행하기 위한 GUI 도구
- **Django**: 설정된 접속 정보로 PostgreSQL에 SQL을 보내는 애플리케이션
- **SQL 파일**: DB의 테이블 구조와 데이터를 다시 만들어 넣을 수 있는 SQL 명령 모음

구조를 그림으로 정리하면 다음과 같다.

```text
Django
  │
  │ DB 설정(settings.py / 환경변수)
  ▼
PostgreSQL (내 PC)
  │
  ├─ 테이블
  └─ 데이터
       ▲
       │ SQL 파일 실행
       │
    DBeaver
```

---

## 2. 왜 먼저 Django의 DB 설정을 확인했는가?

프로젝트를 전달받았다고 해서 무조건 PostgreSQL을 사용하는 것은 아니다.

Django는 `settings.py`의 `DATABASES` 설정에 따라 SQLite, PostgreSQL 등 서로 다른 DB를 사용할 수 있다.

그래서 가장 먼저 해야 할 일은:

> **"현재 이 프로젝트의 코드가 어떤 DB backend를 사용하도록 작성되어 있는가?"**

를 확인하는 것이다.

오늘 사용한 명령어:

```cmd
findstr /S /I "django.db.backends" *.py
```

### 명령어를 왜 쳤는가?

이 명령의 목적은 프로젝트 전체 Python 파일에서 `django.db.backends`라는 문자열을 검색하는 것이었다.

- `findstr` : Windows에서 파일 내부 문자열 검색
- `/S` : 현재 폴더뿐 아니라 하위 폴더까지 검색
- `/I` : 대소문자를 구분하지 않고 검색
- `"django.db.backends"` : 찾으려는 문자열
- `*.py` : Python 파일만 검색

즉 사람 눈으로 폴더를 하나씩 열어보는 대신, **프로젝트 전체에서 DB 설정이 존재하는 위치를 빠르게 찾기 위한 명령어**다.

검색 결과에서 PostgreSQL backend와 SQLite 관련 설정이 함께 확인되었다.

```text
django.db.backends.postgresql
django.db.backends.sqlite3
```

여기서 배운 점은 **코드에 PostgreSQL이라는 문자열이 있다고 해서 실제 실행 시 무조건 PostgreSQL을 쓰는 것은 아니라는 것**이다.

최종적으로는 `settings.py`, 환경변수, 실행 환경에 따라 실제 DB 연결 대상이 결정된다.

## 3. CMD 명령어를 치는 이유: "프로그램을 실행"하는 것보다 "현재 상태를 확인"하기 위해서다

오늘 CMD/터미널 명령어를 보면서 가장 크게 바뀐 생각이다.

예전에는 명령어를 그냥 "외워서 실행하는 코드"처럼 생각했다.

하지만 실제 개발에서는 대부분 다음 질문에 답하기 위해 명령어를 친다.

```text
나는 지금 어느 폴더에 있는가?
프로젝트 설정 파일은 어디에 있는가?
어느 DB를 사용하도록 되어 있는가?
가상환경이 활성화되어 있는가?
필요한 프로그램과 패키지가 설치되어 있는가?
애플리케이션과 DB가 실제로 연결되는가?
```

따라서 명령어 자체보다 **"이 명령으로 어떤 상태를 확인하려는가?"**를 먼저 정의하는 습관이 중요하다.

## 4. 전달받은 SQL 파일의 의미

팀에서 전달받은 SQL 파일은 단순한 문서 파일이 아니다.

SQL 파일에는 상황에 따라 다음과 같은 명령이 들어 있을 수 있다.

```sql
CREATE TABLE ...;
INSERT INTO ...;
ALTER TABLE ...;
```

즉 SQL 파일을 로컬 PostgreSQL에 실행하면 DB의 구조와 데이터를 재현할 수 있다.

오늘 전달받은 데이터는 **로컬에서 운영 환경과 유사한 상태를 만들어 기능을 검증하기 위한 목적**으로 이해했다.

중요한 점은 다음이다.

> SQL 파일을 가지고 있는 것과 DB에 SQL 파일의 내용이 실제 반영된 것은 완전히 다른 상태다.

파일을 다운로드했다고 해서 데이터가 자동으로 PostgreSQL에 들어가는 것이 아니다.

```text
SQL 파일 보유
   ↓
PostgreSQL 연결
   ↓
대상 DB 선택
   ↓
SQL 실행
   ↓
테이블 및 데이터 생성
   ↓
DBeaver에서 확인
```

## 5. DBeaver의 역할을 다시 정의

DBeaver를 처음 보면 "DB 프로그램"처럼 보이지만 정확하게는 **DB Client**이다.

DBeaver 자체에 서비스 데이터가 저장되는 것이 아니라, PostgreSQL 서버에 접속해서 내부를 보여준다.

예를 들어 DBeaver에서 다음 정보를 이용해 연결한다.

```text
Host     : localhost
Port     : PostgreSQL 포트
Database : [LOCAL_DB_NAME]
Username : [LOCAL_DB_USER]
Password : ********
```

> 비밀번호, 실제 계정명, 운영 DB 주소 등 민감 정보는 TIL과 Git 저장소에 기록하지 않는다.

연결이 완료되면 DBeaver는 PostgreSQL에 있는:

- Database
- Schema
- Table
- Column
- Row

등을 GUI로 확인할 수 있게 해준다.

## 6. 로컬 DB를 구성하는 전체 메커니즘

오늘 작업을 기능 단위가 아니라 **데이터가 흐르는 방향**으로 다시 정리하면 다음과 같다.

### STEP 1. 프로젝트 코드를 받는다

프로젝트 코드에는 Django 애플리케이션과 DB 연결 설정이 들어 있다.

하지만 **코드만 받았다고 데이터까지 함께 오는 것은 아니다.**

---

### STEP 2. 프로젝트가 어떤 DB를 바라보는지 찾는다

```cmd
findstr /S /I "django.db.backends" *.py
```

이 단계에서 확인하려는 것은:

> Django가 SQLite를 쓰는가, PostgreSQL을 쓰는가?

이다.

---

### STEP 3. 로컬 PostgreSQL을 준비한다

내 PC에서 실행되는 PostgreSQL은 운영 서버의 PostgreSQL과 별개의 DB 서버다.

```text
운영 PostgreSQL
    ≠
내 PC PostgreSQL
```

따라서 로컬 개발자는 자신의 PC에 별도의 DB 환경을 구성해야 한다.

이렇게 해야 운영 DB를 직접 건드리지 않고 안전하게 개발과 테스트를 할 수 있다.

---

### STEP 4. 전달받은 SQL을 로컬 DB에 반영한다

SQL 파일에 포함된 스키마와 데이터를 로컬 PostgreSQL에서 실행한다.

결과적으로 로컬에서도 필요한 테이블과 데이터를 사용할 수 있게 된다.

```text
전달받은 SQL
    ↓
Local PostgreSQL
    ↓
테이블 + 데이터 생성
```

---

### STEP 5. DBeaver에서 결과를 확인한다

SQL 실행 후에는 실제로 다음을 확인해야 한다.

- 테이블이 생성되었는가?
- 데이터가 들어왔는가?
- 예상한 스키마에 들어갔는가?
- PK/FK 등 관계가 존재하는가?

즉 **실행 성공 메시지만 믿지 않고 실제 DB 상태를 검증하는 과정**이 필요하다.

---

### STEP 6. Django가 같은 DB를 바라보도록 연결한다

마지막으로 Django의 DB 접속 설정과 내가 구성한 PostgreSQL의 정보가 일치해야 한다.

개념적으로는 다음 정보가 맞아야 한다.

```text
ENGINE   → PostgreSQL
HOST     → 로컬 DB 주소
PORT     → 로컬 PostgreSQL 포트
NAME     → 내가 만든 DB
USER     → 로컬 DB 사용자
PASSWORD → 로컬 DB 비밀번호
```

이 중 비밀번호나 실제 운영 정보는 Git에 올리지 않고 `.env` 같은 환경변수 파일로 분리한다.

## 7. 오늘 가장 헷갈렸던 부분

### 1) DBeaver가 DB라고 생각하기 쉬웠다

정확히는:

```text
PostgreSQL = DB 서버
DBeaver    = DB 서버를 관리하는 클라이언트
```

이다.

### 2) SQL 파일을 받으면 DB가 완성된다고 생각하기 쉬웠다

SQL 파일은 **실행해야 하는 명령들의 묶음**이다.

따라서:

```text
SQL 파일 다운로드 ≠ DB 복원 완료
```

이다.

### 3) 프로젝트 코드와 DB 데이터는 별개다

Git에서 코드를 받아도 운영 DB의 데이터가 자동으로 따라오지 않는다.

```text
Git Repository → Source Code
DB             → Data
```

따라서 협업 프로젝트에서는 코드 전달과 DB 전달 전략을 별도로 가져가야 한다.

### 4) CMD 명령어를 외우려고 했다

앞으로는 명령어를 보기 전에 먼저:

> **"지금 내가 확인하려는 상태가 무엇인가?"**

를 정의한다.

`findstr`도 단순히 외워야 할 명령이 아니라 **DB 설정의 위치를 찾기 위한 검색 수단**이었다.

## 8. 보안 관점에서 반드시 지켜야 할 것

DB를 로컬로 구성할 때 다음 정보는 GitHub에 직접 커밋하지 않는다.

```text
DB_PASSWORD
실제 운영 DB HOST
운영 계정 ID
API KEY
SECRET_KEY
OAuth Secret
개인 이메일/전화번호
실제 사용자 개인정보
```

예시는 반드시 다음처럼 마스킹한다.

```env
DB_NAME=[LOCAL_DB_NAME]
DB_USER=[LOCAL_DB_USER]
DB_PASSWORD=********
DB_HOST=localhost
DB_PORT=[PORT]
```

특히 `.env` 파일은 `.gitignore`에 포함되어 있는지 확인해야 한다.

공유가 필요한 경우 실제 값이 없는 `.env.example`을 사용한다.

## 9. 실무에서는 왜 운영 DB를 복사해 로컬에서 확인하는가?

개발자가 운영 DB에 직접 연결해서 기능을 개발하는 것은 위험하다.

잘못된 SQL 한 줄로 실제 데이터를 수정하거나 삭제할 수 있기 때문이다.

따라서 일반적으로는 환경을 분리한다.

```text
Local
  ↓ 개발자 개인 개발

Development / Test
  ↓ 팀 통합 테스트

Staging
  ↓ 운영 직전 검증

Production
  ↓ 실제 서비스
```

오늘 구성한 로컬 DB의 핵심 목적도 **운영 환경을 직접 건드리지 않고 비슷한 데이터 구조에서 기능을 테스트하기 위한 것**이다.

단, 실제 운영 데이터를 로컬로 가져올 경우 개인정보와 민감 데이터는 반드시 비식별화/마스킹되어야 한다.

## 10. 오늘 이해한 전체 흐름

```text
[프로젝트 코드]
      │
      │ DB backend 확인
      ▼
[settings.py / 환경변수]
      │
      │ 접속 정보
      ▼
[Local PostgreSQL]
      ▲
      │ SQL 실행
      │
[전달받은 SQL 파일]
      │
      ▼
[DBeaver로 구조/데이터 확인]
      │
      ▼
[Django 실행 및 기능 테스트]
```

결국 오늘 한 일은 단순히 "DB를 설치했다"가 아니다.

> **전달받은 Django 프로젝트가 어떤 DB를 바라보는지 추적하고, 로컬 PostgreSQL에 필요한 구조와 데이터를 구성한 뒤, DBeaver로 검증하여 애플리케이션이 안전한 로컬 환경에서 동작할 수 있도록 만드는 과정**이었다.
