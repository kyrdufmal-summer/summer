## 1. 핵심 결론

오늘은 FastAPI에서 API 계약을 이해하고, PostgreSQL 조회 결과를 JSON으로 반환하는 흐름과 Swagger 검증 방법을 학습했다. GitHub에 과제 소스코드를 제출할 때 필요한 파일 범위와 Git 명령의 역할도 검토했다. 추가로 AI 서비스 기획에서 정책·규제·고객 문제를 근거로 가설을 검증하는 방법을 논의했다.

**API가 실행된 것, 데이터가 올바른 것, GitHub에 제출된 것은 서로 다른 검증 대상이다.**

## 2. 문제 정의: 왜 DB 연동이 필요한가?

초기 API 실습에서는 Python 리스트를 임시 데이터로 사용할 수 있다. 하지만 실제 서비스는 데이터를 지속적으로 저장하고 여러 요청에서 일관되게 읽어야 한다. PostgreSQL 같은 DBMS를 사용하면 이러한 요구를 다룰 수 있다.

학습한 기본 흐름:

1. 클라이언트가 `GET /members` 요청을 보낸다.
2. FastAPI 엔드포인트가 요청을 받아 조회 로직을 실행한다.
3. DB 접근 코드가 PostgreSQL에서 회원 데이터를 조회한다.
4. 응답 모델(Pydantic)을 통해 반환 데이터의 구조를 검증·변환한다.
5. HTTP 상태 코드와 JSON 본문을 클라이언트에 전달한다.

이는 **개념적 흐름**이다. 실제 구현의 함수명과 계층 분리는 코드에 따라 달라질 수 있다.

## 3. API Contract와 Response Model

API Contract는 서버와 클라이언트 사이의 약속이다. HTTP 메서드, URL, 입력, 검증 규칙, 성공·실패 상태 코드, 응답 구조 등을 포함한다.

Pydantic 응답 모델은 그 약속 중 **응답 데이터의 필드와 타입**을 표현한다.

```python
# 설명용 예시: 당일 실행 증거가 있는 코드가 아님
from pydantic import BaseModel

class MemberResponse(BaseModel):
    id: int
    name: str
    email: str
```

예를 들어 프론트엔드가 `id`, `name`, `email`을 기대하는데 서버가 다른 이름의 필드를 반환하면 화면 처리에 문제가 생길 수 있다. DB 컬럼명과 API 필드명을 다르게 운영할 수는 있지만, 그때는 명시적 변환이 필요하다.

**검증 기준:** Swagger 응답의 필드명·타입·상태 코드를 API 계약과 대조한다.

공식 참고: https://fastapi.tiangolo.com/tutorial/response-model/

## 4. DB 조회 결과 처리: fetchall()과 fetchone()

| 함수 | 기본 의미 | 사용 예 |
|---|---|---|
| `fetchall()` | 조회 결과의 남은 행 전체를 가져옴 | 회원 목록 |
| `fetchone()` | 조회 결과의 다음 행 하나를 가져옴 | 회원 단건 또는 INSERT RETURNING 결과 |

함수를 바꾸는 것만으로 API 오류가 해결되지는 않는다. SQL의 반환 컬럼, 결과 자료형, 응답 모델을 함께 확인해야 한다.

### 컬럼명 불일치 문제

학습 대화에서는 `member_id`와 `id`처럼 DB 조회 컬럼명과 API 필드명이 다를 수 있는 상황을 검토했다.

가능한 원인은 다음과 같다.

- SQL이 실제 테이블에 없는 컬럼을 조회함
- SQL 결과의 필드명과 응답 모델 필드명이 다름
- 조회 결과를 모델에 맞게 변환하지 않음

**권장 해결 순서:** 실제 테이블 스키마 확인 → SQL 결과 확인 → Python 반환값 확인 → Swagger 응답 확인.

이 내용은 오류 분석 원칙을 정리한 것이며, 특정 DB 수정이 최종 성공했다고 주장하지 않는다.

## 5. HTTP 상태 코드와 Swagger

| 코드 | 의미 | 학습 사례 |
|---|---|---|
| 200 | 요청 처리 성공 | 회원 목록 조회 |
| 201 | 새 자원 생성 성공 | 회원 등록 |
| 404 | 요청한 자원을 찾을 수 없음 | 존재하지 않는 회원 |
| 422 | 요청 데이터가 API 검증 규칙을 충족하지 않음 | 잘못된 입력값 |

Swagger UI는 API의 요청 형식과 응답을 확인하고 실제 HTTP 요청을 보내볼 수 있는 화면이다. Swagger에서 200이 표시되더라도 반환된 값이 실제 DB와 일치하는지까지 자동으로 보장하지는 않는다.

### 당일 학습에서 확인된 범위

이전 대화에서 `GET /members`에 대해 **HTTP 200과 회원 목록 JSON 응답을 화면에서 확인했다고 정리한 기록**이 있다. 이번 TIL 작성 시 서버를 재실행하거나 원본 HTTP 로그를 별도로 확보하지 않았으므로 독립 재검증 완료로 표기하지 않는다.

POST의 최종 201 응답, 실제 DB 저장 결과, 모든 데이터의 일치 여부는 추가 검증이 필요하다.

공식 참고: https://fastapi.tiangolo.com/tutorial/sql-databases/

## 6. GitHub 과제 제출: main.py만 올려도 되는가?

당일 대화에서는 과제의 소스코드를 GitHub에 제출할 때 `main.py`만 선택해도 되는지, Chapter 06 파일이 어디에 있는지 확인하는 문제가 있었다.

- `git add`: 커밋 대상으로 변경사항을 선택
- `git commit`: 선택한 변경사항을 로컬 Git 이력에 기록
- `git push`: 로컬 커밋을 원격 저장소로 전송

따라서 `git add` 또는 `git commit`만으로 원격 GitHub 제출이 완료되었다고 볼 수 없다.

과제에서 `main.py`만 요구한다면 해당 파일만 제출할 수 있지만, 실제 실행에 다른 모듈이 필요하면 파일 하나만으로는 실행되지 않을 수 있다. **과제의 제출 범위와 프로그램의 실행 의존성을 구분**해야 한다.

### 확인할 사항

1. 로컬에서 Chapter 06의 실제 파일 경로 확인
2. 제출 요구사항에 필요한 파일 목록 확인
3. `git status`로 추가·수정 대상 확인
4. 커밋·푸시 후 원격 브랜치에서 파일 내용 확인
5. 민감한 설정 파일과 비밀값이 포함되지 않았는지 확인

**미검증:** 당일 `main.py`가 최종적으로 원격 저장소에 제출되었다는 확정 커밋·푸시 증거는 이 기록에 없다. 경로 조회에서 파일을 찾지 못하더라도 다른 브랜치·저장소·경로에 존재할 가능성은 남는다.

공식 참고:
- https://docs.github.com/en/get-started/using-git/about-git
- https://docs.github.com/en/get-started/git-basics/ignoring-files

## 7. 장단점과 트레이드오프

| 선택 | 장점 | 한계·주의사항 |
|---|---|---|
| Python 리스트 기반 API | 시작이 간단함 | 영속적 저장과 다중 서버 공유에 한계 |
| PostgreSQL 기반 API | 데이터 저장·조회·일관성 관리 가능 | 연결·권한·스키마·SQL 관리 필요 |
| Pydantic 응답 모델 | 응답 형식 검증 및 노출 필드 제어 | 모델과 반환 데이터가 다르면 오류 |
| Swagger 수동 테스트 | 요청·응답을 즉시 확인 | 자동 회귀·동시성 테스트 대체 불가 |
| 최소 파일만 제출 | 범위가 명확하고 불필요한 파일 감소 | 필수 의존 파일 누락 가능 |

## 8. AI 서비스 기획: 비판적 사고와 근거 중심 접근

오늘은 기술 실습과 별도로 AI 서비스 아이디어의 차별화 방식을 논의했다. 특정 조직이나 비공개 기획 내용은 제외하고 **일반화한 방법론**만 남긴다.

기능을 먼저 정하기보다 다음을 검토한다.

- 고객의 문제가 실제로 반복되는가? (VOC, 인터뷰, 운영 자료)
- 손실이나 비용을 측정할 수 있는가?
- 국가별 세금·규제·표시 기준 같은 정책 제약이 있는가?
- 원인이 예측 정확도인지, 업무 절차인지, 계약 구조인지 구분했는가?
- AI가 규칙 기반 시스템보다 유리하다는 비교 근거가 있는가?
- 경쟁사가 기능을 모방해도 유지되는 운영·데이터 경쟁력이 있는가?

### 가상의 식품 유통 서비스 예시

어떤 지역에서 재고 손실이 발생한다는 가설을 세웠다면, 곧바로 AI 예측 모델을 만들기보다 손실의 원인이 수요 변동, 유통기한, 물류 절차, 현지 규정 중 무엇인지 먼저 조사해야 한다.

이는 **설명용 사례**이며 실제 국가별 세율 조사, 고객 인터뷰, 시장 검증이 완료되었다는 의미가 아니다.

## 9. 위험 요소·재발 방지

- **API 200과 데이터 정합성 혼동:** 실제 DB 행과 응답을 비교한다.
- **POST 성공과 저장 성공 혼동:** 상태 코드뿐 아니라 DB 반영 여부를 검증한다.
- **Git 로컬 커밋과 원격 제출 혼동:** 푸시 후 원격 파일을 확인한다.
- **학습 예제와 실행 증거 혼동:** 예제 코드, 실제 명령, 실제 결과를 별도로 기록한다.
- **기밀 유출:** 비밀번호·토큰·내부 주소·비공개 자료를 공개 TIL에 포함하지 않는다. `.gitignore`는 이미 커밋된 비밀정보를 과거 이력에서 삭제해 주지 않는다.
- **기획 가설과 사실 혼동:** 정책·비용·VOC 근거를 확인하기 전에는 추정으로 표시한다.
