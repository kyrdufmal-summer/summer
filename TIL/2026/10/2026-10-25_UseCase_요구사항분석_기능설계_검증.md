# TIL | Use Case로 이해하는 요구사항 분석·기능 설계·검증
- 학습일: 2026-10-25
- 작성 근거: 당일 대화의 "Usecase가 뭐야"라는 개념 질문
- 구분: **확인된 학습 질문** / **추가 개념 정리** / **가상 사례** / **미검증 구현**
- 공개 범위: 일반적인 소프트웨어 공학 개념과 가상 사례만 포함

## 1. 왜 학습했는가?
개발은 코드를 작성하는 일만이 아니다. 누가 어떤 목적을 달성해야 하는지 정의하지 않으면 정상 처리와 예외 처리를 빠뜨릴 수 있다. 오늘 실제로 확인된 활동은 Use Case의 의미를 묻는 질문이다. 아래의 명세와 예시는 이해를 돕기 위해 추가한 내용이며, 실제 시스템을 구현하거나 검증했다는 뜻이 아니다.

## 2. Use Case란?
Use Case(유스케이스)는 외부 행위자(Actor)가 목표를 달성하기 위해 시스템과 상호작용하는 시나리오다. 핵심 질문은 **누가, 왜, 시스템을 어떻게 사용하며, 어떤 결과를 얻는가?** 이다.

- Actor: 시스템 외부에서 상호작용하는 역할. 사람뿐 아니라 다른 시스템도 가능하다.
- Goal: 달성하려는 업무 목표.
- Trigger: 시나리오 시작 사건.
- Precondition: 실행 전에 필요한 조건.
- Main Flow: 정상적인 흐름.
- Alternative/Exception Flow: 대안 및 실패 흐름.
- Postcondition: 처리 후 보장할 상태.

### 초보자용 설명
도서관에서 책을 빌리는 행동을 생각하자. 회원이 대출 버튼을 누르면 시스템은 회원 자격과 책의 대출 가능 여부를 확인하고 기록을 생성한다. 책이 이미 대출 중이라면 성공 대신 대출 불가 이유를 알려줘야 한다. 버튼 하나를 구현하는 것과 사용자 목표 전체를 충족하는 것은 다르다.

## 3. 문제·원인·해결 방식
**문제:** "대출 기능을 만들어 달라"는 요구만으로는 자격 조건, 중복 신청, 대출 한도, 저장 실패 시 처리가 모호하다.

**원인:** 사용자 목표와 업무 규칙, 예외 조건, 완료 기준을 사전에 합의하지 않았다.

**해결 방향:** Use Case 명세를 작성하고 정상·예외 흐름을 테스트 조건으로 연결한다. 실제 서비스에서는 정책 담당자와 함께 규칙을 확인해야 한다.

## 4. 가상 사례: UC-001 도서 대출 신청
| 항목 | 내용 |
|---|---|
| Actor | 도서관 회원 |
| Goal | 대출 가능한 도서를 신청 |
| Trigger | 대출 신청 버튼 선택 |
| Precondition | 유효한 회원 자격 |
| Success | 대출 기록 생성 및 결과 안내 |

**정상 흐름**
1. 회원이 도서를 선택한다.
2. 시스템이 회원 자격을 확인한다.
3. 시스템이 도서 대출 가능 여부와 한도를 확인한다.
4. 시스템이 대출 기록을 생성한다.
5. 시스템이 성공 결과를 반환한다.

**예외 흐름**
- 회원 자격이 유효하지 않으면 신청 거절.
- 이미 대출된 도서라면 대출 불가 안내.
- 한도 초과 시 사유 안내.
- 기록 저장 실패 시 성공으로 표시하지 않고 오류 처리 및 재확인.

이는 **가상의 예시**이며 실제 시스템에 적용하거나 테스트한 내역이 아니다.

## 5. Use Case와 다른 개발 산출물의 차이
| 구분 | 질문 | 산출물 |
|---|---|---|
| User Story | 사용자가 어떤 가치를 원하는가? | 간결한 요구 문장과 인수 조건 |
| Use Case | 사용자가 시스템과 어떤 순서로 상호작용하는가? | 정상·대안·예외 시나리오 |
| API 명세 | 프로그램은 어떤 요청과 응답을 주고받는가? | 엔드포인트와 계약 |
| 테스트 케이스 | 실제 결과가 기대 조건과 일치하는가? | 입력·기대값·실행 결과 |

Use Case 하나에 API가 여러 개 필요할 수 있고, API 하나를 여러 Use Case가 재사용할 수도 있다. Use Case는 구현 코드나 DB 설계 자체가 아니다.

## 6. Use Case에서 테스트를 도출하는 방법
| 테스트 | 조건 | 기대 결과 |
|---|---|---|
| TC-001 | 유효한 회원, 대출 가능한 도서 | 대출 성공 |
| TC-002 | 무효한 회원 | 거절 및 이유 안내 |
| TC-003 | 이미 대출된 도서 | 대출 불가 |
| TC-004 | 대출 한도 초과 | 한도 초과 안내 |
| TC-005 | 저장 실패 | 성공 표시 금지 및 오류 처리 |

**주의:** 위 표는 테스트 *설계 예시*다. 실제 실행 출력이나 통과 기록은 없다.

## 7. 운영·VOC 관점에서 확장하기
실제 운영에서는 "대출 버튼을 눌렀는데 완료됐는지 모르겠다"는 문의가 발생할 수 있다. 단순 화면 오류로 분류하지 않고, 요청 접수 여부 → 자격 검사 → 재고/상태 검사 → DB 저장 → 응답 반환의 단계별 실패 지점을 구분해야 한다.

- **VOC 누수 가설 1:** 처리 성공 후 응답이 끊겨 사용자가 실패로 오해하고 재신청할 수 있다. 대응: 요청 식별자, 멱등성 검토, 처리 결과 재조회.
- **VOC 누수 가설 2:** 거절 사유가 모호해 동일 문의가 반복된다. 대응: 업무 규칙별 오류 코드와 이해 가능한 안내.
- **VOC 누수 가설 3:** 고객센터의 반복 문의가 개발 백로그에 연결되지 않는다. 대응: 문의 유형, 원인, 발생 단계, 재발 여부를 구조화해 관리.
- **VOC 누수 가설 4:** 화면 성공과 DB 반영 상태가 다를 수 있다. 대응: 서버 결과 기준의 상태 확인과 장애 후 정합성 검사.

이 항목은 **일반적인 운영 리스크를 바탕으로 제안한 가설**이며, 실제 특정 회사에서 발생한 사건이나 측정된 VOC가 아니다.

## 8. 트레이드오프
상세한 Use Case는 요구사항 누락을 줄이는 데 도움이 되지만 작성·유지 비용이 든다. 단순 조회 기능은 간결한 User Story와 인수 조건으로 충분할 수 있다. 결제·취소·권한·재처리처럼 예외와 상태 전이가 복잡한 기능은 상세 Use Case가 유리하다. 문서가 실제 동작과 달라지지 않도록 변경 시 함께 갱신해야 한다.

## 9. 확인된 사실, 미검증, 다음 과제
**확인된 사실**
- 2026-10-25 대화에서 Use Case의 의미를 질문했다.
- 본 문서는 일반적인 개념과 가상 도서 대출 사례로 확장 정리했다.

**미검증**
- 실제 Use Case 명세서 승인, 코드 구현, SQL/API 실행, 테스트 통과, 배포는 확인되지 않았다.
- 실제 장애·VOC 데이터와 원인 분석을 수행한 것은 아니다.

**다음 과제**
1. 공개 가능한 가상 업무를 하나 정해 Actor와 Goal을 정의한다.
2. 정상·대안·예외 흐름을 작성한다.
3. 각 예외에 대해 사용자 안내, 운영 로그, 복구 절차를 정한다.
4. 인수 조건과 테스트 케이스를 연결한다.
5. 실제 실행 결과가 생기면 명령 출력과 검사 날짜를 별도로 기록한다.
