## 1. 왜 공부했는가
교수님 Chapter 07의 회원 등록 POST/INSERT/Transaction 수업에서 rollback을 단순 SQL 오류 처리로 이해하는 데 그치지 않고, 실제 기업의 회원가입·결제·주문·재고·송금·예약·환불·정산·물류 서비스에서 **어디서 사전 차단하고 어디서 원자성을 보장하며 언제 보상해야 하는지** 판단할 수 있도록 설계했다. Chapter 06에서는 사용자가 GET/POST + INSERT까지 일부 구현했고 Chapter 07은 EmailStr, 중복 409, INSERT 결과, 422/500, commit/rollback 및 DB evidence 검증에 초점이 있다.

## 2. 핵심 개념 — 중학생 설명과 실무 정의
- **사전 검증(백엔드)**: 가게 문 앞에서 주문 자격과 입력을 먼저 확인한다. 명백히 불가능한 작업을 DB에 쓰기 전에 차단한다.
- **DB 제약/잠금**: 계산대에서 최종적으로 중복 판매나 음수 재고가 일어나지 않도록 막는 마지막 안전장치다.
- **Transaction**: DB 변경 여러 개를 하나의 성공/실패 단위로 묶는 경계다.
- **commit**: 지금까지의 DB 변경 확정.
- **rollback**: 아직 확정되지 않은 **같은 DB 트랜잭션의 변경** 취소. 이미 commit된 값이나 외부 PG·WMS 작업은 되돌리지 못한다.
- **멱등성(idempotency)**: 동일한 요청이 여러 번 도착해도 의도한 결과가 중복 수행되지 않게 한다.
- **보상 트랜잭션/대사**: 외부 시스템에서 이미 일어난 일을 별도 취소·복구·상태조회로 조정한다.
- **Evidence**: HTTP 상태만 보지 말고 DB SELECT, 서버 로그, 외부 거래상태, 재시도 후 결과를 비교한 증거.

## 3. 공통 처리 흐름

```text
클라이언트 요청
  ↓
FastAPI(Presentation) : Pydantic 형식 검사 → 422
  ↓
Application / Domain : 업무규칙·사전조회 → 거절(예: 409)
  ↓
Infrastructure / PostgreSQL : 제약조건·조건부 UPDATE·잠금
  ↓
같은 DB 작업 성공 → commit / 실패 → rollback
  ↓
외부 PG·은행·WMS에 이미 발생한 작업? → 상태조회·멱등 재처리·보상·대사
  ↓
API 응답 + DB/외부 상태 검증
```

## 5. 실행 절차 — QA 템플릿
1. **사전 상태**: 대상 테이블/거래의 시작 행 수·잔액·재고·상태를 SELECT로 기록.
2. **정상 요청**: 기대 응답 코드와 DB 상태 일치 확인.
3. **오류 주입**: 테스트 전용 DB 환경에서 장애 유발. 운영·공용 DB 임의 변경 금지.
4. **응답 검증**: HTTP 201/409/422/500 등 실제 상황에 맞는 상태와 로그 확인. 500을 모든 DB 오류에 무조건 대응시키지 않는다.
5. **사후 검증**: commit/rollback 범위, 추가·수정된 행, 외부 상태를 직접 재조회.
6. **중복·동시성**: 같은 요청 2회, 마지막 재고 병렬 요청 등으로 제약조건 확인.
7. **복구 검증**: 네트워크 타임아웃과 응답 유실 상황에 멱등 키로 재시도하고 중복 집행 방지 확인.
8. **기록**: TC-ID, 입력·장애 지점·예상/실제 상태·로그·증거 링크·판정·실행 일시·담당자.

## 6. SQL 학습 예시(미실행)
```sql
-- 단순 수량 차감을 DB에서 최종 검증
UPDATE product_variants
SET stock = stock - 1
WHERE id = 100 AND stock >= 1
RETURNING stock;
```
결과가 0행이면 조건을 만족하는 재고 변경이 이뤄지지 않은 것이다. 주문 INSERT와 재고 변경을 묶으려면 **같은 커넥션·트랜잭션에서 commit을 한 곳에서** 수행해야 한다.

```python
# 구조 예시. 실제 모델/테이블 이름과 예외 계약에 맞춰 구현 필요.
with get_connection() as conn:
    with conn.cursor() as cur:
        cur.execute("UPDATE product_variants SET stock=stock-1 WHERE id=%s AND stock>=1 RETURNING stock", (variant_id,))
        if cur.fetchone() is None:
            raise InsufficientStockError()
        cur.execute("INSERT INTO orders (...) VALUES (...) RETURNING id")
        created_order = cur.fetchone()
# psycopg 연결 컨텍스트가 정상 종료되면 commit, 예외로 종료되면 rollback
```
위 주문 INSERT는 **설명용 의사코드**로 SQL 그대로 실행 가능한 완성문이 아님.

## 8. 위험 및 개선 Best Practice
- 입력 검증과 DB UNIQUE/제약은 경쟁 관계가 아닌 다층 방어.
- 실패한 SQL 앞에 성공한 변경이 없으면 롤백의 원자성 증거가 약하므로 **의도적인 다단계 DB 변경 테스트** 설계.
- 외부 결제 승인 후 DB 장애는 ‘PG 결제도 롤백됐음’으로 간주 금지.
- 트랜잭션을 외부 HTTP 호출까지 장시간 붙잡지 않도록 설계.
- 서버 응답이 타임아웃이어도 DB commit 여부가 불확실할 수 있어 재조회 및 멱등성 필요.
- 운영/공용 DB가 아니라 격리된 테스트 DB에서 실패를 재현.
- 민감정보는 Git에 커밋하지 않고 `.env` 제외, 외부 기록 시 `***` 적용.
- 다음 학습: TC01 실제 201/409/422/500 확인 → TC02 롤백 테스트 → TC03 동시성 테스트 → TC04 외부 결제 실패 복구 설계.
